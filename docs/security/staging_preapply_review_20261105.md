# 試験環境（bondex-staging）への SQL の適用の前の確認

作成: 2026-11-05。対象: Supabase `bondex-staging`（`oeucjrmuigtfnwowvzwr`・シンガポール・Free）。**まだ SQL は適用していない**（適用は別の承認）。

## 1. 接続の確認（読み取りだけ）— 17/17 合格

`bash scripts/staging/check-connection.sh`。値は画面に出さない。
- 接続ファイル `.env.staging.local`: 権限 600・Git の対象外・本番の ID なし・接続文字列の利用者は `postgres.oeucjrmuigtfnwowvzwr`・Session pooler・API の URL は試験環境・キーは publishable と secret の形で取り違えなし。
- DB: 利用者 postgres・PostgreSQL 17.11・**読み取りだけの接続**（書き込みの SQL は拒否）・public の表 0・試験環境の印なし・pg_cron と pg_net は入っていない。
- API: 2つのキーとも試験環境の認証の稼働の確認で 200。anon キーは本番の API では使えない。

**起きたこと（訂正済み）**: 最初の確認で、読み取りだけの設定を接続の設定（PGOPTIONS）で渡したが、Supabase の接続の中継（Supavisor）がこれを通さず、書き込みの確認の SQL が実際に空の表 `public._write_probe`（RLS なし・行 0）を作った。気づいてすぐ消し（試験環境だけ）、表 0 に戻したことを確認。スクリプトは、DB の中で最初に読み取りだけに切り替える形に直し、書き込みの確認も必ず取り消す（begin … rollback）形にした。本番には接続していない。

## 4. SQL 065 と最新の main（重複の適用・既存の表の破壊の防止）

- 065 の 3表は、本番の表の定義の写し（順 1）に**すでに入る**。`sql/065_sagawa_bulk_pickups.sql` は試験環境では**流さない**（重複の適用をしない）。
- 順 1 は `shipments` があれば飛ばす。順 0 は、印が無いのに public に表があれば止める（既存の表を上書きしない）。
- 067〜079 は 065 の表を変えない（予行演習で 065 の表がある状態で全部通ることを確認）。
- 統合ブランチは main の #100・#101（065 を含む）を取り込んでいない。試験環境で動かすアプリ（統合ブランチ）は 065 の表を使わないので、表があっても影響しない。main へのマージの前の取り込みは別の作業（`docs/security/prod_sql065_mismatch_20261105.md`）。

## 5. 切り戻し

| 場面 | 方法 |
|---|---|
| 途中で 1つの SQL が失敗 | そのファイルの分は何も変わらない（1つのトランザクション）。原因を直して `apply.sh migrate` を流し直す（どの SQL も流し直せる） |
| 試験環境を最初からやり直す | Supabase のダッシュボードで `bondex-staging` を消して作り直す（Free・データはダミーだけ）。接続ファイルは作り直す（`setup-env.sh`） |
| 079 だけ戻す | `sql/rollback/rollback_079.sql` → 074 の `b2c_charge_check` を流し直す（本番移行チェックリストの 6章と同じ） |
| 067〜072 を戻す | `sql/rollback/rollback_067_072.sql`（本番移行チェックリストの L3 と同じ） |
