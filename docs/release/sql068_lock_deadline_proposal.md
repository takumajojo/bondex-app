# SQL068 など: 表の確保の「10秒で諦める」を時間で区切る（提案）

作成: 2026-11-05。状態: **提案だけ（SQL は未変更）**。変更の案: `docs/release/patches/migration_lock_deadline.patch`（`git apply --check` 済み）。
担当: Biz-Logi の移行の担当のセッション（調整中）。適用はたくまさんの承認の後。

## 1. 何が起きているか

本番移行の SQL（067・068・070・071・072・078・切り戻し 2本・`sql/ops/migration_lock_prefix.sql`）は、最初に関係する表をまとめて確保する。
確保できなければ 0.2秒待って取り直し、10秒たっても確保できなければ何も変えずに失敗する、という設計（068 の 16〜24行目の説明）。

実装は **回数（50回 × 0.2秒）** で数えている。1回ごとに「確保を試す・失敗の例外を受ける・0.2秒待つ」の手間が加わるので、
実際に諦めるまでの時間は 10秒より長く、機械の負荷で変わる。

| 計測（ローカルの PostgreSQL・表を掴んだままの別のトランザクションを用意） | 今の実装（回数） | 案（時間） |
|---|---|---|
| 1回目（2026-11-05 16:30・他の試験が動いている） | 12.44秒・12.48秒 | — |
| 2回目（18:00・負荷なし／CPU の負荷 4本） | 10.38秒・10.24秒・10.39秒 | 10.12秒・10.12秒・10.11秒 |

移行のリハーサル（`scripts/test-integ/migration-rehearsal.sh`）は「12秒の長いトランザクションの最中の 068 は 10秒で諦める」を確かめる。
諦めるまでが 11秒を超えると、その間に長いトランザクションが終わって 068 が通ってしまい、この確認が失敗する。

| リハーサル | 結果 |
|---|---|
| 今の実装・単独で 7回（16:25〜16:30） | 7回とも失敗（068 が通った・12秒を超えた） |
| 今の実装・全試験の中で（16:50） | 合格 |
| 今の実装・単独で 3回（18:04） | 3回とも合格 |
| **案・単独で 5回（18:02）** | **5回とも合格** |
| 案・DB の結合試験（`db-integration.sh`） | 101/101 合格 |

## 2. 影響（安全性）

- 失敗の時は「何も変えずに失敗する」のは同じ（1つのトランザクションの中で流す。例外で全部が戻る）。
- 待っている間は表を持たないのも同じ（nowait で試し、失敗したら何も持たずに待つ）。利用者の操作とデッドロックしない。
- 違いは「諦めるまでの時間が 10秒を超えない」ことだけ。本番の移行の手順書の「10秒で失敗したら少し待って流し直す」がそのとおりになる。
- 長く待ちすぎないので、移行の SQL を流している人が「止まった」と誤解して中断するおそれが減る。

## 3. 本番・staging の状態

- 本番: 067〜079 は **未適用**（本番移行チェックリストの手順 2 の前）。main にも無い（main の sql は 065 まで）。
- staging（bondex-staging）: 067〜079 を適用済み（2026-11-05）。表の確保の部分は「流す時の手順」なので、**適用済みの DB の中身には影響しない**。
  直した後に staging で流し直す必要は無い（新しく流すのは本番の移行の時だけ）。
- 本番に適用済みの SQL は変えない。今回の対象は、まだどこにも本番適用していない移行の SQL の「表の確保の前置き」だけ。

## 4. 進め方の案

1. Biz-Logi の担当のセッションが、この案（9ファイルの同じ前置き）を統合ブランチの SQL に取り込む（または別の案を出す）。
2. 移行のリハーサル・DB の結合試験を流す（ローカル）。
3. 本番移行チェックリスト（`MyClaudecode/docs/bizlogi-prod-migration-checklist-20261104.md`）の「10秒で失敗」の説明はそのまま使える。
4. 新しい migration（081 など）は要らない（本番に未適用の SQL の前置きの直しのため）。
