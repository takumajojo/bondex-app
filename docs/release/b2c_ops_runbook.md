# B2C 公開の後の監視と障害の対応の手順書（案）

作成: 2026-11-05。対象: 阪急交通社向けの限定 Beta（B2C Phase 1A）。**本番での運用の開始の前に、当番・連絡の順番をたくまさんが決める（下の【未決】）。**
前提: 運営への通知は `sendOpsAlert`（宛先 = `ALERT_EMAIL`・support@bondex.express。Slack は `SLACK_WEBHOOK_URL` がある時だけ）。運営の画面は `/operator`・`/operator/b2c`。
**大原則: 新しい予約の受付を止めても、既存の予約の配送・請求・回収・問い合わせの対応は続ける**（B2C のスイッチは別々に止められる: `lib/b2c/flags.ts`）。

| いつ | 見る所 | 確かめること |
|---|---|---|
| 毎朝・夕方 | `/operator/b2c` | 結果不明の請求（unknownCharges）・保留の請求（on_hold）・通知の要確認（outbox）・ホテルの確認待ち |
| 夕方 18:00〜 | 運営への通知・`/operator`（集荷依頼） | 集荷漏れの可能性・明日の集荷の依頼漏れ（19:00〜） |
| 毎日 | 定時の処理が動いているか | `select * from cron_heartbeats`（最後の成功・失敗の連続）・GitHub Actions の Cron heartbeat check の結果・pg_cron の実行の記録（`net._http_response`） |

## 1. 事象ごとの対応

各事象: **検知** → **通知先** → **対応** → **復旧の確認** → **記録**（`~/JOJO/state/bondex.md` に結論を 1行・必要なら事故の記録）。

| # | 事象 | 検知 | 通知先 | 対応 | 復旧の確認 | 再発防止の記録 |
|---|---|---|---|---|---|---|
| 1 | 予約のエラー（予約の画面で失敗が続く） | 旅行者・阪急からの問い合わせ／Vercel のログ（`[b2c]`）／`/api/b2c/orders` の 5xx | 運営 | 原因が DB・Google の場所の照会・佐川の日数のどれかを切り分け。続くなら `B2C_BOOKING_ENABLED` を OFF（新規だけ止まる） | 社内の試験の予約が通る | 原因・止めた時間・影響の件数 |
| 2 | カード登録の失敗 | `/operator/b2c`（card_status=failed）・旅行者の問い合わせ | 運営 | Stripe のテスト・本番の状態を確認。カード会社の拒否なら別のカードを案内。3D セキュアの失敗は旅行者に再試行を案内 | 同じ予約でカード登録が registered | 拒否の理由の分類 |
| 3 | Stripe の請求の失敗・結果不明 | 運営への通知「【B2C 請求】要確認」（結果不明・保留・予定を 60分過ぎても未完了・処理中のまま 10分。同じ請求の同じ状態は 1日 1回・状態が変われば再通知・`lib/b2c/charge-watch.ts`）と `/operator/b2c` | 運営（メール・Slack） | 結果不明は**再請求しない**。照合（10分後に自動）を待ち、Stripe の画面で PaymentIntent を確かめる。失敗は支払のページの案内（自動で 1・3・7日） | 状態が succeeded か、案内中 | PaymentIntent の ID・原因 |
| 4 | 二重請求の疑い | 旅行者の問い合わせ・Stripe の画面で同じ予約に Charge が 2つ | 運営→たくまさん | `B2C_CHARGE_LIVE` を OFF（請求を止める・予定は残る）。Stripe と DB（`b2c_payments`）を照合。二重なら返金（運営の画面・理由を書く） | Charge と DB の 1対1・返金の完了 | 原因の調査（DB の一意の制約・重複防止のキーがあるので通常は起きない） |

| 6 | 集荷依頼の送信の結果不明 | 通知「送信中のまま止まっています」（5分）・夕方の依頼漏れの通知（19:00〜・締め前と超過に 1回） | 運営 | **自動で再送しない・Excel に切り替えない**。世田谷営業所に受付の有無を確認し、運営の画面で結果を記録 | 記録が accepted か、依頼なしを確認して送り直し | 原因（通信・Biz-Logi） |

| 10 | DB の障害 | Vercel のログ（Supabase の接続の失敗）・予約の画面の「混み合っています」・Supabase の状態のページ | 運営→たくまさん | `B2C_BOOKING_ENABLED` を OFF。カード登録の途中は Stripe 側に残り、復旧後に照合（card_dbdown の試験で確認済み）。請求は止まり、復旧後に照合 | Supabase の復旧・`/operator/b2c` の照合 | 停止の時間・影響の件数 |

## 2. 止め方の早見表（`lib/b2c/flags.ts`。どれも "true" の時だけ ON）

| スイッチ | OFF にすると | 既存の予約への影響 |
|---|---|---|
| `B2C_BOOKING_ENABLED` | 新しい予約・カード登録の受付が止まる | なし（確認・取消・請求は続く） |
| `B2C_CHARGE_LIVE` | 請求の実行が止まる（予定は残り、ON に戻すと照合してから 1回ずつ） | 請求が遅れる |
| `B2C_MY_BOOKING_ENABLED` | 予約の確認ページ・取消が止まる（緊急時だけ） | 旅行者が確認・取消できない |
| `B2C_SCHEDULER_ENABLED` | リマインド・期限切れ・請求の定時の処理が止まる | 請求・通知が止まる |

## 4. 監視の仕組みと、止まった時に何が起きるか（2026-11-05・単一障害点の調査）

見張りは 2つの別の仕組みで、お互いを見張る。どちらも**読むだけ**で、請求・照合・Stripe には触れない（試験 `scripts/test-integ/charge-watch.ts` 12章でコードを確認）。
二重請求・誤請求の防止は見張りに依らない（DB の一意の制約 `b2c_payments_one_base_per_order`・請求の確保の関数 `b2c_claim_charges`・Stripe の重複防止キー）。見張りが止まっても請求は誤らない。止まるのは「知らせ」だけ。

| 仕組み | 動かすもの | 見張る相手 | 止まったと判断する時間 |
|---|---|---|---|
| A. pg_cron（Supabase） | 集荷の監視（10分おき・8〜23時）・B2C の定期の処理（数分おき） | B の見張りの最後の実行（`cron_heartbeats` の heartbeat-check） | 8時間（GitHub の間引き 2〜6時間を見込む・`HEARTBEAT_CHECK_STALE_MIN`） |
| B. GitHub Actions（`.github/workflows/cron-heartbeat.yml`・1時間おき） | `/api/cron/heartbeat-check` | A の 2つの処理の最後の成功・失敗の連続、B2C の請求 | B2C 30分・集荷の監視 40分・3回続けて失敗 |

| 止まったもの | 気づく仕組み | 知らせの経路 | 請求への影響 |
|---|---|---|---|
| pg_cron | B（最大で GitHub の遅れ＋1時間） | 運営へのメール・Slack ＋ GitHub の失敗の知らせ | 請求の処理も止まる（請求されないだけ。再開後に照合してから 1回ずつ） |
| GitHub Actions | A（8時間） | 運営へのメール・Slack | なし |
| Vercel（アプリ） | B の呼び出しが失敗 → GitHub の失敗の知らせ | GitHub のメール（アプリのメールは使えない） | 請求の処理も止まる |
| Supabase | 同上（B が 503） | GitHub のメール | 請求の処理も止まる |
| メールの送信（Resend・SMTP） | 送れなかった知らせは次の回に送り直す。B が 503 → GitHub のメール | Slack（設定時）・GitHub のメール | なし |
| A と B が同時に | **自動では気づけない** | 0章の毎日の見回り（`cron_heartbeats`・GitHub の Actions の画面） | 請求の処理も止まる |

残る単一障害点（受け入れて、毎日の見回りで補う）:
- GitHub の失敗の知らせは、リポジトリの持ち主の GitHub の通知の設定（Actions の失敗をメールで受け取る）に依る。**公開の前に設定を確かめる**。
- Slack を設定しなければ、運営への知らせはメールの 1経路だけ（`SLACK_WEBHOOK_URL` の設定を推奨）。
- 公開の直後は B の記録が無いので、A は「見張りが止まった」を知らせない（誤報の防止）。**main に入った後の最初の 1回の実行を、GitHub の Actions の画面で確かめる**。
