## 1. PHASE 1 調査結果（既存システムの事実）

根拠はすべて `origin/main` のファイル。

### 1.1 データ構造

- **予約・料金・課金・追跡・監査は、すべて `shipments` 1テーブルに載っている（1区間＝1行）。** bookings / hotels / payments の独立したテーブルは無い。予約は `booking_id` で行をまとめているだけ（`sql/001_shipments.sql`、`sql/003` の `(booking_id, leg_index)` UNIQUE）。
- **代理店は `shipments.agency text NOT NULL`（代理店名の文字列）で識別している。** `agency_id` も FK も無い。課金・月次請求・RLS・通知・レポートが、この文字列で照合している。
- `shipments.status` の値は CHECK 制約で固定されている（`sql/011:24-25`）: `requested, pending, issued, picked_up, in_transit, delivered, failed, cancelled`。
- `agencies.payment_method` は `'invoice' | 'card'`（`sql/010:15`）。`agencies.billing_exempt=true`（テスト代理店）は、課金（`lib/charge.ts:94`）・月次請求（`app/api/cron/monthly-invoices/route.ts:72`）・請求締切（`invoice-deadline:84`）・自動送付（`invoice-autosend:77`）・追加清算（`addition-settle:78`）のすべてで除外されている。
- **ホテルマスタは無い。** 各行に Google `place_id`・ホテル名（ja/en）・都道府県・市区を非正規化して持っているだけ。
- B2B では民泊・個人宅も受け付けている（`from_residence` / `to_residence` jsonb、`lib/residence.ts`、`sql/016`）。**「フロントあり・有人」という概念はコードに存在しない。**

### 1.2 予約・料金・日付

- B2B 予約 API（`app/api/agency/booking/route.ts`）は `status:"requested"`, `amount_yen:0` で保存する。金額は、運営が発行操作（`app/api/shipandco/create/route.ts:979`）をした時点で「個数 × 代理店単価」として確定する。
- 料金は `lib/pricing.ts:10` の `PRICING.regularPrice = 4980` で定義されている（**税抜**・1個あたりの単価）。区間別・サイズ別の料金という概念は無い。
  - B2C は**税込表示が必須**。参考値 4,980円（税抜）は、税込で **5,478円**。
- 配達日のルール（`lib/carrier.ts` の `minOffsetDays:1 / maxOffsetDays:7`）は、**送り状を発行する時にしか検証されない**。予約 API には、サーバー側で過去日・当日を弾くチェックが無い。
- **地域ごとの所要日数を計算するロジックは無い。** 営業資料も「目安」の表現で、「保証」「必ず」は使わない方針（`docs/collateral/service-overview/deck.mjs`）。
- 受付締切の表記が、媒体ごとに食い違っている（LP=前日16:00／営業資料=前日18:00／ポータル=前日17:00）。既存の未決事項。
- 祝日は 2026〜2028年分をコードに直接書いている（`lib/business-days.ts:14-30`）。

### 1.3 既存の課金・請求・Stripe 経路の全件調査（修正指示 1）

`STRIPE_SECRET_KEY` を使う箇所、`shipments` の金額・課金列を書き換える箇所、請求書を組み立てる箇所を全件洗い出した。B2C の行（以下「B2C 行」）がこれらに入り込んだ場合の挙動は次のとおり。

| No. | 経路 | 何をするか | B2C 行が入り込んだ場合の危険 |
|---|---|---|---|
| P01 | `lib/charge.ts` `chargeShipmentIfDue` | 集荷完了で off_session の PaymentIntent を作成する | 代理店行の設定次第で、二重課金・課金エラー通知 |
| P02 | 　呼び出し元 `PATCH /api/shipments`（`route.ts:262`） | 運営が手動でステータスを変えた時 | 同上 |
| P03 | 　呼び出し元 `app/api/cron/sync-tracking/route.ts:389` | 追跡の同期時（現在は停止中） | 同上。追跡を再開した瞬間に一斉に走る |
| P04 | 　呼び出し元 `lib/tracking/reconcile.ts:154` | 追跡の照合時 | 同上 |
| P05 | 　呼び出し元 `app/api/operator/charge-retry` | 運営の「課金を再試行」ボタン | 同上 |
| P06 | `app/api/shipments/addition-settle/route.ts:108` | 「追加」区間の Checkout を作成する | 別の決済リンクができ、二重決済 |
| P07 | `app/api/stripe/webhook/route.ts` `handleRefund` / `handleDispute` / `handlePaymentFailed` | PaymentIntent から `shipments` を逆引きし、**見つからなければ throw して 500** | **B2C の返金・係争・決済失敗のイベントが同じ Stripe アカウントから届くと、500 を返し続ける。** Stripe は最大3日再送し、失敗が続くとエンドポイントを無効化しうる。**そうなると B2B の返金・係争の検知まで止まる** |
| P08 | 同 `handleAdditionCheckout` | `metadata.kind==="addition"` の時だけ `charged_at` を記録する | B2C の Checkout は素通りする（危険なし）。ただし B2C を同じルートに足す改修は危険 |
| P09 | `app/api/shipandco/create/route.ts:712-719, 979-990` | 発行時に `amount_yen = 個数 × 代理店単価` で上書きし、status を `issued` にする | **B2C の確定額が 4,980円（税抜）に上書きされる** |
| P10 | `app/api/voucher/generate`・`/operator` の「この依頼を発行」 | `requested` の行を発行キューに出す | B2C 行が発行キューに載り、P09 を誘発する |
| P11 | `app/api/operator/adjust-count/route.ts` | 個数と金額を変え、代理店へ「返金します／追加で請求します」とメールする | 金額の書き換え、代理店宛ての誤った返金案内 |
| P12 | `lib/invoice-build.tsx:110-117`、`cron/monthly-invoices`・`invoice-deadline`・`invoice-autosend` | 代理店名で集計し、月次請求書を作る | 請求対象の代理店名を使えば請求に混入する（`billing_exempt` の代理店なら対象外） |
| P13 | `app/api/agency/invoice/route.ts` | `charged_at` のある区間の領収書を代理店に出す | 代理店ユーザーがいなければ到達しない |
| P14 | `PATCH /api/shipments`・sync-tracking・reconcile の通知 | `sendAgencyStatusEmail`・プッシュ通知 | 旅行者ではなく代理店の連絡先へ送られる／送り先なしの警告 |

- 補足: `app/api/agency/shipment/[id]/route.ts`（代理店のセルフ変更）も `amount_yen` を書き換えるが、代理店認証で自社の行に限定されている。B2C 用の代理店にログインユーザーを作らない限り、到達しない。
- `getShipmentByPaymentIntentId`（`lib/shipments-db.ts:845-859`）は `maybeSingle` で検索している。1つの PaymentIntent が複数の行に載ると、エラー → null → 500 になる。

### 1.4 ホテル連絡

- **自動送信は無い。** 運営が電話・メールで手動で連絡し、「連絡済み」を押す（`pickup_hotel_notified_at` / `guest_hotel_notified_at`）。期限は発送日の2営業日前（`lib/hotel-notification.ts:108`）。毎朝の督促 cron がある（`app/api/cron/hotel-contact/route.ts`）。
- 連絡方法・メモは `shipments.hotel_contact_info` jsonb に入っている（`lib/hotel-contact-info.ts`）。**誰が連絡したか、ホテルが受け入れたかの記録は無い**（memo の自由記述だけ）。
- 公式サイトから電話番号を拾う処理（`lib/hotel-website-phone.ts`）、初めてのホテルかの判定（`lib/hotel-history.ts`）、紹介メール（`lib/hotel-intro-email.ts`）がある。
- 既存の確定事項: 「ホテル宛ての紹介メールは社外宛てのため自動送信しない」。

### 1.5 佐川・追跡・配達完了・運営認証

- 2026-09-24 以降、BondEx は送り状を発行しない（`AUTO_ISSUE_ENABLED` の既定は OFF、`lib/waybill-issuance.ts`）。佐川への集荷依頼は、運営が手動で行い記録する（`sql/038`）。
- 追跡の自動同期は**停止中**（`lib/tracking-pause.ts`）。
- 配達完了は、運営の手動ステータス変更だけで決まる。記録は `delivered_at` だけで、**担当者も根拠も残らない**。
- **運営のログインは共有パスワードとパスキーで、個人を識別できない。** セッションは `v1.<期限>.<HMAC>` で、利用者の情報を含まない（`lib/operator-session.ts`）。パスキーには端末名 `label` しかない（`sql/031`）。
- 定期処理は GitHub Actions から `CRON_SECRET` 付きで呼んでいる（sync-tracking は15分ごと）。GitHub Actions は実行が間引かれることがあると記録されている。

### 1.6 バウチャー・メール・公開ページ・テスト

- バウチャー生成（`lib/voucher-regen.tsx`）は、代理店名・代理店の連絡先に依存している。旅行者向けの面は en/zh/it/fr/es で、**日本語が無い**（`lib/guest-language.ts:9`）。
- **旅行者宛てのメールは1通も無い。** `shipments` には旅行者のメール・電話の列も無い。
- 公開追跡ページ `/track/[bookingId]` は、予約番号だけで閲覧できる（トークンなし・姓のみに匿名化）。
- `middleware.ts` は `/api/*` を既定で拒否する。公開されているのは prefix で許可されたものだけ。
- 個人の消費者向けの規約・特定商取引法の表示・キャンセルポリシーは無い。
- **テストの仕組みは無い。** ローカル開発は本番 Supabase を参照する運用（読み取りのみ）。

## 2. 全体アーキテクチャ（ハイブリッド構成・承認済み）

```
[旅行者 ブラウザ]  /en/book  /book(ja)  （noindex）
        │
        ▼
[/api/b2c/*]  公開API（Turnstile＋レート制限＋各ルートで自前検証）
        │
        ├── b2c_orders / b2c_payments / b2c_facilities / b2c_routes …（B2C専用・決済状態の正本）
        │
        │   決済が確定したら「手配処理」が作る（失敗しても再処理できる）
        ▼
[shipments]  既存。B2C行は channel='b2c'・agency='BondEx Direct'
        │    ・課金列（charged_at / stripe_*）は使わない（DBトリガーで禁止）
        └── 既存の運営フロー（ホテル連絡督促・佐川集荷依頼TODO・追跡・レポート）に表示として載る

[Stripe]  B2C専用アカウント（推奨）… B2BのWebhook・課金キーと物理的に分ける
[B2C管理画面] /operator/b2c/*  … 共有ログイン＋担当者個人のログイン（二段階認証）＋監査ログ
```

### 設計の核心（B2B を壊さないための原則）

1. **決済状態の正本は `b2c_orders` と `b2c_payments` だけ。** `shipments` の `charged_at`・`stripe_payment_intent_id`・`charge_amount_yen`・`stripe_checkout_*` は B2C 行では常に NULL のまま使わない（4章）。
2. **未払い・未確認の予約は `shipments` に入れない。** 決済が確定した後に、手配処理（9.4）が `shipments` 行を作る。
3. **B2C 行の識別は `shipments.channel='b2c'`** を正にする。`b2c_order_id`・専用代理店名 `BondEx Direct` は補助の目印にする。
4. **誤課金の防止は3層。** 層1 Stripe アカウントの分離、層2 アプリ共通ガード、層3 DBトリガー（4章）。
5. **既存テーブルへの変更は追加だけ。** `shipments` に列を2つ追加（`channel`、`b2c_order_id`）、`agencies` に1行 INSERT、`shipments` にトリガーを1つ追加。既存の列の型・制約の変更や削除はしない。

## 3. 施設適格性と予約ごとの受け入れ確認（修正指示 2・5）

**次の2つを、別々の仕組みとして扱う。**

| | 施設の適格性（facility eligibility） | 予約ごとの受け入れ確認（booking acceptance） |
|---|---|---|
| 問い | このホテルは、そもそも B2C の対象施設か | このホテルは、この予約のこの荷物を、この日に預かれるか・受け取れるか |
| 単位 | 施設（`place_id`）ごと。一度確認すれば以後の予約で使える | 予約×集荷側／配送側ごと。毎回確認する |
| 記録先 | `b2c_facilities`、`b2c_facility_reviews` | `b2c_hotel_acceptances` |
| いつ | 予約前（未確認なら予約リクエストの段階） | 予約確定の後〜集荷前日まで |
| 断られた場合 | 施設を対象外にする。以後は予約不可 | その予約をキャンセルし、全額返金する（3.6）。施設は原則として確認済みのまま |

### 3.1 施設の状態

| 状態 | 意味 | 予約画面での扱い |
|---|---|---|
| `verified`（確認済み） | 運営が 3.3 の基準をすべて確認した | 即時予約・決済できる |
| `unverified`（未確認） | マスタ未登録、または確認期限切れ | **決済前の予約リクエスト**として受け付ける（審査に回す） |
| `rejected`（対象外） | 運営が審査し、基準を満たさないと判断した（民泊・無人・フロントなし等） | **予約もリクエストも不可** |

- **「確認済み」にできるのは、運営の審査だけ。** 自動処理で確認済みにすることはない。
- **「対象外」にできるのも、運営の審査だけ**（根拠の記録が必須）。自動で対象外にすることはない（3.2）。
- 確認済みには**有効期限**を持たせる（既定12か月）。期限が切れたら未確認に戻し、再審査する。
- **民泊・無人施設が通らない根拠は、キーワード判定ではなく「確認済みの施設でなければ決済できない」という構造にある。** 未確認の施設は必ず運営の審査を通る。審査で民泊・無人施設と分かれば対象外になり、その予約は成立しない。

### 3.2 自動の事前ふるい分け（v1.1 で見直し）

v1.0 では、名称・住所のキーワードで自動的に禁止にしていた。正規のホテルを誤って拒否するおそれがあるため、次のとおり改める。

**自動で選べなくするのは、次の2つだけ（キーワードは使わない）。**

| 条件 | 扱い | 理由 |
|---|---|---|
| 運営が対象外（`rejected`）と登録した施設（`place_id` が一致） | 検索結果に「BondEx の配送対象外の施設です」と表示し、選択不可 | 運営が根拠を持って判断した、明確な禁止施設 |
| 宿泊施設ではない場所（Places の検索結果で `lodging` の種別を持たない場所。住所・建物・駅など） | 検索結果に出さない | そもそもホテルではない。自由入力を認めないため、ホテルを選ぶ画面に出す必要が無い |

**疑わしい施設は、拒否せず「要確認」の目印を付けて審査に回す。**

- 目印の例:
  - 名称に `apartment`・`condo`・`residence`・`stay`・`house`・`villa`・`民泊`・`Airbnb`・`アパートメント`・`ゲストハウス` などを含む
  - 住所に部屋番号（`#301`・`○○号室`）を含む
  - Places の種別が、貸別荘・ゲストルーム系の種別を示す（種別の一覧は、実装時に Google の現行仕様で確認して辞書に登録する）
  - 口コミの件数が極端に少ない、営業時間・電話番号が無い
- 目印は運営の審査画面で強調表示し、審査の優先度を上げるためだけに使う。**目印があっても、それだけでは拒否しない。**
- 目印の辞書（`b2c_review_signals`）は設定データとして持ち、運営が追加・修正できるようにする。
- 旅行者の画面では、目印の有無を出さない（「確認後にご案内します」とだけ表示する）。

### 3.3 施設の審査（verified にする唯一の経路）

**判定基準（すべて満たした場合だけ verified）**

| No. | 基準 | 確認方法 |
|---|---|---|
| 01 | 旅館業法の許可を受けたホテル・旅館である（住宅宿泊事業法の届出住宅＝民泊、特区民泊ではない） | 公式サイト・自治体の公表情報で確認し、根拠の URL を記録する |
| 02 | フロントデスクにスタッフが常駐している（少なくとも集荷の時間帯 9〜18時と、配達の時間帯） | **公式の電話番号へ電話して確認する**（電話番号は公式サイトから取る。Google の電話データは使わない＝既存方針） |
| 03 | 宿泊客の荷物を、チェックアウト後・チェックイン前に預かれる | 同じ電話で確認する |
| 04 | 佐川急便の集荷担当に荷物を引き渡せる（集荷先として） | 同上 |
| 05 | 宅配便で届いた宿泊客の荷物を受け取り、宿泊客の到着まで保管できる（配送先として） | 同上 |
| 06 | BondEx からの事前連絡の窓口がある（メールでよいか、担当部署） | 同上。メールで連絡してよいという同意を取れたら記録する |
| 07 | 個別の予約ごとの事前確認が必要か、事前の連絡だけで包括的に受け入れられるか | 同上。包括的に受け入れられる場合は `standing_acceptance=true` を記録する（3.5） |

- 集荷先としての可否（04）と配送先としての可否（05）は、**別々に記録する。** 片方だけ可の施設は、可の側でだけ予約を受け付ける。
- 審査の記録には、**担当者（個人ログイン）・日時・方法・応対者・各基準の回答・根拠 URL・メモ**を必ず残す（`b2c_facility_reviews`、追記のみ）。
- 既存の B2B で配達完了の実績があるホテル（`lib/hotel-history.ts` で抽出できる）は、審査候補として優先して表示する。ただし**実績だけでは verified にしない。**
- 審査の結果が対象外のときは、理由を定型から選ぶ（民泊・届出住宅／無人・セルフチェックイン／フロントの時間外／荷物の預かり不可／配送の受け取り不可／その他）。
- ホテル自身から「対象外になっているが対応できる」と連絡が来た場合は、再審査できる（履歴は残す）。

### 3.4 予約者側の確認（安全網として追加する。施設の審査の代わりにはしない）

予約フォームの STEP 3 で、次に同意しないと先へ進めない。

- 英語:
  > Hotel-to-hotel delivery only. Both hotels must have a staffed front desk that can accept and hand over luggage. Airbnb, vacation rentals, and unmanned accommodations are not supported.
  > - [ ] I confirm that both are hotels with a staffed front desk, and that I have a reservation at each hotel under the name below.
- 日本語:
  > ホテル間の配送のみ承ります。集荷先・配送先ともに、スタッフが常駐し、荷物の預かりと受け渡しができるフロントのあるホテルに限ります。Airbnb・民泊・無人の宿泊施設はご利用いただけません。
  > - [ ] 両方とも、スタッフが常駐するフロントのあるホテルであり、下記の予約名で宿泊予約があることを確認しました。
- 両ホテルの**予約名**、**集荷先のチェックイン日・チェックアウト日**、**配送先のチェックイン日・チェックアウト日**を必須の入力にする。

### 3.5 予約ごとの受け入れ確認（修正指示 5）

**状態（`b2c_hotel_acceptances.status`、予約×集荷側／配送側ごと）**

| 状態 | 意味 |
|---|---|
| `pending` | 未連絡 |
| `requested` | ホテルへ連絡済み・回答待ち |
| `accepted` | 受け入れの回答を得た（応対者・日時・方法を記録） |
| `accepted_standing` | 包括的に受け入れる施設（3.3 の 07）。事前連絡を送れば受け入れとみなす |
| `reservation_not_found` | ホテルが予約名・日付で宿泊予約を確認できない |
| `declined` | 受け入れを断られた（理由を記録） |
| `no_response` | 期限までに回答が無い |

**期限と、受け付ける日程の条件**

- 両側とも、**集荷日の前日 15:00 JST** までに `accepted` か `accepted_standing` になっていること。
- 予約の時点で、集荷日まで2営業日を切っている場合は、**両ホテルとも `standing_acceptance=true` の施設に限って**予約を受け付ける（個別に確認する時間が無いため）。それ以外は、予約画面で「この日程ではご予約いただけません」と表示する。
- 運営の作業は、既存のホテル連絡の督促（発送日の2営業日前）と同じ画面・同じ期限に並べる。

**連絡内容（日本語のテンプレート）**

| 集荷先ホテル向け | 配送先ホテル向け |
|---|---|
| 予約番号、宿泊者の予約名、チェックアウト日、個数 | 予約番号、宿泊者の予約名、チェックイン日・チェックアウト日、個数 |
| 集荷日（佐川急便が伝票を持参して集荷） | 配達予定日（目安） |
| チェックアウト時に荷物を預かり、佐川急便の集荷担当へお渡しいただくお願い | 荷物を受け取り、到着まで保管のうえお渡しいただくお願い（チェックイン前に届く場合は明記） |
| 予約名・日付での宿泊予約の照合のお願い／受け入れ可否の回答のお願い | 同左 |

- 送信は既存の方針どおり、**運営が内容を確認してから送る**（社外宛てのため自動では送らない）。メールの同意が無いホテルには電話で連絡する。
- 回答の記録は、B2C の管理画面で、担当者の個人ログインで行う。記録すると、既存の `pickup_hotel_notified_at` / `guest_hotel_notified_at` も同時に更新し、既存の督促を止める。

### 3.6 決済後にホテルが受け入れを断った場合（修正指示 5）

| 事象 | BondEx の対応 | 返金 | 旅行者への通知 |
|---|---|---|---|
| 集荷先が `declined` | 代わりの手段は無い（旅行者がそのホテルに泊まっているため）。予約をキャンセル | **全額**（BondEx 側の事情として扱い、キャンセル料なし） | 断られた事実・キャンセル・返金額と返金の時期（カード会社により数日〜10日程度）・問い合わせ先を ja/en で |
| 配送先が `declined` | 旅行者に連絡し、同じ日程で受け取れる別の確認済みホテル（旅行者の宿泊先）があれば変更を提案する。期限までに決まらなければキャンセル | 変更できなければ**全額** | 同上。変更の提案は返信期限を明記する |
| `reservation_not_found` | 旅行者に予約名・日付の確認を依頼し、訂正後にホテルへ再照会する | 期限までに解消しなければ**全額**（旅行者の入力ミスで手数料を取るかは、未決事項として事業側で判断） | 確認依頼（返信期限つき）→ 結果 |
| `no_response`（前日 15:00 時点） | 電話で再度連絡する。それでも確認できなければキャンセル | **全額** | キャンセルと返金のお知らせ |
| 集荷当日にフロントで断られた・荷物が出てこない | 例外として扱う（`delivery_failed`）。運営がホテル・佐川と調整する | 集荷できなければ**全額** | 当日中に状況を連絡 |

- 返金は運営の管理画面から実行する（8.3）。**理由コード `hotel_declined` 等の BondEx 側の事情による返金は、全額を既定値**にし、旅行者都合のキャンセルと区別して記録する。
- 通知の期限: 断られたことが分かってから、営業時間内なら **2時間以内** に旅行者へ連絡する。
- 施設への影響:
  - 理由が「方針として受けられない」なら、運営が施設を `rejected` にし、未発送の他の予約を例外キューに出す。
  - 「その日だけ満杯」などの一時的な理由なら、施設は `verified` のまま。
  - 90日以内に2回断られた施設には、自動で再審査の目印を付ける（拒否はしない）。

## 4. 決済状態の一元管理と誤課金の防止（修正指示 1）

### 4.1 正本は `b2c_orders` / `b2c_payments`

- 注文の支払い状態 `b2c_orders.payment_status`: `unpaid` / `processing` / `paid` / `partially_refunded` / `refunded` / `disputed`。
- 決済の試行ごとの記録 `b2c_payments`: Checkout セッション ID・PaymentIntent ID・金額・通貨・状態（`open` / `complete` / `expired` / `succeeded` / `failed`）・Stripe から最後に取得した時刻。
- 返金 `b2c_refunds`、係争は `b2c_payments.dispute_*` に持つ。
- `shipments` の B2C 行では、`charged_at`・`stripe_payment_intent_id`・`charge_amount_yen`・`charge_error`・`refunded_at`・`refund_amount_yen`・`disputed_at`・`payment_failed_at`・`is_addition`・`stripe_checkout_session_id`・`stripe_checkout_url` を**一切使わない（常に NULL / false）。**
- `shipments.amount_yen` には、実績レポートで B2B と同じ単位で集計できるよう、**税抜の確定額の写し**を入れる。この値は表示・集計用であり、課金の判断には使わない。B2C の手配処理と、B2C 管理画面の個数変更（専用の DB 関数経由）だけが書き込める（4.4）。

### 4.2 `channel` 列の検討結果: 採用する

| 案 | 内容 | 評価 |
|---|---|---|
| A. 代理店名だけで判別 | `agency='BondEx Direct'` | 文字列の一致に依存する。運営画面の手入力（`/operator` は任意の代理店名で作成できる）で混入しうる。**不十分** |
| B. `b2c_order_id` だけで判別 | NULL でなければ B2C | 判別はできるが、意味が暗黙的になる。将来、OTA 経由など別の販路が増えたときに表せない |
| **C. `channel` 列を追加（採用）** | `shipments.channel text NOT NULL DEFAULT 'b2b' CHECK (channel IN ('b2b','b2c'))` | 明示的で、索引も張れる。既存行は既定値 `'b2b'` になる。PostgreSQL 11 以降では、既定値付きの列追加は表の書き換えを伴わない（既存データ・既存の処理に影響しない） |

- 整合のための制約: `CHECK ((channel = 'b2c') = (b2c_order_id IS NOT NULL))`。
- 将来の販路（`ota` など）は、CHECK に値を足すだけで済む（その時に別途承認を得る）。

### 4.3 3層の防御

**層1: Stripe アカウントの分離（推奨・コード変更なしで最も効く）**

- B2C は **B2B と別の Stripe アカウント**で運用する（Stripe は1つのログインで複数のアカウントを持てる。追加費用なし）。
- 効果:
  - B2B の課金処理（P01〜P05）は B2B のキーしか持たないため、B2C の顧客に課金できない。
  - B2B の Webhook（P07）に、B2C のイベントが届かない（1.3 の 500 問題が起きない）。
  - 売上・入金・明細書の表記・税務の資料を、販路ごとに分けられる。
- 分離しない場合の代替案: B2B の Webhook の `handleRefund` / `handleDispute` / `handlePaymentFailed` の冒頭に、「B2C の決済なら何もせず 200 を返す」判定を足す必要がある（判定方法: PaymentIntent の `metadata.kind==="b2c_order"`、または `b2c_payments` に PaymentIntent ID があるか）。**B2B の Webhook のコードに手を入れることになるため、推奨しない。**

**層2: アプリの共通ガード（`lib/channel-guard.ts`・新規）**

```ts
// 判定は fail-closed: どれか1つでも B2C の目印があれば B2C とみなす
isB2CShipment(row) = row.channel === 'b2c' || row.b2c_order_id != null || row.agency === B2C_AGENCY_NAME
// B2B 専用の処理の入口で呼ぶ。B2C 行なら処理せず、運営へ警告を送る
guardB2BOnly(row, operation): { ok: true } | { ok: false, reason: 'b2c_shipment' }
```

ガードを入れる箇所（1.3 の全経路）:

| 経路 | ガードの入れ方 | B2B の挙動 |
|---|---|---|
| P01〜P05 | `chargeShipmentIfDue` の**最初の行**（安全ゲートより前）で `guardB2BOnly`。呼び出し元4か所すべてを1か所で止める | 変わらない |
| P06 | `addition-settle` の入口で `guardB2BOnly` → 400 | 変わらない |
| P07・P08 | 層1を採用すれば不要。採用しない場合のみ、前述の判定を追加 | 変わらない |
| P09・P10 | `shipandco/create` と `voucher/generate` の入口で `guardB2BOnly` → 409「B2C の予約は B2C 管理画面で扱います」。発行キュー・ダッシュボードの一覧では B2C 行に発行ボタンを出さない | 変わらない |
| P11 | `adjust-count` の入口で `guardB2BOnly` → 409 | 変わらない |
| P12 | `invoice-build` の集計に `.eq('channel','b2b')` を追加する（多重の防御。B2C 用の代理店は `billing_exempt` で、もともと対象外） | 既存行はすべて `'b2b'` なので、結果は変わらない |
| P13 | 変更なし（B2C 用の代理店にログインユーザーを作らない） | — |
| P14 | 通知の送信関数の入口で、B2C 行なら代理店宛てに送らず、B2C の旅行者向け通知（10.3）へ振り分ける | 変わらない |
| 運営による手動の作成 | `/operator` の作成・`saveShipment` で、代理店名 `BondEx Direct` を B2B 経路から指定することを禁止する（予約名として扱う） | 変わらない |
| `PATCH /api/shipments`（ステータス・ホテル連絡の変更） | B2C 行は 409「B2C 管理画面から操作してください」（担当者の記録を必ず残すため。7.2） | 変わらない |

- ガードが B2C 行を止めたときは、運営へ警告を送る（本来は起きないはずの事象なので、起きたこと自体を検知する）。

**層3: DB トリガー（アプリの不具合があっても、DB が拒否する）**

`shipments` に `BEFORE INSERT OR UPDATE` のトリガーを1つ追加する。

- `channel='b2c'` の行で、次の列に値を入れようとしたら**エラーにする**: `charged_at`・`stripe_payment_intent_id`・`charge_amount_yen`・`stripe_checkout_session_id`・`stripe_checkout_url`・`is_addition=true`。
- `channel='b2c'` の行の `amount_yen`・`suitcase_count` の変更は、B2C 専用の DB 関数（`b2c_apply_fulfillment`・`b2c_change_count`）の中からだけ許可する（関数の中で `set_config('bondex.b2c_writer','on', true)` を立て、トリガーがそれを確認する）。
- `channel` 自体を後から書き換えることは禁止する。
- B2B 行（`channel='b2b'`）では、トリガーは何もせず通過する。

> 層3だけでは、Stripe への課金そのものは止められない（P01 は Stripe に課金してから DB に記録するため）。課金を止めるのは層1と層2。層3は、金額の上書きや記録の混入を確実に止める最後の砦。

## 5. 予約フロー

### 5.1 画面フロー（スマートフォン優先）

| STEP | 画面 | 入力 | サーバーの処理 |
|---|---|---|---|
| 1 | 区間と日程 | 集荷地域・配送先地域・集荷日・荷物の個数（1〜5） | 対応区間か、集荷日を受け付けられるかを判定し、配送予定日（目安）を算出する（6章） |
| 2 | 料金と配送予定日 | なし（表示のみ） | 料金ルールから税込総額を算出し、見積を発行する（15分有効） |
| 3 | ホテル | 集荷先・配送先のホテルを検索して選択、各ホテルの予約名と日付、同意のチェック | 施設の状態を判定（3章）。「即時予約」か「予約リクエスト」かを決め、画面に明示する |
| 4 | お客様情報 | 氏名（ローマ字）、メール、電話（国番号付き・推奨）、表示言語 | 形式の検証 |
| 5a | 確認して決済（**両ホテルが verified**） | 規約・キャンセル規定への同意 | **料金・日程・施設の状態をサーバーで再検証** → Stripe Checkout へ |
| 5b | 確認してリクエストを送信（**どちらかが unverified**） | 規約への同意 | 予約リクエストとして保存する。**決済はしない** |
| 6 | 完了 | — | 5a: 予約確定のメールとバウチャー／5b: リクエスト受付のメール |

- 集荷時刻は既定で **11時**（チェックアウトに合わせる既存の運用）。「チェックアウトまでにフロントへお預けください」と案内する。
- 配送予定日は**システムが算出し、旅行者には選ばせない。** 時間帯の指定は、初期リリースでは提供しない。
- 初期リリースは **1予約＝1区間**（往復・複数区間は将来対応）。

### 5.2 注文の状態

注文全体の状態（`b2c_orders.status`）と、支払い（`payment_status`）・手配（`fulfillment_status`）は、**別々の列で管理する。**

```
status:
 pending_review ─承認→ awaiting_payment ─支払い確定→ confirmed ─集荷→ in_transit ─配送完了確定→ completed
      └─拒否→ rejected        └─期限切れ→ expired          │
                                                          ├→ cancelled（運営の処理）
                                                          └→ exception（ホテルの拒否・配達の失敗など。運営が対応）

payment_status:     unpaid → processing → paid → (partially_refunded | refunded) / disputed
fulfillment_status: not_started → pending → done / failed（再処理あり。9.4）
```

| status | `shipments` 行 | 説明 |
|---|---|---|
| `pending_review` | なし | 未確認のホテルを含むリクエスト。運営の審査待ち |
| `awaiting_payment` | なし | 決済待ち |
| `expired` / `rejected` | なし | 期限切れ／運営が拒否 |
| `confirmed` | 手配処理が作る | 支払いが確定し、手配に入った |
| `in_transit` | 連動 | 集荷済み |
| `completed` | 連動 | 配送完了を確定した（7章） |
| `cancelled` | `cancelled` | 運営がキャンセル処理をした |
| `exception` | 連動 | 例外。運営が対応する |

- 状態の遷移は、すべて**条件付き更新**（`update … where id=$1 and status=$期待する状態`）で行う。逆戻りはさせない（遷移表に無い変更は拒否する）。遷移はすべて `b2c_order_events` に記録する。

### 5.3 未確認のホテルを含む予約リクエスト

- 受け付ける条件: 集荷日が**4営業日後以降**（施設の審査と、予約ごとの受け入れ確認の時間を確保するため）。
- 運営の処理期限: 受付から**1営業日以内**に承認か拒否をする。
- 審査画面（`/operator/b2c/requests/[id]`）でできること:
  1. 未確認のホテルを審査し（3.3）、`verified` か `rejected` にする（この結果は以後の予約にも使われる）
  2. リクエストを**承認**する（全ホテルが verified の場合だけ押せる）／**拒否**する（理由は必須・定型から選ぶ）
- 承認したとき: サーバーが料金・日程・施設の状態を**再検証**し、決済の案内（Checkout）を送る。
  - 決済期限 = 「承認から48時間」と「受付締切」の早い方。
  - 金額は、リクエスト時の見積額で固定する（その後に料金が下がっていれば、安い方を採用する）。
- 拒否したとき: 理由（定型）と、確認済みのホテルなら予約できることを案内する。決済していないので、返金処理は不要。
- 対象外（`rejected`）の施設を含む場合は、送信ボタンを出さない（サーバー側でも 422 で拒否する）。

## 6. 配送日・受付条件（修正指示 6）

### 6.1 方針

- **配送日数は区間ごとに設定できる整数**にする（1日・2日に固定しない）。最短と最長を持てるようにする。
- **配送予定日は「目安」であり、確約ではない**ことを明記する。画面・メール・規約で「配達予定日（目安）」と表記し、「保証」「必ず」は使わない（既存の営業資料の方針と同じ）。
  - 理由: 実際の配達は佐川急便の運行に依存し、BondEx が日時を約束できる立場にないため（既存の整理では、BondEx は「確認・取次」）。
  - 遅れたときの対応・補償は未決事項（13章）。
- 予約の可否は、目安の**最も遅い日**を基準に判定し、旅行者が荷物より先にホテルを発つことが無いようにする。

### 6.2 設定データ

**区間 `b2c_routes`**

| 列 | 内容 |
|---|---|
| `origin_area` / `dest_area` | 地域。都道府県の集合で定義する（`b2c_areas`。例: 「東京23区＋神奈川」「京都・大阪」）。佐川の12地帯（`lib/sagawa-rates.ts`）を初期値にし、必要なら細かく分ける |
| `enabled` | B2C で受け付ける区間か（初期は、運営が実績を確認した区間だけ ON） |
| `transit_days_min` / `transit_days_max` | 集荷日から配達までの日数（1以上の整数。例: 1/1、1/2、2/3） |
| `pickup_weekdays` | 集荷できる曜日（例: 月〜土） |
| `delivery_weekdays` | 配達できる曜日 |
| `cutoff_business_days_before` / `cutoff_time_jst` | 受付締切（例: 集荷日の1営業日前の 16:00） |
| `min_lead_days` / `max_days_ahead` | 何日後から何日先まで受け付けるか（既定 1日後〜60日先） |
| `effective_from` / `effective_to` | 適用期間。注文には、使ったルールの ID と内容を保存する |

**日付の例外 `b2c_calendar`**

| 列 | 内容 |
|---|---|
| `date` / `area`（NULL なら全国） | 対象 |
| `type` | `no_pickup`（集荷しない）／`no_delivery`（配達しない）／`no_booking`（受付停止）／`peak`（繁忙期） |
| `extra_transit_days` | 繁忙期に足す日数（例: 年末は +1） |
| `note` | 理由（年末年始、お盆、台風による運休など） |

- 祝日は `lib/business-days.ts` を使う。2029年以降の祝日を追加する作業を、毎年の運用作業として登録する。

### 6.3 判定の手順（予約 API・Checkout の作成時・リクエストの承認時の3回、同じ関数で行う）

1. 区間が `enabled` で、適用期間内である。
2. 集荷日 ≥ 今日（JST）＋`min_lead_days`。**当日の集荷・当日の配送は不可。**
3. 集荷日が `pickup_weekdays` に含まれ、`no_pickup`・`no_booking` に当たらない。
4. 現在時刻が受付締切（集荷日の `cutoff_business_days_before` 営業日前の `cutoff_time_jst`）より前である。
5. 配達予定日（目安）を算出する。
   - 最短 = 集荷日 + `transit_days_min`
   - 最長 = 集荷日 + `transit_days_max` + 期間中の `peak` の `extra_transit_days`
   - 最短・最長が `no_delivery` の日や、`delivery_weekdays` に無い曜日に当たる場合は、次の配達可能日まで後ろにずらす。
6. ホテルの日付との関係を確かめる。
   - 集荷先: チェックイン日 ≤ 集荷日 ≤ チェックアウト日
   - 配送先: 配達予定日の**最長** ≤ 配送先のチェックアウト日の前日（荷物が届く前に旅行者が出発しないため）
   - 配達予定日の最短 < 配送先のチェックイン日の場合は、チェックイン前の保管が必要になる。配送先が 3.3 の 05 で保管可と確認済みの場合だけ受け付け、受け入れ確認の連絡にその旨を明記する。
7. 予約ごとの受け入れ確認の期限（3.5）を間に合わせられる。

- 表示: 最短と最長が同じなら「10月24日（目安）」、違えば「10月24日〜25日（目安）」。
- 区間ごとの日数は、**運営が佐川急便の配達の目安で確認してから登録する**（推測では入れない）。東京〜関西の翌日配送は、実運用で確認できている区間として最初に登録する候補にする。
- 予約の後で例外の日（台風による運休など）を追加したときは、影響する予約を運営の画面に一覧で出し、旅行者への連絡につなげる。

## 7. 担当者の個人認証・監査ログ・配送完了の確定（修正指示 4・追加指示 4）

### 7.1 B2C 管理機能の認証（v1.1 で見直し）

v1.0 の「共有ログインのまま担当者名を選ぶ」方式は、本人の確認にならないため取りやめる。

**方式: 既存の共有ログインはそのまま残し、B2C 管理画面ではその上に担当者個人のログインを必須にする（二重の認証）。**

| 項目 | 内容 |
|---|---|
| 1段目（既存・変更なし） | `middleware.ts` の運営認証（共有ログイン・パスキー）。`/operator/*` と `/api/operator/*` の入口 |
| 2段目（新規） | **Supabase Auth による担当者個人のアカウント**（メール＋パスワード＋**二段階認証の TOTP 必須**）。B2C 管理の API（`/api/operator/b2c/*`）は、すべてのリクエストで担当者のトークンを検証し、二段階認証済み（`aal2`）であることを確認する |
| 担当者の台帳 | `operator_staff`（`auth_user_id` 一意、表示名、権限、有効／無効）。**代理店ユーザー（`user_agencies`）と同じ人が担当者を兼ねることはできない**（両方に登録されていれば、どちらのログインも拒否する） |
| 権限 | `b2c_viewer`（閲覧のみ）／`b2c_operator`（審査・受け入れ確認・配送完了の確定・キャンセル）／`b2c_finance`（返金） |
| 重要な操作の再認証 | 返金・施設を対象外にする・配送完了の取り消しは、直近15分以内に二段階認証を通っていることを必須にする |
| 退職・異動 | `operator_staff.active=false` にすると、即座に B2C の操作ができなくなる（Supabase のアカウントも停止する） |
| B2B への影響 | 既存の運営ログイン・パスキー・セッションの形式・代理店の認証は**一切変更しない** |

- 既存のダッシュボード（共有ログインのみ）から B2C 行を変更する操作は、4.3 の層2で拒否し、B2C 管理画面へ案内する。これで、B2C の操作は必ず個人のログインを通る。
- 費用: Supabase Auth と TOTP の二段階認証は、現行のプランに含まれる（追加費用なしの想定。実装前に、プランの上限を確認する）。
- 比較した別案（採用しない）: 既存のパスキーを担当者ごとにひも付け、セッションに担当者 ID を入れる案。運営の B2B ログインの形式を変えることになり、B2B への影響が大きい。将来、B2B を含めて運営ログインを個人化する時に検討する。

## 8. 変更・キャンセル・返金（追加指示 2）

### 8.1 方針

- 旅行者は、確認ページの問い合わせフォーム（予約番号が入った状態で開く）か、メールで依頼する。**旅行者による自動の変更・キャンセル・返金は実装しない。**

### 8.2 運営の処理画面（`/operator/b2c/orders/[id]`・個人ログイン必須）

| 操作 | できる条件 | 処理 |
|---|---|---|
| ホテルの変更 | 集荷前・新しいホテルが verified | 既存の RPC `apply_hotel_change` を使う。受け入れ確認をやり直す（3.5） |
| 日程の変更 | 集荷前・新しい日程が 6.3 を満たす | 日付を更新し、受け入れ確認をやり直す |
| 個数の変更 | 集荷前 | 増える場合は、追加分の決済リンクを送る（B2C 専用。B2B の addition-settle は使わない）／減る場合は、一部を返金する |
| キャンセル | 集荷前（集荷後は配送を止められないため、返金するかの判断だけ） | `shipments` を `cancelled`（既存の監査列 `cancelled_at / by / source='operator'`）、`b2c_orders` を `cancelled` |
| 返金 | 支払い済み | 8.3 |

- すべての操作で、担当者と理由を必須にし、監査ログ（7.2）に記録する。

### 8.3 返金

- アプリの中から `stripe.refunds.create` を実行する（**B2C 用 Stripe のテストモードでのみ実装・テストする**）。
  - 金額は全額か一部。上限（＝決済額 − 返金済みの額）を、サーバー側で検証する。
  - `idempotencyKey = refund_<注文ID>_<連番>`（同じ操作が二重に送られても、二重に返金しない）。
  - 先に `b2c_refunds` を `requested` の状態で作り、Stripe の応答で `succeeded` / `failed` に更新する。最終的な額は Webhook と定期の照合（9.3）で確かめる。
  - 理由コード: `customer_request`（旅行者の都合）／`hotel_declined`・`reservation_not_found`・`no_response`・`delivery_failed`・`system_error`（BondEx 側の事情。全額が既定）。
- 返金の実行は、`b2c_finance` の権限と、直近の二段階認証を必須にする（7.1）。
- キャンセル料・返金の条件は**未確定**。規定が決まるまで、旅行者都合のキャンセルは運営が金額を入力する方式にし、既定値を持たせない。

## 9. 決済（Stripe）詳細（修正指示 1・3）

### 9.1 方式

- **Stripe Checkout**（`mode:"payment"`、旅行者が画面で支払う方式）を使う。カード情報は BondEx を通らない。
- **B2C 専用の Stripe アカウント**を使う（4.3 層1）。キーは `B2C_STRIPE_SECRET_KEY`・`B2C_STRIPE_WEBHOOK_SECRET`。B2B の `STRIPE_*` とは別の系統にする。
- Webhook のエンドポイントは、B2C 専用の `/api/b2c/stripe/webhook` を新しく作る。**既存の `/api/stripe/webhook` には手を入れない。**
- Checkout の作成時に、`metadata` と `payment_intent_data.metadata` の両方へ `kind:"b2c_order"`・`b2c_order_id`・`booking_id` を入れる（PaymentIntent や Charge のイベントからも、注文を特定できるようにする）。
- `expires_at`: 即時予約は30分、承認後の決済の案内は 5.3 の決済期限。
- 金額は、常にサーバーの料金ルールから算出する。

### 9.2 Webhook の受け方: 「イベントは合図、正は Stripe の最新状態」

Webhook のイベントは、**重複して届く・順番が入れ替わる・途中で処理が止まる・まったく届かない**ことがある前提で設計する。

1. **受信**: 署名を検証し、`b2c_stripe_events` に `event_id`（主キー）・種類・対象のオブジェクト ID・受信時刻を INSERT する（既にあれば何もしない）。
2. **すぐに 200 を返す**のは、INSERT に成功したときだけ。DB に書けなかったら 500 を返し、Stripe の再送に任せる。
3. **処理**: イベントの中身（`data.object`）は信用しない。対象の **Checkout セッション・PaymentIntent・Charge を Stripe の API から取り直し**、その最新の状態で注文を照合する（`reconcileOrder(orderId)`）。
   - 順番が入れ替わっても問題にならない（例: 「期限切れ」が「支払い完了」の後に届いても、取り直した最新の状態は「完了・支払い済み」なので、支払い済みとして扱う）。
   - 同じイベントが何度処理されても、結果は同じになる（照合は冪等）。
4. 処理の結果を `b2c_stripe_events.status`（`processed` / `failed` / `ignored`）・試行回数・最後のエラーに記録する。`failed` は、定期の照合（9.3）が拾い直す。

**`reconcileOrder` で行う照合**

| Stripe の最新状態 | 注文の状態 | 処理 |
|---|---|---|
| セッション完了・支払い済み、金額・通貨が一致 | `awaiting_payment` | `payment_status=paid`、`status=confirmed`、`fulfillment_status=pending` を**1つのトランザクションで**更新する（DB 関数）→ 手配処理（9.4）を呼ぶ |
| 同上 | 既に `paid` | 何もしない（重複） |
| 支払い済みだが、金額・通貨が一致しない | どれでも | 確定にせず `exception`。運営へ警告する |
| 支払い済みだが、注文が `expired` / `cancelled` / `rejected`（競合で起きうる） | 終わった注文 | `exception`。運営へ警告し、**全額返金の候補**として表示する（理由 `system_error`） |
| セッションが期限切れ・未払い | `awaiting_payment` | `expired` にする（即時予約の場合は、見積を解放する） |
| 返金がある | `paid` | `b2c_refunds` と照合し、`refunded_amount_yen`・`payment_status` を更新する |
| 係争がある | どれでも | `payment_status=disputed`。運営へ警告する（証拠の提出期限があるため） |

- 支払い完了の画面（`success_url`）でも、サーバーから同じ `reconcileOrder` を呼ぶ（Webhook が遅れていても、旅行者がすぐに結果を見られる）。

### 9.3 定期の照合（Webhook が届かない・途中で止まった場合の復旧）

**`/api/cron/b2c-reconcile`（新規・5分ごと）**

| 対象 | 処理 |
|---|---|
| `b2c_stripe_events.status='failed'`、または `received` のまま5分以上 | 再処理する（上限10回。超えたら運営へ警告し、手動の再処理キューへ） |
| `awaiting_payment` で、Checkout セッションの作成から35分以上経った注文 | Stripe からセッションを取り直して `reconcileOrder` |
| `paid` で `fulfillment_status` が `pending` / `failed` の注文 | 手配処理を再実行する（9.4） |
| 直近48時間に成功した B2C の PaymentIntent の一覧（Stripe の検索 API） | DB に `paid` として載っていない注文があれば `reconcileOrder`（**Webhook がまったく届かなかった場合の最後の網**） |

- 起動の仕組み: 既存の GitHub Actions は実行が間引かれることがあるため、**Supabase の pg_cron と pg_net から呼ぶ方式を推奨する**（本番 DB での拡張機能の有効化が必要＝承認事項）。それまでの間は GitHub Actions と、支払い完了の画面・Webhook の受信時に呼ぶ処理を併用する。
- 二重の起動は、既存の `lib/cron-lock.ts` で防ぐ。

### 9.4 手配処理（決済の成功と、`shipments` の作成を分ける）

`fulfillOrder(orderId)` は、支払い済みの注文から既存の配送基盤の記録を作る。**何度呼んでも結果が同じになる**（冪等）。

1. 注文の `fulfillment_status` を `pending` から `in_progress` に条件付きで更新する（同時実行を防ぐロック。`in_progress` のまま10分経ったら、再び取れるようにする）。
2. B2C 専用の DB 関数 `b2c_apply_fulfillment` を呼び、**1つのトランザクションで**次を行う。
   - `shipments` を `(booking_id, leg_index)` で upsert する（`channel='b2c'`・`b2c_order_id`・`agency='BondEx Direct'`・`status='issued'`・`amount_yen`＝税抜の写し・ホテル・日付・個数・集荷時刻11時）
   - 予約ごとの受け入れ確認（3.5）の行を、集荷側・配送側の2件作る
   - `fulfillment_status=done` にする
3. トランザクションの後に、旅行者への予約確定のメール（バウチャー付き）を送る。送信の結果は `b2c_notifications_log` に記録する（送れなければ、定期の照合で再送する）。

- **`status='issued'` で作る理由**: `requested` で作ると、運営の発行キューに載ってしまい、発行操作で金額が上書きされる（1.3 の P09・P10）。B2C は決済の時点で金額が確定し、送り状も発行しない（2026-09-24 以降の運用）ため、`issued`（送り状なし）が実態に合う。
- 失敗したとき（DB の一時的な障害・制約違反など）: `fulfillment_status=failed`・試行回数・エラーを記録する。定期の照合が、間隔を空けながら再実行する（1分 → 5分 → 15分 → 1時間）。
- 支払いから **15分以上、手配が終わっていない**場合は、運営へ警告し、B2C 管理画面の「支払い済み・手配未完了」の一覧に出す。担当者が原因を確かめて「再実行」を押せる（監査ログに記録）。
- 手配が成り立たないことが分かった場合（例: 決済の後に施設が対象外になった）は、`exception` にして、全額返金の候補として出す（理由 `system_error`）。

### 9.5 二重決済・二重予約の防止のまとめ

| リスク | 対策 |
|---|---|
| 予約ボタンの二重押し | ブラウザで作る `request_key`（UUID）を `b2c_orders.request_key UNIQUE` で受ける。同じキーなら既存の注文を返す |
| 同じ注文で Checkout を2回作る | `b2c_payments` に、有効なセッションは1注文に1件という一意の制約を置く。有効なものがあれば再利用し、作成時は `idempotencyKey = checkout_<注文ID>_<試行番号>` を付ける |
| 決済の後に予約が二重にできる | `shipments` の `(booking_id, leg_index)` UNIQUE（既存）と、状態の条件付き更新 |
| Webhook の重複・順番の入れ替わり | `b2c_stripe_events` の主キー＋最新状態の取り直しによる照合（9.2） |
| Webhook の途中停止・不着 | 定期の照合（9.3） |
| 決済は成功したが手配に失敗 | 手配処理の分離と再処理（9.4） |
| 金額の改ざん | サーバーで算出した金額だけを使い、Stripe の最新状態の金額と照合する |
| 本番のキーの誤用 | `B2C_STRIPE_SECRET_KEY` が `sk_test_` 以外ならサーバーの起動時に拒否する（本番のキーを許可するのは、承認を得てからのコード変更で行う） |

### 9.6 安全スイッチ

| 環境変数 | 既定 | 意味 |
|---|---|---|
| `B2C_ENABLED` | `false` | B2C のページ・API 全体の公開。false の間は 404 |
| `B2C_PAID_BOOKING_ENABLED` | `false` | 有料予約の受付。**正式価格の承認まで、本番は false 固定** |
| `B2C_STRIPE_SECRET_KEY` | なし | B2C 用。`sk_test_` 以外は起動時に拒否 |
| `B2C_STRIPE_WEBHOOK_SECRET` | なし | B2C 用 Webhook の署名シークレット |

## 10. 予約後の旅行者体験

### 10.1 確認ページ（専用リンク）

- URL: `/b2c/r/<access_token>`（32バイトの乱数。DB には **SHA-256 のハッシュだけ**を保存する）。

### 10.2 バウチャー

| 手配処理 | `shipments` の作成の失敗 → 再処理で復旧／同時に2回呼んでも1件だけ／15分を超えたら警告／手配が成り立たない場合に返金候補 |
| 返金 | 全額・一部、上限超過の拒否、二重押し、理由コード、Webhook・定期の照合との一致 |
| 認証・監査 | 共有ログインだけでは B2C の管理 API が 401／二段階認証を済ませていないと 403／権限の無い返金が 403／無効化した担当者が即座に操作できない／代理店ユーザーが担当者になれない／監査ログが UPDATE・DELETE できない |
| 配送完了 | 追跡による確定、手動の確定で担当者・根拠が必須、取り消し、1区間1件 |
| 言語 | 全画面・エラー・メールの ja/en の切り替え、訳し漏れのキーが無いこと |
| バウチャー | B2C 行の生成、日本語の旅行者向けの面、B2B の既存予約の出力が変わらないこと |
| セキュリティ | アクセストークンの総当たりへの耐性、リンクの再送が予約の有無の確認に使えない、運営の API が未認証で 401、本番のキーでの起動の拒否 |
| アクセシビリティ | axe で重大な違反がゼロ、キーボードで操作できる、フォームのラベル・エラーが読み上げられる |
| モバイル | 幅375pxで全 STEP を完了できる、横スクロールが出ない |
| B2B の回帰 | 代理店の予約の作成、カード代理店の集荷時の課金（テストモード）、月次請求の集計、ホテル連絡の督促、実績レポート、バウチャーの再生成、既存の Webhook（返金・係争・決済失敗・追加の決済） |

### 18.2 DB の変更の影響

- 11.1 のとおり、追加だけ（列2つ・索引1つ・トリガー1つ・代理店1行）。既存の行は `channel='b2b'`・`b2c_order_id=NULL` になり、トリガーは B2B の行では何もしない。

## 20. 残るリスク

| No. | リスク | 対策・残る度合い |
|---|---|---|
| 01 | 法的な整理が「取次業」と合わず、公開ができない、または形を変える必要が出る | 弁護士の確認を公開の前提にする。設計の変更が必要になる可能性がある（決済の主体・規約） |
| 02 | 未確認のホテルの審査と、予約ごとの受け入れ確認が手作業のため、件数が増えると運営が追いつかない | 受付の一時停止のスイッチ、包括受け入れの施設を増やす。処理の上限は事業側で決める |
| 03 | 決済の後にホテルに断られ、全額返金になる（売上が立たず、Stripe の手数料が戻らない可能性がある） | 包括受け入れの施設を優先して表示する。断りの頻度を施設ごとに記録し、再審査につなげる |
| 04 | 配達予定日は目安のため、遅れたときに旅行者の不満・問い合わせが出る | 規約・画面で「目安」と明記し、日数の最長で予約の可否を判定する。補償は未決 |
| 05 | B2B の Webhook の 500 問題（1.3 の P07）は、**B2C 専用の Stripe アカウントを作らない場合**に B2B の改修が必要になる | アカウントの分離を推奨。分離しない場合は、B2B の Webhook の回帰テストを必須にする |
| 06 | 既存のファイルに共通ガードを入れる変更（18.1）で、B2B の不具合を起こす | B2B の回帰テストを、B2C の機能より先に用意する（4-2） |
| 07 | 定期の照合を GitHub Actions で動かす間は、実行の間引きで復旧が遅れる | pg_cron への移行を推奨（承認事項）。支払い完了の画面・Webhook の受信時の照合を併用する |
| 08 | 共有ログインの運営ダッシュボードから、B2C 以外の経路で B2C の行に影響する操作が見つかる | 層3（DB トリガー）で、金額・課金の列は必ず止まる。他の列は、B2B の回帰テストの中で洗い出す |
| 09 | 旅行者の個人情報（連絡先・宿泊先と日程＝所在が分かる情報）が漏れる | RLS で全拒否、トークン、追跡ページの匿名化、保存期間の規定（例: 配送完了から2年で匿名化）。期間の決定は事業側 |
| 10 | 競合 UX を実測していないため、画面の設計を見直す可能性がある | 4-4 の前に実測する |
| 11 | 本番 Supabase を参照するローカル開発の運用のまま、B2C の書き込みを誤って本番で動かす | 本番の接続を拒否するガード（15.1）と、ローカル Supabase の利用 |
