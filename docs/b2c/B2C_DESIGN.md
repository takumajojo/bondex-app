## 0. 確定方針（変更しない前提）

| 項目 | 内容 |
|---|---|
| 対象区間 | **ホテル → ホテルのみ**。空港・駅・民泊・個人宅は B2C 画面に出さない |
| 対象施設 | フロントデスクにスタッフが常駐し、荷物の預かり・受け渡しができるホテルのみ。**集荷先・配送先の両方**が条件を満たすこと |
| 拒否対象 | Airbnb／民泊／無人ホテル／フロントなし／スタッフ非常駐／預かり不可／個人宅。**例外対応なし**。予約リクエストも受け付けない |
| 予約方式 | ゲスト予約（アカウント登録なし）。予約後は安全な専用リンクで確認する |
| 言語 | 英語・日本語（多言語に広げられる構造） |
| 決済 | Stripe 事前決済。B2B の請求書払い・代理店カード課金とは分離する |
| 変更・キャンセル | 初期は **BondEx への問い合わせ方式**。旅行者による自動変更・自動返金はなし |
| 価格 | 4,980円（B2B の税抜単価）は**暫定の参考値**。B2C の確定価格に流用しない。正式価格が確定するまで、本番で有料予約を受け付けない |
| **アフィリエイト（v1.3 で変更）** | **AJ 限定で実装する。** 範囲は、AJ 専用の紹介リンク、30日間の紹介の帰属、Web 申込への紹介元の保存、配送完了の個数に基づく成果台帳、取消・返金時の調整、AJ 専用の成果確認画面、月次の精算明細。**紹介料の振込は当初は手動。** 他の媒体の一般募集・自由登録は含めない |
| **WhatsApp（v1.3 で追加）** | **Web の受付完了後の連絡に限定する。** 用途は、追跡・質問対応、実際の集荷日と預け入れの期限に基づく当日の案内、対象の予約に影響する確定した遅延の通知。チャットでの新規受付・予約前の相談は含めない |
| **公開追跡・自動応答（v1.3 で追加）** | **B2C の予約は、予約番号だけでホテル名・日付を取得できる公開追跡と WhatsApp の自動応答から除外する。** 追跡・質問対応は、本人のアクセス権を確認できる方法（確認ページの専用リンク・連携済みの WhatsApp）につなぐ |
| **AJ の画面（v1.3 で追加）** | 顧客の氏名・連絡先・ホテル・旅程を表示しない |
| 禁止 | 既存 B2B への影響、既存 DB の破壊的変更、本番 Stripe の変更、実課金、別作業の未コミット変更への接触 |

## 1. PHASE 1 調査結果（既存システムの事実）

根拠は `origin/main`（ca27290）のファイルと、本番の読み取り結果（2026-10-28）。

### 1.1 データ構造

- **予約・料金・課金・追跡・監査は、すべて `shipments` 1テーブルに載っている（1区間＝1行）。** bookings / hotels / payments の独立したテーブルは無い（`sql/001_shipments.sql`、`sql/003` の `(booking_id, leg_index)` UNIQUE）。
- **代理店は `shipments.agency text NOT NULL`（代理店名の文字列）で識別している。** `agency_id` も FK も無い。
- `shipments.status` の値は CHECK 制約で固定（`sql/011:24-25`）: `requested, pending, issued, picked_up, in_transit, delivered, failed, cancelled`。
- `agencies.payment_method` は `'invoice' | 'card'`（`sql/010:15`）。`agencies.billing_exempt=true` は、課金・月次請求・請求締切・自動送付・追加清算のすべてで除外される。
- **ホテルマスタは無い。** 各行に Google `place_id`・ホテル名・都道府県・市区を持つだけ。
- B2B では民泊・個人宅も受け付けている（`lib/residence.ts`、`sql/016`）。**「フロントあり・有人」の概念はコードに無い。**
- `sql/053` で `delivered_notified_at`・`tracking_limit_reached` が追加された。

### 1.2 予約・料金・日付

- B2B 予約 API は `status:"requested"`, `amount_yen:0` で保存し、運営の発行操作で「個数 × 代理店単価」として金額を確定する（`app/api/shipandco/create/route.ts:979`）。
- 料金は `lib/pricing.ts:10` の `PRICING.regularPrice = 4980`（**税抜**・1個あたり）。参考値の税込は **5,478円**。
- 配達日のルール（`lib/carrier.ts` の `minOffsetDays:1 / maxOffsetDays:7`）は送り状の発行時にしか検証されない。**地域ごとの所要日数のロジックは無い。** 営業資料は「目安」の表現（「保証」「必ず」は使わない）。
- 受付締切の表記が媒体ごとに食い違っている（16時・17時・18時）。既存の未決事項。
- 祝日は 2026〜2028年分を直接持つ（`lib/business-days.ts`）。

### 1.3 既存の課金・金額・請求・公開情報の経路（全件）

B2C の行（以下「B2C 行」）が入り込んだ場合の危険。**v1.3 で P15〜P20 を追加した。**

| No. | 経路 | 何をするか | B2C 行が入り込んだ場合の危険 |
|---|---|---|---|
| P01 | `lib/charge.ts` `chargeShipmentIfDue` | 集荷完了で off_session の PaymentIntent を作る | 二重課金・課金エラーの通知 |
| P02 | 　呼び出し元 `PATCH /api/shipments` | 運営の手動ステータス変更 | 同上 |
| P03 | 　呼び出し元 `app/api/cron/sync-tracking`（`:465`） | 追跡の同期時 | 同上（追跡の再開で一斉に走る） |
| P04 | 　呼び出し元 `lib/tracking/reconcile.ts`（`:193`） | 追跡の即時照会 | 同上 |
| P05 | 　呼び出し元 `app/api/operator/charge-retry` | 「課金を再試行」と、#85 で追加された「この区間を課金…（集荷メールなし）」 | 同上 |
| P06 | `app/api/shipments/addition-settle` | 「追加」区間の Checkout を作る | 二重決済 |
| P07 | `app/api/stripe/webhook` の `handleRefund` / `handleDispute` / `handlePaymentFailed` | PaymentIntent から区間を逆引きし、**見つからなければ 500** | 同じ Stripe アカウントで B2C の返金・係争・決済失敗が起きると、500 を返し続ける。受け口が無効化されると、B2B の返金・係争の検知も止まる |
| P08 | 同 `handleAdditionCheckout` | `kind==="addition"` だけ処理 | 危険なし（素通り） |
| P09 | `app/api/shipandco/create` | 発行時に `amount_yen = 個数 × 代理店単価` で上書きし、`issued` にする | **B2C の確定額が 4,980円（税抜）× 個数に上書きされる** |
| P10 | `app/api/voucher/generate`・`/operator` の「この依頼を発行」 | `requested` の行を発行キューに出す | P09 を誘発する |
| P11 | `app/api/operator/adjust-count` | 個数と金額を変え、代理店へ返金/追加請求の案内を送る | 金額の書き換え、代理店宛ての誤った案内 |
| P12 | `lib/invoice-build.tsx`、月次請求の cron 3本 | 代理店名で集計して請求書を作る | 請求への混入（`billing_exempt` の代理店なら対象外） |
| P13 | `app/api/agency/invoice` | 課金済みの区間の領収書を代理店に出す | 代理店ユーザーがいなければ到達しない |
| P14 | ステータスの通知（`sendAgencyStatusEmail`・プッシュ）、#88 の配達完了メール | 代理店の連絡先へ送る | 旅行者ではなく代理店宛てに送られる |
| **P15** | `app/api/agency/shipment/[id]` → `lib/amount-recalc.ts` `amountForNewCount`（#78） | 代理店のセルフ変更で、金額を「新個数 × 代理店単価」に更新 | 代理店の認証で自社の行に限られるため、通常は届かない |
| **P16** | `app/api/operator/change-requests/[id]:103` → `amountForNewCount` | 変更リクエストの承認で金額を更新 | **B2C の確定額の上書き** |
| **P17** | `app/api/operator/shipment/[id]/correct:119` → `amountForNewCount` | 運営の訂正で金額を更新 | **B2C の確定額の上書き** |
| **P18** | `app/api/track/[bookingId]`・`/track/[bookingId]` | 予約番号だけで、区間のホテル名・日付・状態・追跡番号・姓の頭文字を返す | **旅行者の所在（ホテルと日付）が、予約番号を知る誰にでも分かる** |
| **P19** | `app/api/whatsapp/webhook` → `lib/whatsapp-tracking.ts` | 誰からのメッセージでも、予約番号か追跡番号があれば、ホテル名と状態を返す | 同上 |
| **P20** | バウチャーの追跡 QR（`/track/<予約番号>`） | 紙のバウチャーから公開追跡へ誘導する | P18 への入口になる |

- `getShipmentByPaymentIntentId`（`lib/shipments-db.ts`）は `maybeSingle` で検索する。1つの PaymentIntent が複数の行に載ると 500 になる。

### 1.4 ホテル連絡

- **自動送信は無い。** 運営が電話・メールで連絡し「連絡済み」を押す。期限は発送日の2営業日前。毎朝の督促 cron あり。
- 誰が連絡したか、ホテルが受け入れたかの記録は無い（memo の自由記述だけ）。
- 公式サイトから電話番号を拾う処理、初回ホテルの判定、紹介メール（運営がワンクリックで送信）がある。
- 既存の確定事項: 「ホテル宛ての紹介メールは社外宛てのため自動送信しない」。

### 1.5 佐川・追跡・配達完了・運営認証（v1.3 で更新）

- 2026-09-24 以降、BondEx は送り状を発行しない（`AUTO_ISSUE_ENABLED` の既定は OFF）。佐川への集荷依頼は運営が手動で行い記録する。
- **追跡（2026-10-28 時点）**:
  - コードは、Ship&co の追跡 API で配送状況を確かめ、配達完了を自動で検知して完了メールを1回送る（#88）。**Ship&co の上限は「追跡番号あたり15回」**で、照会の配分は `lib/tracking/poll-policy.ts`。上限に達した番号は、ダッシュボードの「追跡上限（手動確認）」に出る。
  - 停止のフラグは、コードの既定が「停止しない」、環境変数 `TRACKING_SYNC_PAUSED` で切り替える（`lib/tracking-pause.ts`）。**本番の環境変数の値は確認していない**（読み取りの方法が、秘密の値の取得を伴うため）。
  - **本番の定期実行は pg_cron と pg_net**（`sql/052`）。2026-10-28 の読み取りでは、**`sync-tracking-15min` と `sync-tracking-30min` の2本とも停止中（`active=false`）**、最後の実行は 2026-10-27 10:30 JST。GitHub Actions のワークフローは手動実行だけ。→ **今は、追跡の自動同期は止まっている。**
- 配達完了は、運営の手動ステータス変更か、追跡の自動検知で決まる。記録は `delivered_at`（と `delivered_notified_at`）だけで、**手動の場合の担当者・根拠は残らない。**
- **運営のログインは共有パスワードとパスキーで、個人を識別できない**（`lib/operator-session.ts`、`sql/031`）。

### 1.6 バウチャー・メール・WhatsApp・公開ページ・テスト

- バウチャーの生成は、代理店名と代理店の連絡先に依存する。旅行者向けの面に**日本語が無い**（`lib/guest-language.ts:9`）。バウチャーの送付はサーバー生成に一本化された（ca27290）。
- **旅行者宛てのメールは無い。** `shipments` に旅行者のメール・電話の列も無い。
- WhatsApp:
  - 受信: 署名を検証し（`verifyWhatsAppSignature`）、重複は `whatsapp_processed` で排除する。自動応答は P19 のとおり。
  - 送信: 24時間の枠内の自由文の返信（`sendWhatsAppText`）と、代理店宛ての承認済みテンプレート（`lib/agency-push.ts`）。
- 個人の消費者向けの規約・特定商取引法の表示・キャンセルポリシーは無い。
- テストフレームワークは無いが、偽の DB・メールで動く**自己検証スクリプト**がある（`scripts/test-amount`・`scripts/test-tracking`・`scripts/tracking-*`）。
- ローカル開発は本番 Supabase を参照する運用（読み取りのみ）。
- **AGENTS.md は存在しない。** 作業ルールは `CLAUDE.md` と `~/JOJO/state/bondex.md`。

## 2. 全体アーキテクチャ（ハイブリッド構成・承認済み）

```
[AJ の記事・バナー・メルマガ]
        │  /r/accessible-japan?placement=…   （紹介の到達を記録→同意に応じて30日の紹介IDを保存）
        ▼
[旅行者 ブラウザ]  /en/partners/accessible-japan  /en/book  /book(ja)
        │
        ▼
[/api/b2c/*]  公開API（Turnstile 非対話型＋レート制限＋各ルートで自前検証）
        │
        ├── b2c_orders / b2c_payments …… 決済状態の正本（紹介元と規則の版を申込時に固定）
        ├── b2c_facilities / b2c_routes / b2c_price_rules …… 施設・区間・料金の設定
        │
        │   決済が確定したら「手配処理」が作る（失敗しても再処理できる）
        ▼
[shipments]  既存。B2C行は channel='b2c'・agency='BondEx Direct'
        │    課金列は使わない（DBトリガーで禁止）。公開追跡・WhatsApp自動応答の対象外
        └── 既存の運営フロー（ホテル連絡督促・集荷依頼TODO・追跡・レポート）に表示として載る
        │
        ▼
[shipment_delivery_confirmations] 配送完了の確定（追跡 or 担当者＋根拠）
        │
        ▼
[commission_ledger] → [settlement_batches] → 手動振込 → [payouts]   ……AJ の成果と精算

[WhatsApp] 受付完了後だけ。確認ページから一時コードで連携 → 追跡・質問・当日案内・確定遅延
[B2C管理画面] /operator/b2c/* … 共有ログイン＋担当者個人のログイン（二段階認証）＋監査ログ
[AJ画面]      /partners/*      … AJ 担当者の個人ログイン（二段階認証）。集計と精算明細だけ
[Stripe]      構成は未決（既存アカウント共用＋Webhook分離が推奨案。9.7）
```

### 設計の核心（B2B を壊さない・個人情報を出さないための原則）

1. **決済状態の正本は `b2c_orders` と `b2c_payments` だけ。** `shipments` の課金列は B2C 行では使わない。
2. **未払い・未確認の予約は `shipments` に入れない。** 決済が確定した後に、手配処理が作る。
3. **B2C 行の識別は `shipments.channel='b2c'`** を正にし、`b2c_order_id`・代理店名 `BondEx Direct` を補助の目印にする。
4. **誤課金の防止は3層**（Stripe 上の分離・アプリの共通ガード・DB トリガー）。
5. **既存テーブルへの変更は追加だけ。**
6. **（v1.3）予約番号は認証に使わない。** B2C の詳細（ホテル・日付・氏名）は、専用リンクか連携済みの WhatsApp を通した本人にだけ出す。
7. **（v1.3）紹介の成果は、クリックではなく「入金済み × 配送完了の個数」から作る。** 紹介の仕組みに異常があっても、成果の確定と精算だけを止め、予約と配送は続ける。

## 3. 施設適格性と予約ごとの受け入れ確認

**次の2つを、別々の仕組みとして扱う。**

| | 施設の適格性 | 予約ごとの受け入れ確認 |
|---|---|---|
| 問い | このホテルは、そもそも B2C の対象施設か | このホテルは、この予約の荷物を、この日に預かれるか・受け取れるか |
| 単位 | 施設（`place_id`）ごと | 予約×集荷側／配送側ごと |
| 記録先 | `b2c_facilities`、`b2c_facility_reviews` | `b2c_hotel_acceptances` |
| いつ | 予約前（未確認なら予約リクエストの段階） | 予約確定の後〜集荷の前営業日まで |
| 断られた場合 | 施設を対象外にする | その予約をキャンセルし、全額返金する（3.6） |

### 3.1 施設の状態

| 状態 | 意味 | 予約画面での扱い |
|---|---|---|
| `verified`（確認済み） | 運営が 3.3 の基準をすべて確認した | 即時予約・決済できる |
| `unverified`（未確認） | マスタ未登録、または確認期限切れ | **決済前の予約リクエスト**として受け付ける |
| `rejected`（対象外） | 運営が審査し、基準を満たさないと判断した | **予約もリクエストも不可** |

- 「確認済み」「対象外」にできるのは、**運営の審査だけ**。自動では決めない。
- 確認済みの有効期限は既定12か月。
- **民泊・無人施設が通らない根拠は、「確認済みの施設でなければ決済できない」という構造にある。**

### 3.2 自動の事前ふるい分け

**自動で選べなくするのは、次の2つだけ（キーワードは使わない）。**

| 条件 | 扱い |
|---|---|
| 運営が対象外と登録した施設（`place_id` が一致） | 検索結果に「BondEx の配送対象外の施設です」と表示し、選択不可 |
| 宿泊施設ではない場所（Places で `lodging` の種別を持たない場所） | 検索結果に出さない |

- 疑わしい施設（名称に `apartment`・`condo`・`villa`・`民泊`・`Airbnb`・`ゲストハウス` など、住所に部屋番号、貸別荘系の種別、口コミが極端に少ない など）は、**拒否せず「要確認」の目印を付けて審査の優先度を上げる。** 目印の辞書（`b2c_review_signals`）は運営が修正できる。
- 旅行者の画面には、目印の有無を出さない。

### 3.3 施設の審査（verified にする唯一の経路）

| No. | 基準 | 確認方法 |
|---|---|---|
| 01 | 旅館業法の許可を受けたホテル・旅館である（住宅宿泊事業法の届出住宅＝民泊、特区民泊ではない） | 公式サイト・自治体の公表情報。根拠の URL を記録 |
| 02 | フロントにスタッフが常駐している（集荷の時間帯 9〜18時と配達の時間帯） | **公式の電話番号へ電話して確認**（公式サイトから取る。Google の電話データは使わない） |
| 03 | 宿泊客の荷物を、チェックアウト後・チェックイン前に預かれる | 同じ電話で確認 |
| 04 | 佐川急便の集荷担当に荷物を引き渡せる（集荷先として） | 同上 |
| 05 | 宅配便で届いた宿泊客の荷物を受け取り、到着まで保管できる（配送先として） | 同上 |
| 06 | BondEx からの事前連絡の窓口がある（メールの可否・担当部署） | 同上 |
| 07 | 個別の確認が必要か、事前の連絡だけで包括的に受け入れられるか | 同上。包括的なら `standing_acceptance=true` |

- 集荷先の可否（04）と配送先の可否（05）は別々に記録する。
- 審査の記録には、**担当者（個人ログイン）・日時・方法・応対者・各基準の回答・根拠 URL・メモ**を残す（追記のみ）。
- B2B で配達完了の実績があるホテルは、審査候補として優先表示する。**実績だけでは verified にしない。**
- 対象外の理由は定型から選ぶ。ホテルからの申し出で再審査できる（履歴は残す）。

### 3.4 予約者側の確認（安全網）

STEP 3 で次に同意しないと進めない。

- 英語:
  > Hotel-to-hotel delivery only. Both hotels must have a staffed front desk that can accept and hand over luggage. Airbnb, vacation rentals, and unmanned accommodations are not supported.
  > - [ ] I confirm that both are hotels with a staffed front desk, and that I have a reservation at each hotel under the name below.
- 日本語:
  > ホテル間の配送のみ承ります。集荷先・配送先ともに、スタッフが常駐し、荷物の預かりと受け渡しができるフロントのあるホテルに限ります。Airbnb・民泊・無人の宿泊施設はご利用いただけません。
  > - [ ] 両方とも、スタッフが常駐するフロントのあるホテルであり、下記の予約名で宿泊予約があることを確認しました。
- 両ホテルの**予約名**と、**チェックイン日・チェックアウト日**を必須にする。

### 3.5 予約ごとの受け入れ確認

**状態（`b2c_hotel_acceptances.status`）**: `pending`（未連絡）／`requested`（回答待ち）／`accepted`／`accepted_standing`（包括受け入れ・事前連絡を送れば受け入れとみなす）／`reservation_not_found`／`declined`／`no_response`

**期限（BondEx の営業日・営業時間を基準に数える。3.7）**

- 受け入れ確認の期限: 両側とも、**集荷日の前営業日の 15:00 JST** まで。
- 予約の受付締切（6章の区間ごとの締切と比べて早い方）:

| 両ホテルの施設 | 受付締切 |
|---|---|
| 両方とも包括受け入れ | 集荷日の前営業日の 12:00 |
| それ以外 | 集荷日の**2営業日前**の 12:00 |

**連絡の内容（日本語のテンプレート）**

| 集荷先ホテル向け | 配送先ホテル向け |
|---|---|
| 予約番号、予約名、チェックアウト日、個数 | 予約番号、予約名、チェックイン日・チェックアウト日、個数 |
| 集荷日（佐川急便が伝票を持参） | 配達予定日（目安） |
| チェックアウト時に預かり、佐川急便へ渡すお願い | 受け取り、到着まで保管して渡すお願い（チェックイン前着なら明記） |
| 宿泊予約の照合と、受け入れ可否の回答のお願い | 同左 |

- 送信は**運営が内容を確認してから送る**（社外宛てのため自動では送らない）。回答の記録は B2C 管理画面で個人ログインで行い、既存の `pickup_hotel_notified_at` / `guest_hotel_notified_at` も更新する。
- **受け入れ確認が済むまで、旅行者の画面・メールに「両ホテル確認済み」と表示しない。**

### 3.6 決済後にホテルが受け入れを断った場合

| 事象 | BondEx の対応 | 返金 | 旅行者への通知 |
|---|---|---|---|
| 集荷先が `declined` | 代わりの手段は無いため、キャンセル | **全額**（BondEx 側の事情。キャンセル料なし） | 事実・キャンセル・返金額と時期・問い合わせ先（ja/en） |
| 配送先が `declined` | 同じ日程で受け取れる別の確認済みホテルがあれば変更を提案。期限までに決まらなければキャンセル | 変更できなければ**全額** | 同上。返信期限を明記 |
| `reservation_not_found` | 予約名・日付の確認を依頼し、訂正後に再照会 | 解消しなければ**全額**（入力ミスで手数料を取るかは未決） | 確認依頼（返信期限つき）→ 結果 |
| `no_response` | 電話で再連絡。確認できなければキャンセル | **全額** | 3.7 のとおり |
| 集荷当日にフロントで断られた | 例外として運営がホテル・佐川と調整 | 集荷できなければ**全額** | 3.7 のとおり |

- 返金は運営が管理画面から実行する（8.3）。BondEx 側の事情による返金は、全額を既定値にし、旅行者都合と区別して記録する。
- **AJ の成果への影響**: 全額返金・キャンセルになった予約は成果の対象外（12.5）。
- 施設への影響: 方針として受けられないなら `rejected`。一時的な理由なら `verified` のまま。90日以内に2回断られたら再審査の目印。

### 3.7 受け入れ拒否・例外時の対応期限

#### 3.7.1 考え方

- 期限は、**BondEx の営業時間**と、**集荷までの残り時間**で決める（「一律2時間以内」は採らない）。
- 営業時間外に人の対応を約束しない代わりに、**旅行者が荷物を預けて困ることだけは、システムの自動通知で防ぐ。** 自動通知は状況と荷物の扱いを伝えるだけで、キャンセルの確定と返金は担当者が営業時間内に行う。
- 受付締切と受け入れ確認の期限により、ホテルの拒否・予約の不一致は、通常は集荷の前の営業日のうちに分かる。

#### 3.7.2 営業時間

- `b2c_business_calendar` で営業日・営業時間を持つ（佐川の集荷・配達の日とは別に管理する）。
- 初期値の案: 平日 9:00〜18:00 JST（土日祝・年末年始は休み）。**実際の値は未決**（15章 U02）。仕組みは値に依存しないように作る。

#### 3.7.3 対応期限

| No. | 事象 | 旅行者への最初の連絡 | 結果の連絡・確定 | 返金の実行 |
|---|---|---|---|---|
| 01 | ホテルの拒否・不一致が営業時間内に分かった | 営業時間で3時間以内（集荷の前営業日なら 17:00 まで） | 拒否はキャンセル・返金の案内。不一致・変更の提案は「24時間」と「前営業日 15:00」の早い方を返信期限にする | キャンセル確定から2営業日以内 |
| 02 | ホテルの回答が営業時間外に届いた | 次の営業日の 11:00 まで | 同上 | 同上 |
| 03 | 前営業日 15:00 に確認が取れていない | **15:00 に自動通知**（確認中・18:00 までに結果） | 17:30 までに担当者が連絡。取れなければ **18:00 に自動通知**（明日の集荷は手配できない・荷物は手元に・次の営業日に手続き） | 次の営業日に確定し、そこから2営業日以内 |
| 04 | 集荷当日にフロントで断られた（営業時間内） | 1時間以内に担当者が返答 | 同日中に続行か中止かを連絡 | 集荷できなければ確定から2営業日以内 |
| 05 | 同上（営業時間外） | **すぐに自動返信**（荷物は手元に・次の営業日 11:00 までに連絡） | 次の営業日 11:00 まで | 同上 |
| 06 | 配送先で受け取れなかった・配達できなかった | 営業時間内なら3時間以内、時間外なら次の営業日 11:00 まで | 再配達・保管の調整を1営業日以内に連絡 | 補償・返金は未決 |

- 期限の1時間前に運営へ警告する。自動通知の文面は ja/en で用意し、送信の記録を残す。
- No.03 の 18:00 の通知を送った注文を `exception` にし、集荷依頼の TODO から外す処理は、**システムによる安全のための停止**であり、**採用は未決**（15章 U03）。仕組みは機能フラグ `B2C_SAFETY_STOP_ENABLED`（既定 false）の裏に作る。
- 自動通知の経路は、WhatsApp の連携と同意があれば WhatsApp、無ければメール（11章）。**当日の預け入れ案内（11.5）と同時に送らない**（送信待ちの列で無効化する）。

## 4. 決済状態の一元管理と誤課金の防止

### 4.1 正本は `b2c_orders` / `b2c_payments`

- 注文の支払い状態 `b2c_orders.payment_status`: `unpaid` / `processing` / `paid` / `partially_refunded` / `refunded` / `disputed`。
- 決済の試行ごとの記録 `b2c_payments`: Checkout セッション ID・PaymentIntent ID・**Stripe アカウントの識別子**・金額・通貨・状態・最後に Stripe から取得した時刻。
- `shipments` の B2C 行では、課金列（`charged_at`・`stripe_payment_intent_id`・`charge_amount_yen`・`charge_error`・`refunded_at`・`refund_amount_yen`・`disputed_at`・`payment_failed_at`・`is_addition`・`stripe_checkout_*`）を**一切使わない。**
- `shipments.amount_yen` には、レポートで B2B と同じ単位で集計できるよう、**税抜の確定額の写し**を入れる。書き込めるのは B2C 専用の DB 関数だけ。

### 4.2 `channel` 列: 採用

- `shipments.channel text NOT NULL DEFAULT 'b2b' CHECK (channel IN ('b2b','b2c'))`。既存行は `'b2b'`。PostgreSQL 11 以降では、既定値付きの列追加は表の書き換えを伴わない。
- 整合の制約: `CHECK ((channel = 'b2c') = (b2c_order_id IS NOT NULL))`。

### 4.3 3層の防御

**層1: Stripe 上の分離**（構成は未決。9.7）

- B2C のキーは、B2B の `STRIPE_SECRET_KEY` とは別の `B2C_STRIPE_SECRET_KEY` で持つ（共用案では同じアカウントの制限付きキー。権限は 9.8）。
- B2C の決済には必ず `metadata.kind="b2c_order"` を付ける（Checkout セッションと PaymentIntent の両方）。
- B2C の Webhook は専用の受け口 `/api/b2c/stripe/webhook` で受ける。
- B2B の課金処理（P01〜P05）は、代理店の保存済みカードにしか課金しない。B2C の旅行者は Customer として保存しないため、B2C の顧客に課金されることは無い。それでも層2・層3で重ねて止める。

**層2: アプリの共通ガード（`lib/channel-guard.ts`・新規）**

```ts
// 判定は fail-closed: どれか1つでも B2C の目印があれば B2C とみなす
isB2CShipment(row) = row.channel === 'b2c' || row.b2c_order_id != null || row.agency === B2C_AGENCY_NAME
guardB2BOnly(row, operation): { ok: true } | { ok: false, reason: 'b2c_shipment' }
```

| 経路 | ガードの入れ方 | B2B の挙動 |
|---|---|---|
| P01〜P05 | `chargeShipmentIfDue` の最初の行（安全ゲートより前）。#85 の手動課金も同じ入口。ダッシュボードの B2C 行には課金ボタンを出さない | 変わらない |
| P06 | `addition-settle` の入口 → 400 | 変わらない |
| P07 | Stripe 構成の決定後に対応（9.7）。共用案なら「区間が見つからない」分岐の中だけに判定を追加 | B2B の決済のイベントは同じ処理 |
| P08 | 変更不要 | — |
| P09・P10 | `shipandco/create` と `voucher/generate` の入口 → 409。発行キュー・一覧で B2C 行に発行ボタンを出さない | 変わらない |
| P11 | `adjust-count` の入口 → 409 | 変わらない |
| P12 | `invoice-build` の集計に `.eq('channel','b2b')` を追加 | 既存の行はすべて `'b2b'` のため結果は同じ |
| P13 | 変更なし（B2C 用の代理店にログインユーザーを作らない） | — |
| P14 | 通知の送信関数の入口で、B2C 行なら代理店宛てに送らず、旅行者向けの通知（10.3・11章）に振り分ける。#88 の配達完了メールも同じ | 変わらない |
| **P15〜P17** | **`amountForNewCount` の冒頭**で `guardB2BOnly`（例外にする）。加えて P16・P17 のルートの入口でも 409 | 変わらない |
| **P18** | 公開追跡の API で `channel='b2c'` の行を返さない（10.2） | B2B の応答は同じ |
| **P19** | WhatsApp の自動応答の検索で `channel='b2c'` の行を除外する（11.4） | B2B の応答は同じ |
| **P20** | B2C のバウチャーには公開追跡の QR を載せない（10.4） | B2B のバウチャーは同じ |
| 運営による手動の作成 | `/operator` の作成・`saveShipment` で、B2B 経路から `BondEx Direct`・`channel='b2c'` を指定することを禁止 | 変わらない |
| `PATCH /api/shipments` | B2C 行は 409「B2C 管理画面から操作してください」 | 変わらない |

- ガードが B2C 行を止めたときは運営へ警告する（起きないはずの事象の検知）。

**層3: DB トリガー**

- `shipments` に `BEFORE INSERT OR UPDATE` のトリガーを1つ追加する。
  - `channel='b2c'` の行で、課金列（`charged_at`・`stripe_payment_intent_id`・`charge_amount_yen`・`stripe_checkout_session_id`・`stripe_checkout_url`・`is_addition=true`）への書き込みはエラーにする。
  - `channel='b2c'` の行の `amount_yen`・`suitcase_count` の変更は、B2C 専用の DB 関数（`b2c_apply_fulfillment`・`b2c_change_count`）の中からだけ許可する（関数の中で `set_config('bondex.b2c_writer','on', true)` を立てる）。P15〜P17 のアプリの不具合があっても、ここで止まる。
  - `channel` 自体の書き換えは禁止。
  - B2B 行では何もせず通過する。

## 5. 予約フロー

### 5.1 画面フロー（スマートフォン優先・WCAG 2.2 AA を受け入れ目標）

| STEP | 画面 | 入力 | サーバーの処理 |
|---|---|---|---|
| 1 | 区間と日程 | 集荷地域・配送先地域・集荷日・個数（1〜5） | 対応区間か、受付可能かを判定し、配達予定日（目安）を算出 |
| 2 | 料金と配送予定日 | なし | 税込総額を算出し、見積を発行（15分有効） |
| 3 | ホテル | 両ホテルを検索して選択、予約名と日付、同意のチェック | 施設の状態を判定し、「即時予約」か「予約リクエスト」かを明示 |
| 4 | お客様情報 | **申込者**（氏名・メール・電話〔推奨〕・言語）、**旅行者**（申込者と違う場合の氏名・関係）、**連絡担当者**（どちらか）、本人の承諾（同行者の代理入力の場合） | 形式の検証 |
| 5a | 確認して決済（両ホテルが verified） | 規約・キャンセル規定への同意 | **料金・日程・施設の状態をサーバーで再検証** → Stripe Checkout へ |
| 5b | 確認してリクエストを送信（どちらかが unverified） | 規約への同意 | リクエストとして保存。決済はしない |
| 6 | 完了 | — | 5a: 予約確定のメールとバウチャー（手配処理の後）／5b: 受付のメール。WhatsApp 連携の案内（任意・11章） |

- 集荷時刻は既定 11時。案内は「集荷日 ○月○日の ○時までに、フロントへお預けください」と、**実際の集荷日と預け入れの期限**で示す（チェックアウト日と一致するとは限らない）。
- 配達予定日はシステムが算出し、旅行者には選ばせない。時間帯の指定は初期は提供しない。
- 初期は **1予約＝1区間**。
- **障害の有無・診断名・証明書は入力させない。** 支援の希望は、「テキストで連絡してほしい」「同行者を連絡担当にしたい」などの具体的な選択肢で最小限だけ取る。
- 決済前に表示する: 税込総額、荷物のサイズ・重量の上限、受付期限、集荷日、配達予定日（目安）、対象施設、キャンセル・返金、補償の範囲、連絡先、預けられない物（薬・パスポート・貴重品・すぐ使う物は手元に。**車いす・電動車いす・バッテリー・医療機器を通常の配送で扱えるとは約束しない**）。
- **紹介元**: 紹介の帰属（12.3）の対象がある場合は、STEP 5 の確認画面に「紹介元: Accessible Japan」と表示する。申込の作成時にサーバーが紹介元を決め、注文に固定する（ブラウザから送られた紹介元・金額は信用しない）。
- アクセシビリティ: キーボードだけで操作できる、読み上げの順、ラベル、分かるエラー表示と復旧の方法、フォーカスの可視化、コントラスト、拡大・リフロー、**主要なボタンは 44×44 CSS px 以上**、**日付は文字でも入力できる**、見積の有効期限が切れそうなときの延長・再開、パスワードマネージャーや貼り付けを妨げない。**Turnstile は操作の要らない非対話型だけを使い、画像を選ばせる CAPTCHA を出さない。**

### 5.2 注文の状態

注文の状態（`status`）・支払い（`payment_status`）・手配（`fulfillment_status`）は別々の列で管理する。紹介の成果（`commission_ledger`）も別に管理する（12章）。

```
status:
 pending_review ─承認→ awaiting_payment ─支払い確定→ confirmed ─集荷→ in_transit ─配送完了確定→ completed
      └─拒否→ rejected        └─期限切れ→ expired          │
                                                          ├→ cancelled
                                                          └→ exception
payment_status:     unpaid → processing → paid → (partially_refunded | refunded) / disputed
fulfillment_status: not_started → pending → done / failed（再処理あり）
```

| status | `shipments` 行 | 説明 |
|---|---|---|
| `pending_review` | なし | 未確認のホテルを含むリクエスト |
| `awaiting_payment` | なし | 決済待ち |
| `expired` / `rejected` | なし | 期限切れ／運営が拒否 |
| `confirmed` | 手配処理が作る | 支払い確定・手配中 |
| `in_transit` | 連動 | 集荷済み |
| `completed` | 連動 | 配送完了を確定した |
| `cancelled` | `cancelled` | 運営がキャンセル |
| `exception` | 連動 | 例外。運営が対応 |

- 遷移は条件付き更新で行い、逆戻りさせない。すべて `b2c_order_events` に記録する。

### 5.3 未確認のホテルを含む予約リクエスト

- 受け付ける条件: 集荷日が4営業日後以降。
- 運営の処理期限: 受付から1営業日以内に承認か拒否。
- 承認したとき: 料金・日程・施設を再検証し、決済の案内を送る（決済期限は「承認から48時間」と「受付締切」の早い方）。金額はリクエスト時の見積額で固定する（下がっていれば安い方）。
- 拒否したとき: 理由（定型）と代わりの案内を送る。
- **紹介の帰属は、リクエストを作った時点ではなく、正式申込（`b2c_orders` の作成）の時点で判定して固定する**（12.3）。リクエストも `b2c_orders` として作るので、リクエストの作成時点で固定する。
- 対象外の施設を含む場合は送信ボタンを出さない（サーバーでも 422）。

## 6. 配送日・受付条件

### 6.1 方針

- **配送日数は区間ごとに設定できる整数**（最短と最長）。
- **配達予定日は「目安」で、確約ではない。** 画面・メール・規約で「配達予定日（目安）」と表記する。「翌日着」「全国対応」などを全区間に一律で約束しない。
- 予約の可否は、目安の**最も遅い日**で判定する。

### 6.2 設定データ

**区間 `b2c_routes`**: `origin_area` / `dest_area`（`b2c_areas` の都道府県の集合。佐川の12地帯を初期値）、`enabled`、`transit_days_min` / `transit_days_max`、`pickup_weekdays`、`delivery_weekdays`、`cutoff_business_days_before` / `cutoff_time_jst`、`min_lead_days` / `max_days_ahead`、`effective_from` / `effective_to`。注文には使ったルールの ID と内容を保存する。

**日付の例外 `b2c_calendar`**: `date`、`area`（NULL なら全国）、`type`（`no_pickup` / `no_delivery` / `no_booking` / `peak`）、`extra_transit_days`、`note`。

- 祝日は `lib/business-days.ts` を使い、2029年以降の追加を毎年の運用作業にする。

### 6.3 判定の手順（予約 API・Checkout の作成時・リクエストの承認時に同じ関数で）

1. 区間が有効で、適用期間内。
2. 集荷日 ≥ 今日（JST）＋`min_lead_days`。**当日の集荷・当日の配送は不可。**
3. 集荷日が集荷の曜日に含まれ、`no_pickup`・`no_booking` に当たらない。
4. 受付締切（6.2 と 3.5 の早い方）より前。
5. 配達予定日（目安）= 最短: 集荷日 + `transit_days_min`／最長: 集荷日 + `transit_days_max` + 繁忙期の加算。配達できない日・曜日は次の配達可能日へずらす。
6. 集荷先: チェックイン日 ≤ 集荷日 ≤ チェックアウト日。配送先: 最長 ≤ チェックアウト日の前日。最短 < チェックイン日なら、保管可（3.3 の 05）の施設だけ受け付ける。
7. 受け入れ確認の期限（3.5）に間に合う。

- 表示: 「10月24日（目安）」または「10月24日〜25日（目安）」。
- 区間ごとの日数は、**運営が佐川の配達の目安で確認してから登録する**（推測では入れない）。
- 例外の日（台風による運休など）を追加したら、影響する予約を一覧に出し、確定した遅延の通知（11.6）につなげる。

| 方法 | 条件 | 記録 |
|---|---|---|
| **配送会社の追跡**（`carrier_tracking`） | 追跡で配達完了を検知した | 追跡番号、イベントの時刻、提供元、イベントの参照 |
| **担当者の手動確認**（`operator_manual`） | 追跡が使えない・遅れている・上限に達した | **担当者（個人ログイン）、確認した日時、根拠（必須）** |

- 手動の根拠: `hotel_phone`／`hotel_email`／`carrier_inquiry`／`customer_confirmed`／`other`（詳細の記述が必須）。
- **現状（1.5）**: 自動の追跡同期は止まっており、Ship&co には番号あたり15回の上限がある。**初期リリースでは手動の確定が主**になる前提で作る。
- 追跡の同期処理（`sync-tracking`・`reconcile`）が B2C 行の配達完了を検知したときは、代理店宛ての完了メールの代わりに `shipment_delivery_confirmations`（`source='carrier_tracking'`）を作り、旅行者への通知に振り分ける（P14）。

- 有効な確定は1区間に1件（`unique(shipment_id) where revoked_at is null`）。
- **「旅行者がフロントへ預けた」の自己申告（11.5）は、配送会社の集荷・配送完了とは別に記録し、成果の根拠にしない。**
- 確定・取り消しは、AJ の成果台帳に反映する（12.5）。

## 8. 変更・キャンセル・返金

### 8.1 方針

- 旅行者は、確認ページの問い合わせフォーム・メール・連携済みの WhatsApp で依頼する。**自動の変更・キャンセル・返金は実装しない**（WhatsApp の返信でも自動では処理しない）。

### 8.2 運営の処理画面（`/operator/b2c/orders/[id]`・個人ログイン必須）

| 操作 | 条件 | 処理 |
|---|---|---|
| ホテルの変更 | 集荷前・新ホテルが verified | 既存 RPC `apply_hotel_change`。受け入れ確認をやり直す |
| 日程の変更 | 集荷前・新日程が 6.3 を満たす | 日付を更新し、受け入れ確認をやり直す。**未送信の当日案内を無効化**（11.3） |
| 個数の変更 | 集荷前 | 増える: 追加分の決済リンク（B2C 専用）／減る: 一部返金。`b2c_change_count` で金額の写しも更新 |
| キャンセル | 集荷前（集荷後は返金の判断だけ） | `shipments` を `cancelled`、`b2c_orders` を `cancelled`。**未送信の通知を無効化** |
| 返金 | 支払い済み | 8.3 |

- すべての操作で担当者と理由を必須にし、監査ログに記録する。

### 8.3 返金

- アプリの中から `stripe.refunds.create` を実行する（**テストモードでのみ実装・テスト**）。
  - 全額か一部。上限（決済額 − 返金済み）をサーバーで検証する。
  - `idempotencyKey = refund_<注文ID>_<連番>`。
  - 先に `b2c_refunds` を `requested` で作り、Stripe の応答と Webhook・定期照合で確定する。
  - 理由コード: `customer_request`／`hotel_declined`・`reservation_not_found`・`no_response`・`delivery_failed`・`system_error`（BondEx 側の事情は全額が既定）。
  - **一部返金のときは、影響する個数（`affected_item_count`）を担当者が入力する**（紹介の成果の調整に使う。12.5）。単なるお詫びの値引き（`goodwill`）とサービスの取消を区別する。
- 実行には `b2c_finance` の権限と直近の二段階認証が必要。
- キャンセル料・返金の条件は未決。規定が決まるまで、旅行者都合の場合は担当者が金額を入力する。

## 9. 決済（Stripe）詳細

### 9.1 方式

- **Stripe Checkout**（`mode:"payment"`）。カード情報は BondEx を通らない。WhatsApp・メールでカード情報を受け取らない。
- Stripe のアカウント構成は未決（9.7）。**実装はアカウントに依存しない作りにする**（キーと受け口の署名秘密を B2C 専用の環境変数で持ち、`b2c_payments` に Stripe アカウントの識別子を保存する）。開発とテストはテストモードで行う。
- B2C の受け口 `/api/b2c/stripe/webhook` は、B2C 以外のイベントを受け取っても何もせず 200 を返す。
- `metadata` と `payment_intent_data.metadata` に `kind:"b2c_order"`・`b2c_order_id`・`booking_id` を入れる。**個人情報・紹介元は metadata に入れない。**
- `expires_at`: 即時予約は30分、承認後の決済の案内は決済期限。
- **完了画面に着いただけでは入金済みにしない**（必ず Stripe の最新状態で確かめる）。

### 9.2 Webhook の受け方: 「イベントは合図、正は Stripe の最新状態」

1. 署名を raw body で検証し、`b2c_stripe_events`（`event_id` が主キー）に INSERT する（既にあれば何もしない）。
2. INSERT に成功したら 200。DB に書けなければ 500（Stripe の再送に任せる）。
3. 処理では、対象の Checkout セッション・PaymentIntent・Charge を Stripe の API から取り直し、最新の状態で注文を照合する（`reconcileOrder(orderId)`）。順番の入れ替わり・重複は問題にならない。
4. 結果を `processed` / `failed` / `ignored` で記録する。`failed` は定期の照合が拾い直す。

| Stripe の最新状態 | 注文の状態 | 処理 |
|---|---|---|
| 完了・支払い済み、金額・通貨が一致 | `awaiting_payment` | `paid`・`confirmed`・`fulfillment_status=pending` を1トランザクションで → 手配処理 |
| 同上 | 既に `paid` | 何もしない |
| 支払い済みだが金額・通貨が不一致 | どれでも | `exception`・運営へ警告 |
| 支払い済みだが注文が終わっている | `expired` / `cancelled` / `rejected` | `exception`・全額返金の候補 |
| 期限切れ・未払い | `awaiting_payment` | `expired` |
| 返金あり | `paid` | `b2c_refunds` と照合して更新 → 紹介の成果を調整（12.5） |
| 係争あり | どれでも | `disputed`・運営へ警告 → 紹介の成果を保留（12.5） |

- 完了画面（`success_url`）でも、同じ `reconcileOrder` を呼ぶ。

### 9.3 定期の照合

**`/api/cron/b2c-reconcile`（新規・5分ごと）**

| 対象 | 処理 |
|---|---|
| `b2c_stripe_events` が `failed`、または `received` のまま5分以上 | 再処理（上限10回 → 運営の手動キュー） |
| `awaiting_payment` で作成から35分以上 | セッションを取り直して照合 |
| `paid` で手配が `pending` / `failed` | 手配処理を再実行 |
| 直近48時間に成功した B2C の PaymentIntent | DB に `paid` で無ければ照合（Webhook 不着の最後の網） |
| 紹介の台帳と、注文・返金・配送完了の差異（12.7） | 差異を運営へ警告し、該当の成果を `held` にする |

- 起動の仕組み: **既存の pg_cron と pg_net（`sql/052` で本番に導入済み）に、新しいジョブを1本足す**（本番 DB の変更なので承認事項）。それまでは、完了画面・Webhook の受信時の照合で補う。
- 二重起動は `lib/cron-lock.ts` で防ぐ。

### 9.4 手配処理（決済の成功と `shipments` の作成を分ける）

`fulfillOrder(orderId)`（冪等）:

1. `fulfillment_status` を `pending` → `in_progress` に条件付きで更新（10分で再取得可）。
2. B2C 専用の DB 関数 `b2c_apply_fulfillment` で、1トランザクションで:
   - `shipments` を `(booking_id, leg_index)` で upsert（`channel='b2c'`・`b2c_order_id`・`agency='BondEx Direct'`・`status='issued'`・`amount_yen`＝税抜の写し・集荷時刻11時）
   - 受け入れ確認の行を2件作る
   - 紹介の成果の見込み（`commission_ledger` の `pending`）を作る（12.5）
   - `fulfillment_status=done`
3. その後に、予約確定のメール（バウチャー付き）を送信待ちの列に積む。

- **`status='issued'` で作る理由**: `requested` だと発行キューに載り、P09 で金額が上書きされるため。
- 失敗時は `failed` にし、間隔を空けて再実行（1分 → 5分 → 15分 → 1時間）。15分以上終わらなければ運営へ警告し、「支払い済み・手配未完了」の一覧に出す。

### 9.5 二重決済・二重予約の防止

| リスク | 対策 |
|---|---|
| 予約ボタンの二重押し | `request_key`（UUID）を `b2c_orders.request_key UNIQUE` で受ける |
| Checkout の二重作成 | 有効なセッションは1注文に1件の一意の制約。`idempotencyKey = checkout_<注文ID>_<試行番号>` |
| 決済後の予約の二重作成 | `shipments` の `(booking_id, leg_index)` UNIQUE と条件付き更新 |
| Webhook の重複・順番の入れ替わり | `b2c_stripe_events` の主キー＋最新状態の取り直し |
| Webhook の途中停止・不着 | 定期の照合 |
| 決済は成功・手配は失敗 | 手配処理の分離と再処理 |
| 金額の改ざん | サーバーで算出した金額だけを使い、Stripe の金額と照合 |
| 本番のキーの誤用 | テストモードのキー（`sk_test_` / `rk_test_`）以外は起動時に拒否 |

### 9.7 Stripe アカウント構成の比較（未決）

#### 9.7.1 前提となる Stripe の仕様

- **Webhook の受け口はアカウント単位でイベントを受け取る。** 絞り込めるのはイベントの種類だけで、metadata では絞れない。同じアカウントに B2B と B2C の受け口を作ると、両方に両方のイベントが届く。
- 受け口は本番モードとテストモードで別々。既存の B2B の受け口は本番モード。**問題が起きるのは B2C の本番の決済を始めた時点から。**
- 既存の B2B の Webhook は、区間が見つからないと 500 を返す（DB の一時障害で検知を失わないための意図的な設計）。失敗が続く受け口は無効化されうる。

#### 9.7.2 比較

| 観点 | 案A: 既存アカウントを共用し、Webhook を分離 | 案B: B2C 専用アカウントを新設 |
|---|---|---|
| B2B の Webhook への影響 | 「区間が見つからない」分岐の中だけに判定を追加。B2B の決済のイベントは同じ処理 | 変更不要 |
| 返金・係争 | 両方の受け口に届き、それぞれ自分の分だけ処理 | それぞれのアカウントにだけ届く |
| 決済失敗 | B2C ではカードの拒否が日常的に起きるため、B2B 側の判定が必須 | B2B 側には届かない |
| 運用の負荷 | ダッシュボード・権限・係争の対応が1か所 | 設定・キー・Webhook・不正対策を二重に管理 |
| 入金の管理 | 同じ振込に入る。販路別の集計が必要 | 振込の段階で分かれる |
| 障害の影響 | アカウントの制限・キーの漏えいで B2B と B2C が同時に止まる | 片方で済む（同じ法人のため、審査で一緒に見られる可能性はある） |
| 立ち上げ | 申請不要 | 新規の申請と審査 |
| 後からの切り替え | 移行計画が必要（9.7.5） | — |

#### 9.7.3 案A の Webhook の分離の詳細

- **B2B の受け口への変更**は、`handleRefund`・`handleDispute`・`handlePaymentFailed` の「区間が見つからない」分岐の中だけ。
  1. 対象の PaymentIntent の ID が `b2c_payments` にあるか（DB）
  2. なければ Stripe から PaymentIntent を取り直し、`metadata.kind==="b2c_order"` か
  - **B2C と判別できたら 200 で終える。**
  - **判別のための DB・Stripe の呼び出しに失敗したら 500**（一時障害は再送させる）。
  - **B2C でもなく、ひも付く区間も無い決済は、これまでどおり 500。** （付録A E01: この変更で解消するのは B2C の決済による再送の繰り返しだけで、B2C 以外のひも付かない決済の問題は残る）
- B2C の受け口は、B2C でないイベントを `ignored` で記録して 200 を返す。
- **導入の順序（必須）**: B2B 側の判定を本番に出して回帰テストを通す → 本番モードで B2C の受け口を登録 → B2C の本番の決済を開始。
- 販路別の入金の集計（残高の取引を API で引いて metadata で分類）を、本番の決済の開始前に用意する。

#### 9.7.4 推奨: 案A（条件付き）。**決定は未決**（15章 U01）

- 理由: B2B への変更が1か所の分岐に限られる／審査待ちが無い／管理が1か所で済む／初期の件数が小さい。
- 条件: 導入の順序を守る、制限付きキーを使う、販路別の入金の集計を先に用意する。
- 案B に切り替える目安: B2C の係争が3か月で決済件数の 0.5% を超えた／Stripe から警告・制限の連絡／会計の判断で振込を分ける必要が出た／B2C の件数が B2B を大きく上回った。

#### 9.7.5 案B への移行計画（付録A E02）

キーの差し替えだけでは済まない。移行するときは次を計画する。

- `b2c_payments` の Stripe アカウントの識別子で、旧アカウントの決済と新アカウントの決済を区別する。
- **旧アカウントの決済の返金・係争は、旧アカウントで処理し続ける**（並行運用の期間）。
- Webhook の署名秘密を2系統持ち、両方の受け口を受ける。
- 過去の決済の照合、権限・通知・不正対策の設定、入金レポートの移行。

### 9.8 制限付きキーの権限表（付録A E03）

| 用途 | 対象 | 権限 |
|---|---|---|
| 決済の作成・再利用・照合 | Checkout Sessions | 書き込み（作成・取得・期限切れ） |
| 照合・判別 | PaymentIntents | 読み取り（取得・検索） |
| 照合 | Charges | 読み取り |
| 返金 | Refunds | 書き込み（作成・取得） |
| 係争の検知 | Disputes | 読み取り |
| 販路別の入金の集計 | Balance transactions・Payouts | 読み取り |
| イベントの取り直し（使う場合） | Events | 読み取り |

- 実装で実際に呼ぶ操作を洗い出して最終化し、最小権限のキーで受け入れテストを通す。

## 11. WhatsApp（受付完了後の連絡に限定）

### 11.1 範囲

| 含める | 含めない |
|---|---|
| 追跡の確認、利用者からの質問、集荷当日の預け入れの案内、対象の予約に影響する確定した遅延・集荷停止の連絡 | チャットでの新規受付、予約前の相談、決済、変更・取消の自動処理 |

- 紹介の成果は Web の申込に保存した情報だけを使い、WhatsApp の連携の有無に左右されない。
- WhatsApp を持たない人・連携しない人にはメールで連絡する。**WhatsApp が止まっていても、Web とメールで予約・配送は完了できる。**

### 11.2 連携の手順

1. 予約が `confirmed` になった後、確認ページ（トークンで本人を確認済み）に「WhatsApp で予約の連絡を受け取る」を表示する（予約確定のメールにも案内）。
2. 同意のチェック（**未選択が初期値**）。文面の版・日時・経路・対象の番号・用途を `b2c_consents` に記録する。予約の連絡と販促は別の同意。
3. サーバーが一時コード（暗号学的乱数 128bit 以上、DB にはハッシュ、**有効期限15分・1回限り・失効可能**）を作り、BondEx の番号（**宛先はサーバーで固定**）への送信文を用意する（`https://wa.me/<固定の番号>?text=LINK%20<コード>`）。
4. 利用者が**実際に送信**したら、署名を検証した Webhook で、送信者の番号とコードを照合する。クリックだけでは連携しない。
5. 照合できたら、その注文と送信者の番号を `b2c_channel_links` に結び付け、連携の完了を返信する（24時間枠内の返信）。
6. 期限切れのコードは、確認ページから再発行する。番号の入力やコードの所持だけでは、予約の情報を出さない。

### 11.3 送信待ちの列（`b2c_outbox`・メールと共通）

- 重複防止のキー: `(order_id, kind, channel, target_date)`。
- 日程変更・取消・同意の撤回で、未送信の通知を無効化する。**送る直前にも状態を再確認する。**
- 状態: `queued` / `sent`（API が受け付けた）/ `delivered` / `read` / `failed` / `cancelled`。**既読を必須にしない。**
- 恒久的なエラー・期限までに届かない場合はメールに切り替え、運営の対応キューに上げる。

### 11.4 受信と自動応答（P19）

- 既存の自動応答（`lib/whatsapp-tracking.ts`）の検索から、`channel='b2c'` の行を除外する。B2B の応答は変えない。
- B2C の受信の処理:
  - **連携済みの番号から**: 予約番号や「status」なら、その番号に連携された注文の状態だけを返す（ホテル名は返してよいが、認証付きの URL は載せない）。それ以外の質問は運営の対応キューへ（24時間枠内なら担当者が自由文で返信）。
  - **連携していない番号から B2C の予約番号が送られた場合**: 予約の有無も含めて何も明かさず、「予約確認メールのリンクから、WhatsApp の連携を行ってください」とだけ返す（B2B の「見つかりません」と区別できない文面にする）。
- 受信の重複の排除は、既存の `whatsapp_processed` を使う。

### 11.5 集荷当日の預け入れの案内

- 文面: 「本日 ○時までに、○個の荷物を ○○ホテルのフロントへお預けください」。**実際の集荷日と預け入れの期限**を基準に、日本時間で1回送る。
- **送る直前の確認（すべて満たす場合だけ）**: 両ホテルの受け入れ確認が `accepted` か `accepted_standing`／注文が `exception`・`cancelled` でない／確定した集荷の停止（11.6）に当たらない／集荷日が今日のまま／同意が有効。**3.7 の「荷物は手元に」の通知を送った注文には送らない。**
- 「預けた」の返信を受け付ける場合は、本人の自己申告として記録し、配送会社の集荷とは区別する（成果の根拠にしない）。
- **既存の集荷リマインド（1.7・未コミット）の再利用**:
  - 再利用するもの: 承認テンプレート（`bondex_pickup_reminder`）またはそれを B2C 向けに直したテンプレート、テンプレートの送信の関数、日付の表示の関数。
  - 再利用しないもの: `shipments.traveler_whatsapp`・`reminder_consent`・`reminder_enabled`（**代理店が入力する同意**のため、旅行者本人の同意を記録する B2C には使わない）。B2C 行は `reminder_enabled=false` のままにし、既存の cron の対象にしない（二重送信の防止）。
  - B2C の案内は、送る直前の確認を通る B2C 専用の送信処理（`b2c_outbox`）から送る。
  - **この並行作業が `origin/main` に入った後**に、共通化する部分（送信の関数・テンプレート）を確定する。それまで B2C 側は送信の関数を差し替えられる形にしておく。

### 11.6 確定した遅延・集荷停止の通知

- `service_incidents`: 根拠（配送会社の発表の URL・個別の確認）、確認した時刻、対象の範囲（区間・地域・集荷日・配達日・配送会社）、影響の内容、次の連絡の予定、承認した担当者、文面の版、状態（`draft` / `approved` / `sent` / `updated` / `resolved`）。
- 対象の予約は、範囲から自動で候補を出し、**担当者が確認して確定する**（`incident_recipients`）。一般的な天気予報だけで遅延と判断して一斉に送らない。
- 送信は担当者が確認してから行う（初期は自動送信しない）。更新・解消の連絡も同じ事象に結び付ける。到着の予定が分からない場合は、その旨と次の連絡の予定を伝える。
- `b2c_calendar` の例外の日（6.2）と結び付ける。

### 11.7 同意と 24時間の枠

- 事業者から始める送信・24時間枠の外の送信は、**承認済みのテンプレート**だけを使う。テンプレートの申請・区分の判断は Meta の審査に従う（**Meta の設定・申請は今回の承認範囲に含まない**）。
- 同意の撤回（「STOP」など）を受け付け、撤回の時刻を記録して以後の送信を止める。

## 12. AJ の紹介・成果・精算（v1.3 で追加）

### 12.1 範囲

| 含める | 含めない |
|---|---|
| AJ 専用の紹介リンク、30日の帰属、Web 申込への紹介元の保存、配送完了の個数に基づく成果台帳、取消・返金時の調整、AJ 専用の成果確認画面、月次の精算明細 | 他の媒体の一般募集・自由登録、紹介料の自動送金、クリックへの報酬 |

- 仕組みは `partners` に AJ を1件だけ登録する形で作り、将来の媒体の追加は「行の追加」で済む構造にする（今回は登録画面を作らない）。

### 12.2 紹介リンクと専用ページ

- 紹介リンク: `https://bondex.express/r/accessible-japan?placement=<値>`。`placement` はサーバーの許可リスト（例: `article-luggage`・`banner-top`・`newsletter`）の値だけを受け付ける。**自由な転送先の URL は受け付けない。** リンクは公開されるもので、認証には使わない。
- 到達時の処理: 紹介の到達（`referral_touches`）を記録し、専用ページ `/en/partners/accessible-japan` へ転送する。ボット・リンクの事前読み込み・プレビューは「到達数」には数えても「紹介セッション数」には数えない。
- 専用ページ: 「スーツケースを次のホテルへ。移動は身軽に」。ホテル間配送・英語のサポート・フロントへ預ける流れを短く説明し、主ボタンは料金と配送可能日の確認。**提携であること、利用により AJ へ紹介料が発生することを明示する。** AJ のロゴ・推薦の表現は先方の許諾の後（15章 U10）。「利用者の追加負担はない」の表示は、販売価格を確定してから。
- AJ 側のリンクには `rel="sponsored"` を付けてもらう（AJ への依頼事項）。

### 12.3 帰属の規則（30日・最後の有効な紹介）

- **判定の時点**: サーバーで有効な `b2c_orders` を作成した時点（下書き・相談・WhatsApp の問い合わせは含めない）。
- **対象**: その時点から遡って30日以内の、**最後の有効な紹介**。通常の広告の UTM・直接の訪問では紹介元を消さない。ページの再読み込み・ボットでは期限を更新しない。新しい有効な紹介のクリックでは更新する。
- **固定**: 注文に `partner_id`・`referral_touch_id`・`attribution_method`（`cookie` / `session_apply` / `code`）・`partner_terms_version_id` を固定する。配送が30日より後でも成果の対象にする。
- **後からの追加**: 直接の予約の後から紹介コードを追加することは、原則として対象外（例外は根拠つきで担当者が承認）。
- **規則の版**: 30日・最後の有効な紹介・紹介コードの扱いは `partner_terms_versions` の設定値として持つ。**AJ と未合意の点（競合の規則・コードの扱い）は、合意した版を作るまで本番の精算に使わない。**

| ケース | 判定 |
|---|---|
| AJ のリンクから入り30日以内に申込 | AJ |
| 紹介期間の後の新規の予約 | 対象外（新しい有効な紹介が必要） |
| AJ → 申込 → WhatsApp 連携 | 申込時の帰属を保持（連携しなくても対象） |
| 別の端末で再開 | 本人確認した同じ注文の再開なら保持。端末の指紋などで推測しない |

### 12.4 計測と同意

- **同意の前は、30日の識別子を保存しない。** B2C のページに計測の同意の画面を出す（必須の Cookie と、紹介の計測の Cookie を分ける）。外部の同意管理サービスは使わない。
- 同意した場合: Cookie `bx_ref`（`Secure`・`HttpOnly`・`SameSite=Lax`、最後の有効な紹介から30日）に紹介の到達の ID を入れる。期限はサーバーでも確かめる。
- 拒否した場合: 同じセッションの中で「紹介元: Accessible Japan — この申込に適用する」を本人が選べるようにする（その申込に限って保存）。**セッションの Cookie を、拒否された30日の計測の代わりに隠れて使わない。**
- **公開紹介コード**: 申込の画面で入力でき、適用時に「紹介元: Accessible Japan」と表示する。コードは認証には使わない。クリックの記録が無いコードの利用は、自動の追跡とは別に集計し、成果の対象にするかは規則の版で決める（AJ との合意事項）。コードで30日の制限を無制限に回避できないようにする（コードの適用も「その時点の紹介」として扱う）。
- 別の端末・Cookie の削除・連携なしの直接の予約は、100% は捕捉できない。この限界を AJ に説明する。IP の一致やメールのハッシュで、無断に利用者を追跡しない。
- 対象とする法域・プライバシーの表示は公開前に確定する（15章 U08）。

### 12.5 成果台帳（`commission_ledger`）

- **単位**: 「適格な荷物1個 × 配送区間」。2個の予約で1個だけ配送完了なら、その1個だけ。個口のテーブルは作らず、区間ごとの配送完了の個数（`shipment_delivery_confirmations.delivered_item_count`）を根拠にする。
- **確定の条件（すべて）**: 紹介の帰属が有効／入金済み（`payment_status` が `paid` か `partially_refunded`）／配送完了の確定がある（取り消されていない）／未解決の返金・係争・不正の保留が無い／テストの予約でない。
- **状態**:

| 状態 | 意味 |
|---|---|
| `pending` | 手配処理で作る見込み（配送前） |
| `held` | 返金・係争・照合の差異・不正の疑いで調査中 |
| `approved` | 条件を満たし、支払いの対象 |
| `paid` | 振込を記録し、消し込み済み |
| `rejected` | 配送前の取消・対象外・不正など（理由を残す） |

- **金額**: 整数円。単価・税区分・規則の版は、申込時点の `partner_terms_versions` のスナップショットを持つ。
- **一意性**: 通常の成果は `(partner_id, shipment_id, commission_type='delivered_items')` で一意。配送会社の情報の再取得・イベントの再送で増えない。
- **調整（取消・返金）**:
  - 配送前のキャンセル・全額返金 → `pending` を `rejected`（理由つき）。
  - 確定前の一部返金 → 返金で影響した個数（8.3 の `affected_item_count`）を成果の対象の個数から差し引く。お詫びの値引き（`goodwill`）は個数を減らさない（ただし扱いは AJ との合意で決める）。
  - **確定（`approved`）・支払い（`paid`）の後**の返金・係争・配送完了の取り消し → **元の行は変えず、差額の調整の行（`adjustment`、固有の ID）を追加**し、次の精算に含める。
  - 係争が起きたら、その注文の成果を `held` にする。
  - 返金に対する報酬の減額の基準・相殺の方法は、AJ との合意の後に規則の版で適用する（それまでは担当者の確認で `held` にする）。
- 台帳の行は削除しない。訂正はすべて追記で行い、監査ログに記録する。

### 12.6 月次の精算と手動の振込

- **締め**: 月末（JST）。翌月の第1営業日に、前月に条件を満たした成果を `approved` にして、精算の下書き（`settlement_batches`・明細）を作る。
- **確認と承認**: 担当者（`b2c_finance`・直近の二段階認証）が金額と明細を確認して承認する。承認するまで AJ の画面に「確定」として出さない。
- **振込（手動）**: 当初は担当者が銀行で振り込み、振込日・金額・照会番号を `payouts` に記録して `paid` にする（**成果の条件を満たしただけで自動送金しない**）。支払いの期限は翌月末。
- 締めの後〜振込の前に見つかった返金・係争は、振込の前に保留へ反映できるよう、締めの集計と最終の振込額を照合する。支払い済みの訂正は翌月の調整の明細にする。
- **振込先の情報はシステムに保存しない**（当初は銀行に登録した振込先を使う）。振込先の変更は、AJ からの既知の連絡先への別経路の確認・変更の通知・承認の記録を必須にし、メール本文だけでは変えない。
- 未確定の分は繰り越し、取消・返金・係争は明細に理由を表示する。
- AJ と未合意の条件（税区分・複数区間の数え方・返金時の精算）が残る間は、`B2C_COMMISSION_APPROVAL_ENABLED=false` で、本番の成果の確定と精算を始めない。

### 12.7 AJ の成果確認画面（`/partners`）

| 表示する | 表示しない |
|---|---|
| 期間別・配置（placement）別の紹介の到達数と紹介セッション数（定義を併記） | 顧客の氏名・電話・メール |
| 有効な申込の数、決済済みの数 | ホテル・旅程・日付の詳細・追跡番号 |
| 配送完了の個数 | チャット・問い合わせの内容 |
| 見込み・保留・確定・支払い済みの紹介料 | 障害・健康の情報 |
| AJ 専用の照会番号ごとの明細（月・個数・金額・状態・調整の理由） | Stripe の顧客 ID・予約番号 |
| 月次の精算明細（CSV） | — |
| 最終更新の日時、計測の範囲・定義 | — |

- **AJ 専用の照会番号**は、予約番号とは別に作る（例: `AJ-202611-0007`）。顧客の確認ページへの鍵にはしない。
- 件数が少ない場合に個人の特定につながる細かい属性別の分析は出さない（明細の日付は月単位にする）。
- **分離**: 画面の非表示だけで制御しない。API はログインした `partner_users.partner_id` だけで絞り込み（URL の ID を信用しない）、DB は B2C の専用の関数・ビューで AJ の分だけを返す。CSV・集計・検索・キャッシュでも越境させない。
- CSV は数式の注入を防ぎ、生成したファイルは短時間で失効し、認証が必要。
- ログイン・CSV の出力は監査ログに残す。

### 12.8 不正・異常への対応

- クリックには報酬を払わず、実際の配送で確定する。
- 自動の iframe・背景のリクエストからの紹介の付与を防ぎ、見えるページでの明示的な操作・申込と結び付ける（Referer だけに頼らない）。
- 異常な頻度・取消率・短時間の大量の申込を検知したら `held` にする（IP だけで失格にしない）。
- 紹介の仕組みに異常があるときは、`B2C_COMMISSION_APPROVAL_ENABLED` で成果の確定と精算だけを止め、予約と配送は続ける。
- 定期の照合（9.3）で、「入金・返金」「注文」「配送完了」「紹介の台帳」「精算の明細」の差異を検出する。

## 17. テスト計画

### 17.1 基盤

- `vitest`（単体・結合）と `@playwright/test`（E2E・モバイル・axe）を devDependencies に追加する。既存の自己検証スクリプト（`scripts/test-*`）とは共存させる。

### 20.2 DB の変更の影響

- 追加だけ（列2つ・索引1つ・トリガー1つ・代理店1行・新規テーブル）。既存の行は `channel='b2b'`・`b2c_order_id=NULL`。トリガーは B2B 行では何もしない。
- ロールバック: トリガーの削除 → 列の削除 → 代理店の行の削除 → 新規テーブルの削除（B2C 行が無ければデータの損失なし）。**ロールバックしても、既存の予約・紹介の台帳は消さない**（公開後は、機能フラグで止める方を先に使う）。
