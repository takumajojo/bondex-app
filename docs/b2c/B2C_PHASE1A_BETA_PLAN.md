## 1. 決済の方式（A と B の比較）。**未確定**

BondEx の考え方: 予約の時に旅行者へ請求しない。実際に集荷された後に請求する。

- **A**: 予約の時に SetupIntent でカードを登録する（本人認証・カードの有効性の確認・後日の請求への同意を含む）。集荷の後に、off-session の PaymentIntent で請求する。
- **B**: 予約の時に PaymentIntent（`capture_method=manual`）で、金額の枠を確保する（オーソリ）。集荷の後に、その枠から売上を確定する（キャプチャー）。

どちらも、予約の時点では売上を確定しない。違いは、B は予約の時点で旅行者の利用枠を実際に押さえる（明細に「保留」が出る）こと。

| 観点 | A: SetupIntent → 集荷後に PaymentIntent | B: 予約時にオーソリ → 集荷後にキャプチャー |
|---|---|---|
| 長期の予約（最大 180日先） | 期限が無い。カードの有効期限が切れた時は、Stripe のカード情報の自動更新が効く場合がある | 有効期間を超える予約は枠を持てない。結局 A と同じ登録が必要になり、二つの方式を併用することになる |
| オーソリの有効期間 | 該当しない | 日本の Stripe アカウントで円建てなら、Visa・Mastercard・JCB・Diners・Discover は最長 30日。Amex は 7日[^1]。**ただし海外で発行されたカード（阪急の主な客層）には、2026年10月から Visa の PIPF が適用される。** 期間内に確定または取消をしないオーソリには、手数料がかかりうる。期間は、カード非提示で MIT ではない取引が 10日、MIT が 5日[^2]。Mastercard は国をまたぐ事前オーソリを 7日以内に確定または取消する規則がある[^2]。**実際に安全に持てるのは 5〜10日** |
| カードのブランドの差 | 影響しない | 上のとおり、ブランドと発行国で期間が変わる。予約ごとに期限を管理する必要がある |
| 3D セキュア（本人認証）・SCA | 登録の時に本人認証を通す（顧客が操作する取引）。後の請求は、同意のうえで加盟店が行う取引（MIT）として、免除を申請する。免除が通らなければ `authentication_required` で失敗する[^3] | オーソリの時に本人認証を通すので、確定の時には不要 |
| off-session の失敗 | 起こりうる（残高不足・カードの停止・本人認証が必要）。集荷の後に分かる | 確保した額の範囲では、ほぼ起きない。ただし確定は 1回だけで、追加の個数の分は別の請求（＝A と同じ失敗の可能性）[^1] |
| 再認証・回収 | 失敗した PaymentIntent を使い、メールや WhatsApp で旅行者に本人認証や別のカードの入力を求める。Stripe が示している標準の流れ[^3] | 期限切れの時は、取り直しのために旅行者の操作が必要 |
| キャンセル | 何もしなくてよい（請求していないため）。カード情報を消すだけ | オーソリの取消が必要。取消を忘れると、上の手数料や旅行者の苦情の原因になる |
| 運用の負担 | 失敗した時の回収（人の対応）が発生する | 期限の監視・取り直し・取消漏れ・明細の「保留」への問い合わせが発生する |
| Stripe の手数料 | 請求した分だけ | 確定した分は A と同じ。確定しない取消は、返金の扱いにならない[^4]。**ただし PIPF の期間外のオーソリは、1件ごとに手数料がかかりうる**（標準の料金体系では当面は Stripe が負担すると案内されている[^2]） |
| 既存の B2B との共通化 | **B2B と同じ方式**（`app/api/stripe/setup-intent/route.ts` の `usage: off_session`、`lib/charge.ts` の off-session 請求）。部品をそのまま使える | B2B に無い流れ。新しく作る |

**提案: A（SetupIntent → 集荷後に PaymentIntent）**

阪急の旅行者の多くは海外で発行されたカードを使う。その場合、B のオーソリを安全に持てる期間は 5〜10日しかない。予約は最大 180日先まで受けるので、B では大半の予約に A を併用することになり、仕組みが二重になる。A は BondEx の考え方（集荷の後に請求）にそのまま合い、B2B と同じ部品を使える。失敗の危険は、次の手当てで下げる。

1. 登録の時に、本人認証（3D セキュア）を必ず通す。同意の文面には、請求の時期（集荷の確認の後）・金額の決め方・請求の方法を書き、同意の版と時刻を保存する[^3]。
2. 請求の失敗は、そのまま未収にしない。失敗した PaymentIntent で、旅行者に本人認証や別のカードの入力を求めるリンクを、メールと WhatsApp で送る（B2B に無い部分を足す）。
3. 二重の請求を防ぐ。区間ごとに 1つの重複防止キー（試行ごとに連番）を使い、`b2c_payments` の一意の制約と条件付きの更新で守る。B2B のキーの弱点（13.1）は持ち込まない。
4. （任意・Phase 1B）失敗の率を見て、必要なら「集荷の 2日前に短いオーソリを取る」案を検討する。期間が PIPF の範囲内に収まる。**Phase 1A では入れない。**

**確認が必要なこと（Stripe）**: 当社の料金体系が標準か IC+ か（PIPF の手数料の扱いが変わる）。MIT の免除の通りやすさ。Radar を SetupIntent に効かせる設定[^3]。

[^1]: Stripe「支払い方法を保留する」https://docs.stripe.com/payments/place-a-hold-on-a-payment-method （2026-11-03 に確認）
[^2]: Stripe Support「Visa Processing Integrity Program Fee (PIPF) in Japan」https://support.stripe.com/questions/visa-processing-integrity-program-fee-(pipf)-in-japan （2026-11-03 に確認）
[^3]: Stripe「支払いを行わずに顧客の決済手段を保存する」https://docs.stripe.com/payments/save-and-reuse?payment-ui=elements （2026-11-03 に確認）
[^4]: Stripe「キャプチャされていない決済のレビュー」https://docs.stripe.com/radar/reviews/auth-and-capture?locale=ja-JP

## 2. 未確認のホテルと締切の矛盾の解消（実装済み・`lib/b2c/hotel-gate.ts`）

| ホテルの状態 | 受付 |
|---|---|
| verified（確認済み） | 通常の締切（前日 17:00）まで、即時に予約・確定できる |
| unsupported（受けない） | 予約できない |
| unknown（未確認） | **ホテルを確認する時間を確保できる集荷日だけ選べる**。確認の期限は、予約の翌営業日 17:00。この期限が、ホテルへの連絡の期限（集荷の 2営業日前 17:00。B2B と同じ）を超える日は、最初から選択肢に出さない |

- 例: 集荷前日の 16:50 に未確認のホテルで予約しようとすると、その集荷日は選べない。選べる最も早い集荷日が表示される（`earliestPickupWithUnknownHotel`）。
- 予約を受けた後に「最初から確認できなかった」状態は起きない。確認の期限までに運営が判定しなければ、取消になる（監視して要対応に出す）。
- ホテルの表には `last_verified_at` と `verified_until` を持たせ、後で確認し直せるようにする（表の設計案 v1.2）。
- テスト: `scripts/test-b2c/run.ts`（25件）。金曜の予約は月曜、祝日（11/23）は飛ばすことも確認済み。

## 4. 実装を始めるための最終の承認事項

1. **決済の方式**: A（SetupIntent → 集荷後に PaymentIntent）とする。
2. **Phase 1A の範囲**: 上の 3.1 を作り、3.3 を後回しにする。とくに「1予約 1区間」と「予約後の自己変更は取消だけ」。
3. **未確認のホテルの受付**: 上の 2 の規則とする（確認の期限＝翌営業日 17:00、集荷の 2営業日前 17:00 までに収まる日だけ）。
4. **試験の環境**: Supabase の試験用のブランチを 1つ作る。費用は 1時間 $0.01344（Supabase の見積もり、2026-11-03）で、つけっぱなしで **月 約 $9.8**。Phase 1A の期間（約 2か月）で約 $20。使わない時は消せる。Stripe はテストモードのキーを使う（費用なし）。
5. **Beta の開始の目標**: 2027-01-05（火）。
