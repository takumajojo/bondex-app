## 1. 決済の方式（A と B の比較）。**A を正式採用（2026-11-03）**

BondEx の考え方: 予約の時に旅行者へ請求しない。実際に集荷された後に請求する。

- **A**: 予約の時に SetupIntent でカードを登録する（本人認証・カードの有効性の確認・後日の請求への同意を含む）。集荷の後に、off-session の PaymentIntent で請求する。
- **B**: 予約の時に PaymentIntent（`capture_method=manual`）でオーソリを取り、集荷の後にキャプチャーする。

どちらも予約の時点では売上を確定しない。違いは、B は予約の時点で旅行者のカードの利用可能額を実際に押さえる（明細に「保留」が出る）こと。

| 観点 | A: SetupIntent → 集荷後に PaymentIntent | B: 予約時にオーソリ → 集荷後にキャプチャー |
|---|---|---|
| 長期の予約（最大 180日先） | 期限の問題が無い | オーソリには有効期限がある。日本の Stripe アカウントの円建ては、Visa・Mastercard・JCB・Diners・Discover が最長 30日、Amex は 7日[^1]。180日先の予約は持てず、A の併用が必要 |
| 期限と手数料 | 該当しない | **オーソリの有効期限とは別に**、2026年10月から Visa の PIPF の期間がある。海外で発行されたカードの円建ては、期間内（カード非提示で MIT 以外は 10日、MIT は 5日）に確定または取消をしないと、1件ごとに手数料がかかりうる[^2]。Mastercard は国をまたぐ事前オーソリを 7日以内に確定または取消する規則がある[^2]。オーソリ自体はその後も有効でありうるが、手数料を避けるには短い期間で確定または取消が必要 |
| カードのブランド・発行国の差 | 影響しない | 上のとおり、ブランドと発行国で期間が変わり、予約ごとに管理が必要 |
| 本人認証（3D セキュア） | 登録の時に本人認証を**要求する**。実際に認証されたかどうかは、カードと発行会社によって変わる（結果を記録する）[^3]。後の請求は加盟店が行う取引（MIT）として、免除を申請する。免除が通らなければ `authentication_required` で失敗する[^4] | オーソリの時に本人認証を要求する。結果はカードと発行会社しだい |
| off-session の失敗 | 起こりうる（残高不足・カードの停止・本人認証が必要）。集荷の後に分かる | 押さえた額の範囲ではほぼ起きない。ただしキャプチャーは基本 1回で、追加の個数の分は別の請求（A と同じ失敗の可能性）[^1] |
| 再認証・回収 | 失敗した PaymentIntent を使い、旅行者に本人認証や別のカードの入力を求める（Stripe の標準の流れ）[^4]。それでも回収できない未収は残りうる | 期限切れの時は、取り直しのために旅行者の操作が必要 |
| キャンセル | 請求していないので、カード情報を外すだけ | オーソリの取消が必要。取消漏れは手数料・苦情の原因 |
| 運用の負担 | 請求の失敗の回収 | 期限の監視・取り直し・取消漏れ・「保留」への問い合わせ |
| Stripe の手数料 | 請求した分だけ | 確定した分は A と同じ。期間外のオーソリには PIPF の手数料がかかりうる（標準の料金体系では当面 Stripe が負担と案内）[^2] |
| 既存の B2B との共通化 | B2B と同じ方式（`app/api/stripe/setup-intent/route.ts:84` の `usage: "off_session"`、`lib/charge.ts:135` の `off_session: true`） | B2B に無い流れ |

**提案: A。** 理由は、最大 180日先の予約と「集荷の後に請求する」流れを、期限の管理なしに単純に扱えること。B2B と同じ部品を使えることも理由になる。PIPF の手数料の期間は、B を選ぶ場合の追加の負担として挙げる（A を選ぶ主な理由ではない）。
A の弱点（集荷の後の請求の失敗）は、本人認証の要求と結果の記録、同じ PaymentIntent での回収のリンク、Beta の未収の上限（未回収の請求 2件、または合計 3万円で新しい予約を止める・5章。2026-11-04 に 5件の記載と不一致だったため 5章に統一）で抑える。**集荷後の請求では、回収のリンクを送っても未収が残りうる**ことを前提に運用する。

確認が必要なこと（Stripe）: 当社の料金体系（標準か IC+ か）、MIT の免除の通りやすさ、SetupIntent に Radar を効かせる設定[^4]。

[^1]: Stripe「支払い方法を保留する」https://docs.stripe.com/payments/place-a-hold-on-a-payment-method （2026-11-03 に確認）
[^2]: Stripe Support「Visa Processing Integrity Program Fee (PIPF) in Japan」https://support.stripe.com/questions/visa-processing-integrity-program-fee-(pipf)-in-japan （2026-11-03 に確認）
[^3]: Stripe「3D セキュアの認証フロー」https://docs.stripe.com/payments/3d-secure/authentication-flow （Codex の監査で指摘。未読）
[^4]: Stripe「支払いを行わずに顧客の決済手段を保存する」https://docs.stripe.com/payments/save-and-reuse?payment-ui=elements （2026-11-03 に確認）

## 2. ホテルの条件と、予約の確定の時点（実装済み・`lib/b2c/hotel-gate.ts`、テスト 29件）

**施設の確認**（そのホテルに、フロントに人がいて荷物を預かれる実績・能力があるか）と、**予約ごとの受入の確認**（その予約の荷物を、集荷元が預かって佐川に渡せるか・配送先が受け取れるか）を分ける。

| 予約の種類 | 受付 | 確定 | 確認の期限 |
|---|---|---|---|
| 両ホテルが施設として確認済み、かつ通常の連絡の期限（集荷の 2営業日前 17:00）より前 | 前日 17:00 まで | **予約の時点で確定**。その予約の受入は、通常の連絡の期限までに運営が両ホテルに確認する | — |
| 両ホテルが確認済み、かつ通常の連絡の期限を過ぎた（直前予約） | 前日 17:00 まで。**ただしその日に至急の対応の担当者がいる時だけ**（`b2c_ops_days.late_duty_staff`） | **ホテル確認待ち**。集荷元・配送先それぞれの受入の確認がそろってから確定 | **集荷の前日 18:00**（佐川への連絡を 18:30 までに済ませるため。世田谷営業所の緊急の変更の受付は 18:30 まで・カスタマーサービスは 19:00 まで。マスター 181・182） |
| 未確認のホテルを含む | 確認の期限までに 2時間以上ある集荷日だけ選べる（無い日は最初から選べない） | **ホテル確認待ち**（`awaiting_hotel_confirmation`）。集荷元・配送先の両方について、有人のフロント・荷物の預かり・配送業者への受け渡しができることを確認してから確定 | **min(予約の翌営業日 17:00, 集荷の 2営業日前 17:00)** |
| 受けないホテルを含む | 予約できない | — | — |

- 期限までに確認できない、または受入を断られた時は、**予約を取り消し、旅行者にメールと WhatsApp で通知する。請求はしない**（請求は集荷の確認の後にしか作らない）。通常の予約で、期限内の連絡で断られた場合も同じ。
- **画面とメールに出すこと**（日本語・英語）: 受付の時点では予約が確定していないこと／回答の期限（日時）／期限までに確定しなければ自動で取り消され、料金は一切かからないこと／確定した時に届く通知の方法。確認待ちの間の My Booking は「Request received — Confirming with hotel」と表示し、集荷を約束する表現を使わない。
- これは未確認のホテルの日付の制限を緩めるものではない。確認済みのホテルの直前予約に、確定の条件を足すもの。

## 5. Beta の受付の上限（人員と作業時間からの提案）

**前提（要確認）**: B2C の運用に、1人が 1日 2時間を充てる。担当者の人数と時間が違えば、上限も比例して変える。

1件あたりの人の作業時間の見積もり（B2B の運用からの推定。Beta の最初の 2週間で実測して見直す）:

| 作業 | 分 |
|---|---|
| ホテルへの連絡（集荷元・配送先の 2か所） | 10 |
| 佐川への集荷依頼 | 3 |
| 集荷の確認と請求の確認 | 5 |
| 問い合わせへの対応（平均） | 5 |
| **通常の予約 1件** | **約 23** |
| 未確認のホテルの施設の確認（1ホテル） | ＋15 |
| 直前予約の至急の受入確認と個別の集荷依頼 | ＋15 |
| 請求の失敗の回収（1件） | ＋15 |

1日 120分 ÷ 約 23〜40分 ≒ 3〜5件。これを上限の根拠にする。

| 上限 | 提案 | 理由 |
|---|---|---|
| 1日の新しい予約 | **5件**（集荷日ごと） | 上の計算。超えたらその集荷日は選べない |
| 直前予約 | **1日 2件**、担当者がいる日だけ | 1件あたり＋15分で、夕方の時間帯に集中するため |
| 1予約の個数 | **10個まで**（全体の設計の上限 50個から Beta だけ下げる） | 20個以上は世田谷営業所への事前の連絡が必要（マスター 89） |
| 1集荷日の合計の個数 | **19個まで** | 同上。20個に達しないようにする |
| 未収 | **未回収の請求が 2件、または合計 3万円に達したら、新しい予約を自動で止める**（`B2C_BOOKING_ENABLED` 相当の受付の停止。既存の予約は動く） | 回収は 1件 15分＋追いかけが続く。集荷後の請求では未収が残りうるため、損失の上限を先に決める |
| 担当者の不在 | 担当者がいない日は直前予約を受けない（2）。終日不在の日は `b2c_ops_days.closed` で受付を止める | 確認の期限を守れない予約を作らない |

## 6. Beta の公開の条件

1. 決済の方式の承認（7 の 1）。
2. 二重請求の防止（表の設計案の 5章）を、DB・Stripe・アプリで試験済み。とくに「Stripe で成功・DB の記録に失敗」の後の再試行で二度目の請求が起きないこと。
3. B2C の行が B2B の課金・代理店の API・公開の追跡・WhatsApp の自動応答・CSV に入らない（見えない・変えられない）ことを試験済み。
4. 予約の確定の条件（4章）と期限切れの自動の取消が、通知の順序の逆転・重複でも正しく動くことを試験済み。
5. 試験の環境での通しが全部通る（正常・未確認のホテル・直前予約・締切・カード登録の失敗・請求の失敗と回収・取消・返金・各スイッチの停止）。
6. 法務のページ（特定商取引法の表示・利用規約〔高価品は補償の対象外・カバーの推奨・集荷の現場で個数が増えた時の請求・確認待ちの扱い〕・プライバシー・キャンセル規約）の弁護士の確認。日本語・英語。
7. お客様の問い合わせ窓口（メール・WhatsApp）の確定と、WhatsApp のテンプレートの承認。
