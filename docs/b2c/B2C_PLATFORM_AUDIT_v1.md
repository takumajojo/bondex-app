## 00. 要約

1. **B2C の決済は、既存の B2B と同じ「カード登録 → 集荷後に課金」の形で作れる**（`lib/charge.ts:47-202`）。ただし B2B の仕組みは、課金の相手が代理店（代理店の Stripe の顧客）で、失敗した時に本人に認証してもらう手段も無い。B2C では、**旅行者ごとの顧客・カード・注文を B2B と分け**、海外のカードで起きやすい「本人の認証が必要」「拒否」への対応（13章）を新しく作る。集荷の確認を課金の合図にするので、**何をもって集荷とするか**の定義が課金の正しさを決める（13.3）。
2. **月 3,000件の最大の障害は配送の手作業。** 今は 1件ごとに「佐川へ集荷依頼（電話・メール）」「両ホテルへ連絡」「追跡番号の手入力」を人が行っている（`app/api/cron/daily-todo/route.ts:73-124`、`app/api/operator/sagawa-pickup/route.ts:27-30`、`app/api/operator/shipment/[id]/edit/route.ts:132-160`）。本番の実績は直近で月 15件（2026-10）。3,000件は約 200倍で、**この手作業を自動化しない限り、阪急・ShipAll の受付量を増やせない。**
3. **価格の指示が資料の間で食い違っている。** 今回の依頼は「4,980円（税込）が基準・税抜への変更は未承認」。一方、10/30 のやり取りでは「4,980円 税抜」とお答えいただき、状態ファイル（`~/JOJO/state/bondex.md`）にもそう記録済み。どちらが正しいかの確認が必要（10章 D01）。この監査では、どちらにも書き換えていない。

### E. ShipAll 連携

- 紹介 URL・ホテル識別・端末識別・戻り先・月次 CSV・手数料のどれも、既存のコードには無い（B 参照）。
- 本番の `agencies`「株式会社ShipAll」はカード払いの B2B 代理店として有効。**B2C の紹介取引はこの行と結ばない**（提案書 09章のとおり、`partners` に別の行を作る）。理由: 代理店の行に結ぶと、代理店の画面・権限（名前の一致で他の注文が見える RLS、`sql/002_agencies_auth.sql:51-61`）と請求の対象に、消費者の注文が混ざるため。

## 05. 推奨システム構成

```
[入口]  阪急の紹介URL / 海外代理店URL / ツアーURL / ShipAll タブレット(ホテル固定) / 直接
           │  /h/<推測不能なコード>  （紹介元は URL の中身でなく、サーバーの表で解決）
           ▼
[B2C 予約画面] ── 見積・判定（共通の判定関数: 佐川の日数・締切・ホテル・カレンダー）
           │
           ▼
[b2c_orders 作成] ─→ [カード登録 SetupIntent・本人認証・同意] ─→ [B2C 専用 Webhook + 定期の照合]
                                              │ カード登録の完了＝予約確定（課金なし）
                                              ▼
                                   [手配処理] shipments に channel='b2c' で作成
                                              │ … 集荷 …
                                              ▼
                                   [集荷確認] → [B2C の課金 off_session] → 失敗時は旅行者へ認証・カード変更の案内
                                              │
           ┌──────────────────────────────────┼───────────────────────────┐
           ▼                                  ▼                           ▼
[ホテルへ自動通知・受け入れ返信]   [佐川へ一括の集荷依頼(要確認)]   [旅行者へ確認メール・確認ページ]
           │                                  │
           └──────────── 共通の配送管理（B2B と同じ shipments・追跡・遅延の検知）────┘
                                              │
                                   [パートナー: 月次 CSV・手数料台帳・(将来) Webhook / Partner API]
```

方針:

1. **B2C は「入口から手配まで」を別の層、「手配の後」は B2B と共通。** 注文・決済・紹介は `b2c_*` と `partners*` に閉じ込め、`shipments` には手配の後に 1行（区間ごと）を足すだけにする。こうすると、追跡・遅延の検知・運営の配送画面は B2B と同じものが使える。
2. **既存 B2B への変更は 3か所に絞る。**
   - 集荷時の自動課金（4か所の呼び出し元）で `channel` を見て、B2C の行は B2C の課金へ回す（B2B の課金関数には渡さない）。
   - 金額を書き換える既存の経路（設計書 1.3 の P01〜P17）で B2C を除外する。
   - `shipments` に列を足す（`channel`・`b2c_order_id`）。既存の行は `channel='b2b'` の既定値で、動きは変わらない。
3. **紹介元は URL のパラメータで受けない。** ShipAll の案（`?ref=shipall&hotel=H001`）は書き換えれば別のホテル・別の紹介元になる。推測できないコード（`/h/<code>`）をサーバーの表で引いて、パートナー・ホテル・端末を決める（提案書 04章）。
4. **日数が分からない区間は即時に予約させない。** 旅行者に配達予定日を約束するため。その区間はリクエスト扱い（運営が確認してからカード登録の案内）にする。
5. **将来の OTA・Partner API は、同じ注文の表の「入口の種類」を増やすだけで受けられる形にする。** 今は作らない。

## 06. DB 設計方針

**既存の表への変更は「追加だけ」。** 列の削除・型の変更・既存の行の書き換えはしない。

| 表 | 変更 | 理由 |
|---|---|---|
| `shipments` | `channel text not null default 'b2b'`、`b2c_order_id uuid null` を追加 | 課金の振り分け・金額の書き換えの除外の目印。B2C の課金の記録は `shipments` の課金列（`charged_at` 等）でなく B2C の表に持つ（13.5） |
| `agencies` | 変更しない | B2B 代理店と B2C の紹介元を混ぜない |

**新規の表**（設計書 13章＋提案書の追加。名前は案）:

| 表 | 主な列 | 備考 |
|---|---|---|
| `partners` | `partner_type`（media / travel_agency / platform / hotel）、`status`、`agency_id`（B2B の代理店の行がある会社だけ参照。ShipAll など） | 紹介元の会社 |
| `partner_sub_referrers` | `partner_id`、`kind`（overseas_agency / tour / hotel）、`external_code`（ShipAll の H001 等）、`status` | 阪急の海外代理店・ツアー、ShipAll のホテル |
| `partner_devices` | `sub_referrer_id`、`label`、`status`、`last_seen_at` | **新規（今回の依頼の「端末識別」）。** ログインはさせない。止めたい端末だけ無効にできる |
| `b2c_entry_links` | `code`（推測不能・UNIQUE）、`link_type`（hotel_fixed_origin / referral_only）、`partner_id`・`sub_referrer_id`・`device_id`、固定のホテル、`status`、期限 | 入口。無効化は `status` |

| `b2c_orders` | 設計書 13.2 のとおり＋`entry_link_id`・`partner_session_ref`（ShipAll の受け渡しの値。中身は解釈しない） | 紹介の情報は**作成時に固定** |

## 07. 予約・決済・配送の状態遷移案（2026-10-30 改訂: カード登録 → 集荷後に課金）

設計書 5.2 を、予約時のカード登録と集荷後の課金に合わせて組み替えた。決済の細部は 13章。

```
注文 status（注文全体）:
 draft ─(判定OK・SetupIntent作成)→ card_pending ─(カード登録・本人認証・同意が完了)→ booked
   │                                   └─(30分で期限切れ・登録失敗)→ expired
   └─(日数不明・未審査ホテル)→ pending_review ─承認→ card_pending / ─拒否→ rejected

 booked ─(ホテル両方が受け入れ・佐川の集荷依頼済み)→ ready_for_pickup
        ─(集荷確認)→ picked_up ─(輸送中)→ in_transit ─(配達完了を確定)→ completed
 booked / ready_for_pickup ─(キャンセル)→ cancelled（課金なし・カードを外す）
 どこからでも ─(ホテル拒否・集荷できない・課金の回収不能・係争)→ exception（運営が対応）

課金 payment_status（区間ごと。13.4）:
 card_registered ─(集荷確認)→ charge_scheduled ─(課金の実行)→ charging
   charging ─成功→ paid ─→ (partially_refunded | refunded | disputed)
   charging ─失敗→ action_required（本人の認証が必要）／ declined（拒否・残高不足）
   action_required / declined ─(旅行者が認証・カード変更)→ charging
                              ─(自動の再試行)→ charging
                              ─(期限を過ぎて回収できず)→ uncollectible（運営の未収の一覧）
 集荷前のキャンセル: card_registered → void（課金なし）

集荷確認 pickup_confirmation（区間ごと。13.3）:
 unconfirmed ─(佐川の集荷の記録を取得)→ confirmed_auto
             ─(運営が根拠つきで確認)→ confirmed_manual ─(猶予の30分以内に取り消し)→ unconfirmed
手配 fulfillment_status: not_started → pending → in_progress → done / failed（再処理あり）
集荷の確約 pickup_commitment: none → requested(佐川へ依頼済み) → accepted(佐川の受付あり) / rejected
ホテルの受け入れ（区間の両端ごと）: pending → accepted / declined / no_response
```

v1.3 からの変更点と理由:

- **`awaiting_payment` / `confirmed`（支払い確定）を廃止し、`card_pending` / `booked`（カード登録で予約確定）に置き換えた。** 予約の確定に支払いは要らない。
- **支払いの状態を注文から区間へ移した。** 課金の合図は区間ごとの集荷なので、2区間の注文は 2回に分けて課金する（13.4・確認事項 P-02）。
- **`pickup_confirmation`（新規）**: 課金の正しさは集荷確認の正しさで決まるため、自動・手動を区別し、手動には取り消しの猶予を付ける（13.3）。
- **`ready_for_pickup`（v1 監査で追加）**: 「予約が確定した」と「集荷が確約された」を分ける。配送日数で予約できることと、実際に集荷されることは別（C 章の注意）。
- **予約確定の前後の再判定**: カード登録の作成時と、登録完了から手配の処理に入る時の 2回、同じ判定関数を通す。手配の時点で判定が通らなければ（運休日の追加など）`exception` にし、キャンセル（課金なし）の候補に出す。
- **集荷できなくなった時**: 集荷日の 18時に未集荷を検知（既存の仕組み）→ B2C は `exception` ＋旅行者へ自動の案内（状況と荷物の扱いだけ）。**課金は集荷確認が無い限り起きないので、返金の処理は不要**。振替・キャンセルは運営が営業時間内に確定（設計書 3.7）。

### 12.0 前提と、決まっていないこと

**整合の方針**:

- **B2B の表・列・計算（`agencies.unit_price_yen`・`resolveUnitPriceYen`・請求書・カード課金）は一切変えない。** B2C の料金は別の表で持つ。

- **混同を防ぐ規則**: B2B の代理店単価は「代理店が BondEx に払う卸の値」。B2C の販売価格は「旅行者が払う値」、紹介料は「BondEx がパートナー・ホテルに払う値」。表・画面・CSV で名前を分け、同じ画面に並べない。ShipAll のように両方を持つ会社でも、B2B の単価（`agencies`）と B2C の設定（`partner_price_rules`）は別の画面で扱う。

制約:

### 12.3 料金適用の優先順位

**部品ごと（価格・パートナー紹介料・ホテル紹介料）に、上の段から順に探し、最初に値がある段を使う。**

|---|---|---|
| 1 | 入口リンクの個別の設定（`entry_link`） | 特定のタブレット・キャンペーンの URL |
| 2 | ホテル・チャネルの個別の設定（`sub_referrer`） | ShipAll の導入ホテル H001、阪急のツアー |
| 3 | パートナー企業の設定（`partner`） | ShipAll 全体 |
| 4 | BondEx の標準料金（`standard`） | 全員 |

- **未設定と 0円の区別**: 未設定＝その列が NULL（下の段へ進む）。0円＝値が 0（その段で確定し、紹介料は 0円）。画面でも「上の設定を使う」と「0円」を別の選択肢にする（12.6）。
- 各段は、注文の作成時点で **`status='active'` かつ適用期間内**のものだけを見る。`draft`・`disabled` は無いのと同じ。
- **沖縄（`route_class='okinawa'`）**: 同じ順で `okinawa` の設定を探す。どの段にも無ければ標準の沖縄の価格（13,000円）を使う。**パートナーの `standard` の価格を沖縄に流用しない**（ShipAll の 4,980円が沖縄に効くと赤字になるため）。
- **ホテルの紹介料は、ホテルが特定できる注文だけ**に付く（ホテル固定の入口から来た注文）。ホテルが特定できなければ 0円ではなく「対象外」と記録する。
- **紹介元が無い注文（直接の予約）**: 標準料金を使い、紹介料は付けない。
- 実行例（ShipAll・H001 のタブレット・関西→関東・2個）:
  - 価格: 段1 なし → 段2 なし → 段3 ShipAll 4,980円（税抜） → 小計 9,960円・税 996円・課金予定 10,956円（集荷後に課金）
  - ShipAll 紹介料: 段3 の 500円 × 2個 ＝ 1,000円（1個ごとの場合）
  - ホテル紹介料: 段3 の 500円 × 2個 ＝ 1,000円、支払先 H001

### 12.4 紹介手数料の計算仕様

| 項目 | 仕様 |
|---|---|
| 固定額 | `金額 × 数量`。数量は単位（1個・1注文・1区間）で決まる |
| 料率（将来） | `計算の元 × 料率`。計算の元は**税抜の小計**を既定にする。端数は切り捨て。初期は画面で選べないようにしておき、DB と計算の関数だけ対応させる |
| 税区分 | `undecided` の間は、紹介料を**計上しても支払いの確定（承認）をしない**（設計書 12.6 の `B2C_COMMISSION_APPROVAL_ENABLED=false` と同じ考え） |
| 2つの紹介料 | ShipAll の分とホテルの分は**別の行**で台帳に載せる（`fee_type = partner / hotel`、支払先も別） |
| 上限の検証 | 紹介料の合計が税抜の小計を超える設定は保存できない |
| 計上の条件（案） | **集荷後の課金が成功し、かつ配送完了を確定した時**。未解決の返金・係争・課金失敗（未収）が無いこと。課金に失敗した注文は、回収できるまで `held`。**最終の条件は ShipAll との合意で決める（R03）** |
| キャンセル・返金 | 集荷前のキャンセル（課金なし）→ 紹介料は計上しない。集荷後の一部返金 → 返金で減った個数分を減らす（設計書 8.3 の `affected_item_count`）。紹介料の支払い後の返金・係争 → 元の行は変えず、差額の調整の行を翌月に載せる |

**BondEx の取り分の試算**（ShipAll・1個・関西→関西の例。**目安**）:

| 項目 | 金額 | 根拠 |
|---|---|---|
| 販売価格（税抜） | 4,980円 | ShipAll の協議中の条件 |
| 紹介料（ShipAll＋ホテル） | −1,000円 | 同上 |
| 佐川の契約運賃（関西宛て） | −1,890円 | `lib/sagawa-rates.ts` |
| 決済手数料 | −約200円 | 税込 5,478円 × 3.6% と仮定。**海外発行のカードの料率は Stripe の契約で要確認** |
| **差し引き** | **約 1,890円** | 人件費・事故の補償は含まない |

### 12.5 月次精算の設計

**台帳 `commission_ledger`**（設計書 12.5 をパートナー共通にする）

| 列 | 内容 |
|---|---|
| `order_id` / `fee_type`（partner / hotel） / `beneficiary_type`（partner / sub_referrer） / `beneficiary_id` | どの注文の、誰への、どちらの紹介料か |
| `entry_kind` | `accrual`（計上）／`adjustment`（調整） |
| `amount_yen` / `basis` | 金額と計算の条件（注文の控えから写す） |
| `status` | `pending` → `approved` → `paid`／`held`／`rejected` |
| `settlement_line_id` | どの精算明細に入ったか（1行は 1つの明細にしか入れない） |

**二重払いの防止**:

- `(order_id, fee_type) WHERE entry_kind='accrual'` を UNIQUE。同じ注文に ShipAll の分・ホテルの分を 2回計上できない。
- 1つの台帳の行は 1つの精算明細にしか入らない（`settlement_line_id` を一度入れたら変えない）。
- 精算の締めは支払先・月で 1件（`(beneficiary_id, period) UNIQUE`）。状態は `draft → reviewed → approved → paid`。`paid` の記録は 1回だけで、振込の記録（日付・金額・担当）と一致しなければ保存できない。
- ホテルが ShipAll 経由の紹介と、別の紹介元の両方に関わっても、ホテルの紹介料は「その注文の控えに固定した支払先」1つにしか付かない。

**パートナー別の月次画面と CSV の項目**:

| 項目 | 定義 |
|---|---|
| 注文件数 | その月に予約が確定した（カード登録が完了した）注文（件・個） |
| 配送完了件数 | その月に配送完了を確定した注文（件・個） |
| 売上 | 税抜・税込の両方（集荷後に課金が成功した額） |
| 課金失敗・未収 | 件数と金額（紹介料は回収まで保留） |
| キャンセル・返金 | 件数と金額（その月に発生した分） |
| パートナー紹介料 / ホテル紹介料 | 別の列。ホテルの分はホテルごとの内訳も |
| 支払予定額 | その月に `approved` になった行の合計（調整を含む） |
| 精算済み金額 | `paid` の合計 |

- 月の区切りは、**計上（配送完了の確定）の日**を基準にする案。課金日の基準でも出せるように、CSV には両方の日付を入れる。
- パートナー向けの CSV・画面には、旅行者の氏名・連絡先を出さない（10章 D10）。

**支払いの方法（R04）**: ホテルへの紹介料を、BondEx がホテルへ直接払うか、ShipAll にまとめて払い ShipAll からホテルへ払うかで、支払先の登録（ホテルの口座・インボイスの登録番号）と CSV の形が変わる。データは両方に対応できる形（支払先を行ごとに持つ）にしておき、決まるまでは支払いを確定しない。

### 12.6 管理画面の設計（`/operator/b2c/pricing`）

| 画面 | 内容 |
|---|---|
| 一覧 | 対象（標準・パートナー・ホテル/チャネル・入口）ごとに、今有効な版・次に有効になる版・下書きを表示 |
| 作成・編集 | 新しい版を作る形だけ（有効な版を直接書き換えない）。各項目に「上の設定を使う」「値を入れる（0円を含む）」の選択 |
| 確認 | 保存の前に、変更前→変更後の差分と、**実行例の計算**（1個・2個・沖縄、それぞれの課金予定額・紹介料・BondEx の取り分）を表示 |
| 有効化 | 下書きを有効にする操作は別のボタン。開始日時は今以降のみ（過去にさかのぼって有効にしない） |

**入力値の検証と誤設定の防止**:

- 価格は 1円以上・上限（例 100,000円）以下の整数。0円の販売価格は保存できない。
- 紹介料の合計 ≦ 税抜の小計。料率は 0〜100%。
- **警告（保存は可・確認の入力が必要）**: BondEx の取り分（販売価格−紹介料）が、その区間の佐川の契約運賃の最大を下回る／前の版から 20% 以上変わる／沖縄の価格が標準の価格を下回る。
- 適用期間が他の有効な版と重なる場合は保存できない（DB の制約と画面の両方）。
- 税区分が `undecided` の紹介料は、有効化はできるが、精算の承認ができないことを画面に明示する。
- すべての操作を `pricing_audit_log` に記録する。

## 13. B2C の決済の修正設計: 予約時にカード登録・集荷確認後に課金（2026-10-30 確定要件）

### 13.0 確定要件

- **予約時**: Stripe でカードを登録し、有効性を確認し、必要な本人認証（3Dセキュア）を済ませ、後で本人がいない時に課金すること（オフセッションの課金）への同意を取る。**売上は確定させない。**
- **集荷時**: 佐川の集荷完了を確認してから、登録済みのカードに課金し、結果を注文に反映する。
- 課金の合図は予約の確定ではなく、**実際の集荷確認**。
- ShipAll・阪急から紹介された予約も同じ流れ。パートナー別の価格・紹介料の設定（12章）は維持し、紹介料は実際の配送・課金・返金の状況を確かめてから精算する。

### 13.3 集荷確認の定義（提案）

**正式な集荷確認＝次のどちらかを、区間ごとに 1回だけ記録したもの（`b2c_pickup_confirmations`）。**

**A. 自動の確認（既定）**

1. その区間に結び付いた追跡番号で、佐川の追跡に**集荷の記録（イベント）**があり、記録の時刻が「集荷日の前日 0:00 〜 今」に入っている。
   - 状態の文字は**部分一致でなく、実際に佐川が返す語の一覧（許可リスト）と照合**する。今の部分一致（`lib/tracking/shipandco.ts:78-89`）は「集荷」を含む別の語にも反応しうるため、B2C の課金には使わない。一覧に無い語は確認にせず、運営へ知らせる。
   - 集荷の記録が無くても、輸送中・配達完了の記録があれば集荷済みとみなす（記録の時刻を集荷時刻にする）。
2. 区間がキャンセルされていない。追跡番号が他の区間と重複していない。
3. 確認を記録した後、**課金は別の処理（30分ごとの課金の処理）が行う**。追跡の同期の中で直接課金しない（追跡の遅れ・重複と課金を切り離すため）。

**B. 運営の手動の確認（例外）**

- 担当者の個人ログイン（設計書 7.1）でのみ操作できる。共有パスワードでは不可。
- 根拠の種類を選ぶ（佐川の問い合わせ画面・ドライバー・ホテルの確認）＋メモ＋確認の画面（「この操作で ◯◯円が課金されます」）。
- **確認から 30分は取り消しの猶予**。猶予の間は課金しない。取り消しは理由つきで記録する。
- 毎日、前日の手動の確認の一覧を運営に出す（誤操作の点検）。

**遅れ・重複・誤操作への備え**

| 事象 | 対応 |
|---|---|
| 追跡の更新の遅れ | 課金が遅れるだけで、誤りにはならない。配達予定日を過ぎても確認が無い区間は、運営の一覧に出す |
| 同じ集荷の記録を何度も取得 | 記録は区間ごとに 1件（UNIQUE）。取得した記録は `(区間, 取得元, 記録の内容のハッシュ)` で重複を捨てる |
| 追跡番号の入れ間違い | 確認の後・課金の前に番号が変わったら、課金の予定を止めて再確認。課金の後なら運営の確認へ（誤りなら全額返金） |
| 集荷されていないのに確認された | 判明したら確認を取り消し（課金前）、または全額返金（課金後）。理由を記録し、紹介料も取り消す |
| 追跡番号が入っていない | 確認できない。**今は番号を運営が手で入れている**ので、番号の入力が課金の遅れに直結する（T8 の重要度が上がる） |

前提: 追跡の取得は今 Ship&co 経由で 1番号 15回の上限がある（`lib/tracking/poll-policy.ts`）。佐川の追跡 API への切替（`feat/sagawa-tracking-api` 7c234a4・未反映）と、本番の自動追跡の再開（設計書 U11）の判断が、自動の確認の前提になる。

### 13.4 集荷後の課金

| 項目 | 方針 |
|---|---|
| 単位 | **区間ごと**に課金（集荷の合図が区間ごとのため）。1注文 1区間なら 1回 |
| 金額 | 注文の料金の控え（12.2 `b2c_order_pricing`）の区間分。**設定の表は読まない**（後から料金を変えても影響しない） |
| 個数の違い | 集荷した個数が少なければ、課金の前に運営が理由つきで減額。多ければ同意の上限まで（P-03） |
| 課金の記録 | `b2c_charges` に**先に行を作ってから** Stripe を呼ぶ。区間ごとに「処理中・成功」の行は 1つだけ（部分 UNIQUE） |
| 重複防止キー | `b2c_charge_<課金の行ID>`（**試行ごとに別のキー**）。DB の部分 UNIQUE が二重を防ぎ、Stripe のキーは同じ試行の送り直しを防ぐ（B2B の 24時間の弱点を持ち込まない） |
| 記録の失敗への備え | 新しい試行の前に、Stripe 側でその区間の成功した課金が無いか（metadata で検索）を確かめる |
| metadata | `kind:"b2c_charge"`・`b2c_order_id`・`shipment_id`・試行の番号。個人情報は入れない |
| 安全スイッチ | `B2C_CHARGE_LIVE`（既定 false）。B2B の `STRIPE_CHARGE_LIVE` とは別 |

**失敗した時**

| Stripe の結果 | 状態 | 旅行者への案内（メール・連携済みの WhatsApp） | 再試行 |
|---|---|---|---|
| 本人の認証が必要（`authentication_required` 等） | `action_required` | 「カード会社の確認が必要です」＋確認ページのリンク（本人がその場で 3Dセキュアを通して支払う） | 自動の再試行はしない（本人の操作が必要） |
| 拒否・残高不足など、時間で変わりうるもの | `declined` | 「お支払いができませんでした」＋別のカードで支払うリンク | 1日後・3日後に自動で再試行（P-06） |
| 盗難・紛失・不正の疑いなど、再試行しても通らないもの | `declined` | 別のカードで支払うリンク | 自動の再試行はしない |
| 期限（例: 7日）を過ぎても回収できない | `uncollectible` | 最終の案内 | 運営の未収の一覧へ。紹介料は保留 |

- **荷物の配送は止めない**（輸送中の荷物をホテルで止めると、旅行者とホテルの双方に影響が大きい）。未収の危険は BondEx が負う（P-05）。
- 案内のメール・リンクは本人確認ページ（秘密のリンク）経由。リンクにカード情報・金額の改ざんの余地は無い（金額はサーバーの控えから）。

**Webhook と定期の照合**（設計書 9.2・9.3 の考え方を維持）

- 受ける: `setup_intent.succeeded` / `setup_intent.setup_failed` / `checkout.session.completed`（setup）/ `payment_intent.succeeded` / `payment_intent.payment_failed` / `payment_intent.requires_action` / `charge.refunded` / `charge.dispute.created`。
- `b2c_stripe_events`（イベント ID が主キー）で重複を捨て、処理は Stripe の最新の状態を取り直して行う。DB に書けなければ 500 を返して再送させる（B2B の「失敗しても 200」は持ち込まない）。
- 定期の照合（5分ごと）: 集荷確認から 1時間たっても課金されていない区間、`charging` のまま 15分以上の区間、再試行の時刻が来た区間、直近 48時間の B2C の成功した課金で DB に無いもの。

### 13.5 B2B と B2C で混同しないもの

| 項目 | B2B（変えない） | B2C（新規） |
|---|---|---|
| 支払う人 | 代理店 | 旅行者（予約者） |
| Stripe の顧客 | 代理店ごと（`agencies.stripe_customer_id`） | 注文ごと（`b2c_payment_profiles.stripe_customer_id`） |
| カード | 顧客の既定のカード | 注文に固定した PaymentMethod |
| 注文の ID | `booking_id`＋区間 | `b2c_order_id`＋区間（`shipments.b2c_order_id`） |
| 金額 | `amount_yen`（税抜）× 1.1 | 料金の控え（12.2） |
| 課金の記録 | `shipments` の課金列（`charged_at` 等） | `b2c_charges`（`shipments` の課金列は使わない） |
| 失敗時 | 代理店・運営へ通知 | 旅行者へ認証・カード変更の案内、再試行、未収の一覧 |
| 課金後 | 請求書 兼 領収書を代理店へ | 領収書を旅行者へ |
| 安全スイッチ | `STRIPE_CHARGE_LIVE` | `B2C_CHARGE_LIVE` |

新規の表: `b2c_payment_profiles`（注文 UNIQUE・Stripe のアカウント・顧客・SetupIntent UNIQUE・PaymentMethod・カードの種類と下4桁と発行国・同意の版と時刻・状態）、`b2c_charges`（上記）、`b2c_pickup_confirmations`（区間 UNIQUE・自動/手動・根拠・追跡番号・記録の時刻・担当・猶予の終わり・取り消し）、`b2c_pickup_events`（取得した追跡の記録）。設計書の `b2c_payments`（Checkout の決済の記録）はこの 2表に置き換える。

### 13.6 既存 B2B と共通にできる部分

| 共通にする | 内容 |
|---|---|
| 課金の合図の 4か所 | 直接 `chargeShipmentIfDue` を呼ぶ代わりに、振り分けの関数を 1つ挟む。`channel='b2b'` → 今の `chargeShipmentIfDue` をそのまま呼ぶ（動きは変わらない）。`channel='b2c'` → 集荷確認の記録だけ（課金は B2C の課金の処理が行う） |
| 追跡の取得 | 追跡番号の照会・状態の順位（`progressionRank`）・遅延の検知は共通。B2C の集荷確認だけ、許可リストで厳しく判定する |
| 部品 | Stripe の初期化、税の計算（`lib/tax.ts`）、運営への警告（`lib/ops-alert.ts`）、課金の二重防止の考え方（条件付き更新） |

**B2B に必要な変更は 2つだけ**:

1. 課金の合図の 4か所に振り分けを入れる（B2B の動きは変えない）。
2. Stripe のアカウントを B2B と共用する場合、B2B の Webhook が B2C のイベントで 500 を返し続けないよう、`metadata.kind` が B2C のものは無視する（設計書 1.3 の P07）。アカウントを分ければ不要（P-08）。

**B2B の課金で見つかった弱点（直すかは D15 で別に判断）**: 重複防止キーが区間で固定（24時間の問題）／本人の認証が必要な時の手段が無い／運営の手動の集荷がその場で課金し、取り消しの猶予が無い／集荷の判定が部分一致。

### 13.7 予約の取り消しとカード情報

| 時点 | カードの扱い |
|---|---|
| 集荷前のキャンセル | 課金しない。PaymentMethod を外し（detach）、`b2c_payment_profiles` を `detached` にする。キャンセル料を取る場合（D12）だけ、外す前に課金する |
| 予約の期限切れ・登録の失敗 | 登録途中のものは Stripe 側で期限切れになる。顧客は保存期間（設計書 13.5）で削除 |
| 配送完了の後 | 全区間の課金が成功し、調整の可能性が無くなった時点から一定期間（案: 14日）で外す（P-07） |
| 共通 | カード番号は持たない。表示用にカードの種類・下4桁・有効期限だけ保存。共用タブレットでは、カードの入力を本人のスマートフォンへ QR で引き継ぐことを推奨（提案書 04章） |

### 13.8 パートナー別料金・紹介料との整合

- 課金額は、注文の作成時に固定した料金の控え（12.2）。後で ShipAll・阪急の設定を変えても、課金額は変わらない。
- 紹介料の計上は「**集荷後の課金が成功し、配送完了を確定**」（12.4 を修正済み）。課金に失敗して未収の注文は保留し、回収できなければ紹介料を付けない。
- 月次の精算の画面・CSV に「課金失敗・未収」の欄を足した（12.5）。

## 14. 自己レビュー（この監査の弱点）

1. **工数は 1人＋AI の補助を前提にした概算。** 既存の画面の部品をどこまで使い回せるかで大きく変わる。T3・T5 は特に幅が大きい。
2. **手作業の時間（月約 500時間）は 1件 10分の仮定から出した試算で、実測ではない。** 運営の実際の作業時間を 1週間ほど記録すると精度が上がる。
3. **本番の確認は読み取りだけで、データの件数が少ない**（直近 3か月で 30件）。月 3,000件での追跡の照会の量・Ship&co の上限・メールの送信量は試験していない。
4. **佐川の運用（集荷依頼の一括化・追跡番号の受け取り）は回答待ちで、T8 の工数は最も不確か。** 佐川の答えによっては、手作業を減らせる範囲が限られる。
5. 監査は `origin/main` を対象にした。作業中のブランチ（集荷リマインド・佐川 API の追跡・Biz-Logi・UI 刷新）は中身を前提にしていない。取り込みの順番で、T7・T8 の工数が変わる。
6. 法的な整理（取次業・特定商取引法）は確認していない（Q-L02）。
7. （12章）料金の解決を「部品ごとに上の段から探す」形にしたため、価格はパートナー、紹介料はホテルの設定、のように**段が混ざった組み合わせ**が起こりうる。画面の試算と注文の控え（どの部品がどの版か）で追えるようにしたが、運営が意図しない組み合わせに気づきにくい。
8. （12章）BondEx の取り分の試算の決済手数料（3.6%）は仮定。海外発行のカードが多いと、実際の手数料は上がる可能性がある。
9. （12章）紹介料の税区分・ホテルへの支払い（インボイス制度の影響を含む）は、税理士の確認をしていない。
10. （13章）**集荷後の課金は、荷物を預かった後に回収できない危険を BondEx が負う。** 未収の率は、旅行者の国・カードの種類で大きく変わるはずだが、実績が無いので見積もれていない。
11. （13章）佐川が実際に返す集荷の記録の語（許可リスト）は、まだ集めていない。Ship&co 経由と佐川の追跡 API で語が違う可能性がある。
12. （13章）設計書 v1.3 の矛盾は主な箇所を挙げたが、各章の細かな表現（「決済」の語）までは洗い切れていない。v1.4 の作成時に全文を見直す必要がある。
13. （15章）パートナー画面に出す項目は、ShipAll の 6番の質問（注文番号・ホテルコード・金額・キャンセル有無）を基準にした。ホテルのフロントが「どのお客様の荷物か」を見分ける手段は、パートナー画面ではなくホテル向けの通知（T7）で扱う前提で、まだ詳細を詰めていない。
14. （15章）集荷元の固定は「お客様がそのホテルに泊まっている」ことを前提にしている。チェックアウト日の入力はあるが、宿泊の事実は確かめられない（ホテルの宿泊台帳とは照合しない）。

### 15.1 ShipAll の予約は「集荷元＝設置ホテルに固定・お客様は配送先だけを選ぶ」

ShipAll のタブレットはホテルに置かれるので、お客様が荷物を預ける場所は必ずそのホテル。提案書 07章の `hotel_fixed_origin`（ホテル固定の入口リンク）を ShipAll の標準の形とする。

| 項目 | 入力する人 | 内容 |
|---|---|---|

### 16.8 D06・D12・P-01・P-06 の再検討（2026-11-02）

**Biz-Logi の仕様書（`~/JOJO/ops/vendors/sagawa/Biz-Logi API仕様書_Ver2.82.pdf`）で分かったこと**

- API は 8種類（3.1 API一覧）: 送り状発行（確認・発行依頼）／ファイル存在確認／利用実績／送り状再発行／佐川マスタ参照（郵便番号・住所の判定と担当営業所）／荷物受渡書・出荷明細書／送り状発行 MS／データ返却。**配達日数（リードタイム）を返す API と、追跡（ステータス）を返す API は無い。**
- 送り状発行の「確認機能」で、住所と郵便番号の不一致、配達指定日・時間帯の可否、**中継エリア（W2-0003「中継料金がかかる」）**を事前に判定できる（3.4.1、5.2）。離島など中継の行き先を予約時に見分けられる。
- 集荷依頼の指定日は「今日の翌日以降・30日以内」（E1-0090、E1-0091）。配達指定日も発送日から 30日以内（E1-0037）。→ 前日の締切（D03）と一致。31日以上先の予約は、送り状の発行を後に回す必要がある。
- **送り状発行の受付 ID を発番した時点で、問合番号ごとに Biz-Logi の利用料金が発生する**（2.3 課金。料金の額は「別途ご相談」で未記載）。送り状を発行した後のキャンセルは、この分が BondEx の損になる。

**D06（日数の分からない区間）の再提案**

- 日数は Biz-Logi ではなく、佐川の公開の「配達日数検索」から取っている（`sql/058_sagawa_lead_times.sql`・`lib/sagawa-lead-time.ts`）。国内の住所なら佐川は必ず日数を返すので、**佐川の側に「日数の無い区間」は無い**（たくまさんの見立てどおり）。
- 起きうるのは、当社の表に無い組み合わせを佐川のサイトへその場で照会して**失敗した時**だけ（サイトの停止・形式の変更・住所から郵便番号を引けない）。本番の表は 47都道府県・416営業所・営業所の組み合わせ 4,512件（全組み合わせの一部。足りない分はその場で照会して保存）、記録上の最大日数は 3日（2026-11-02 の読み取り）。
- 提案: 照会に失敗した時は、**安全側の日数（3日。沖縄は別の規則）で受け付け、運営に警告**を出す。中継エリア（離島など）は Biz-Logi の確認機能で見分け、画面で「通常より日数がかかる場合あり」と出す。中継エリアの実際の日数は佐川への確認事項（Q-S02・S03）。

**P-01（集荷確認）の具体化**

- 「佐川の追跡のステータスが、未集荷から集荷・輸送中・配達完了のどれかに変わったら」を集荷確認とする（たくまさんの指示どおり）。追跡は Biz-Logi には無いので、今の Ship&co 経由、または佐川の追跡 API（`7c234a4`）で取る。
- 今の B2B の弱点（部分一致の判定・手動の変更でその場で課金）を避けるため、判定に使うステータスの一覧は佐川の実際の値で作る。運営が手で集荷にした場合は、取り消しの猶予（30分）を付ける。

**P-06（後で失敗しないように）の再提案: 予約時に与信（枠の確保）を取り、集荷後に売上を確定**

- Stripe の「オーソリとキャプチャーの分離」を使う（`capture_method=manual`）。予約時にカードの枠を確保し（売上は未確定・引き落としは無い）、集荷の確認後に売上を確定する。
- Stripe の公式資料: 日本の Stripe アカウントでは、**円建ての Visa・Mastercard・JCB・Diners・Discover は最長 30日**、枠を確保しておける。American Express と円以外の取引は 7日（https://docs.stripe.com/payments/place-a-hold-on-a-payment-method 「日本における 30 日間のオーソリ期間」）。
- これで「予約時は通ったのに、集荷後に残高不足・利用停止で失敗する」はほぼ無くなる。与信が取れなければ、予約自体を受けない。
- 与信の期限内に集荷できない予約（Amex で 7日超、他で 30日超）は、予約時にカード登録だけ行い、**集荷の 7日前に与信を取る**。失敗したら旅行者に別のカードを求め、集荷の前日の締切までに直らなければ予約を取り消す（荷物を預かる前に止める）。
- 確定できる額は与信の額まで（減らすのは可）。個数が増えた場合は追加分を別に課金する。
- キャンセル料（D12）は、与信の一部だけを確定すれば取れる（`amount_to_capture`）。
- 13章の設計（予約時はカード登録だけ）からの変更になる。13章の SetupIntent は、「与信の期限を超える予約」の場合だけ使う。
- 確認が要ること: 当社の Stripe アカウントが日本のアカウントで 30日の与信の対象か、取り消した与信に手数料がかかるか（Stripe に確認）、旅行者の明細に「保留」と出ることへの案内文。

**D12（キャンセル料）の再提案**

- 抑止として取るのは妥当。ただし、消費者向けのキャンセル料は、事業者の「平均的な損害」を超える部分が無効になりうる（消費者契約法 9条）。佐川はキャンセルに料金を取らないので、損害は「送り状の発行料（Biz-Logi）・集荷依頼の手配の手間・空振りの集荷」に限られる。
- 案: 集荷の前日 17:00（締切）までは無料。締切の後のキャンセル・当日の荷物の不在（集荷の空振り）は、**1個あたりの定額（例 1,000円）**。全額（4,980円）は根拠が弱い。額と文言は、公開前に法務の確認を受ける（Q-L02 と合わせて）。
- 与信を取る方式（P-06）なら、キャンセル料は与信の一部の確定で取れて、取り損ねが無い。
