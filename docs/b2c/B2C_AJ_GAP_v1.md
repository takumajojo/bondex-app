### 1.1 未コミットの並行作業（2026-10-28 時点・作業ツリー `bondex-poc-main`）

`origin/main` には無いが、作業ツリーに**旅行者向けの集荷リマインド（WhatsApp）の実装が、未コミットで入っている**（本照合とは別の作業。中身は読んだだけで、変更していない）。

- 内容: 集荷の前日18時と当日8時（JST）に、未集荷の予約の旅行者の WhatsApp へ、承認テンプレート `bondex_pickup_reminder` で「フロントへお預けください」を送る（`lib/pickup-reminder.ts`、`app/api/cron/pickup-reminder/`、`.github/workflows/pickup-reminder-{eve,day}.yml`、`sql/054_pickup_reminder.sql`）。
- データ: `shipments` に `traveler_whatsapp`・`reminder_consent`・`reminder_sender_name`・`reminder_enabled`・`origin_check_out`・送信済みの日時を追加する。連絡先と同意は**代理店が予約時に入力する**（B2B の機能）。
- B2C・AJ との関係:
  - **当日の預け入れの案内（3章 No.15）は、このテンプレートと送信の仕組みを再利用できる可能性が高い。** ただし、B2C では同意を旅行者本人から取り（`b2c_consents`）、送る直前の確認（受け入れ確認・停止・取消）を足す必要がある。
  - B2C 行は `reminder_enabled=false`（既定）のため、この cron の対象にはならない。B2C で再利用する場合は、B2C 側の確認を通してから送る経路を別に用意し、二重送信を避ける。
  - このリマインドの前日の文面も、集荷日とチェックアウト日の違いを注記する作り（`origin_check_out`）になっており、E06 の訂正と方向が一致している。
- この作業が `origin/main` に入った後で、B2C の通知の設計（4.3）を最終化する。

**AGENTS.md** は `origin/main` に存在しない（AJ 設計 14章で読むよう指示されているもの）。リポジトリの作業ルールは `CLAUDE.md`（状態ファイルの更新ルール）と `~/JOJO/state/bondex.md` にある。

### 4.1 方針（0章・11.3）

- 「アフィリエイト: 今回は実装しない」を、**「AJ の限定導入に必要な範囲（紹介の帰属・成果の台帳・月次の精算・紹介元の管理画面）を実装する。その他の紹介元への展開は対象外」**に改める（承認が必要）。
- 商用の条件（紹介料の税区分、複数区間の数え方、帰属の競合の規則、紹介コード、返金・不正時の精算）は**設定値**で持ち、**AJ と合意するまで本番での精算を始めない**。
- 誤課金の防止（3層）と、本番操作の制約は変えない。

### 4.2 共通ガードの対象の追加（1.3・4.3・18.1）

| No. | 経路 | ガード |
|---|---|---|
| P15 | `app/api/agency/shipment/[id]`（代理店のセルフ変更）→ `amountForNewCount` | 代理店の認証で自社の行に限られるため、B2C 行には届かない。念のため `amountForNewCount` の冒頭で `guardB2BOnly` を呼ぶ |
| P16 | `app/api/operator/change-requests/[id]`（変更リクエストの承認）→ `amountForNewCount` | 同上。B2C の変更は B2C 管理画面で扱う |
| P17 | `app/api/operator/shipment/[id]/correct`（運営の訂正）→ `amountForNewCount` | 入口で `guardB2BOnly` → 409 |
| — | ダッシュボードの「この区間を課金…（集荷メールなし）」（#85） | B2C 行には出さない（呼び先は P05 と同じなので、ガードは既にかかる） |
| — | 追跡の同期による配達完了の自動検知・完了メール（#88） | B2C 行では、代理店への完了メールを送らず、`shipment_delivery_confirmations`（`source='carrier_tracking'`）を作り、旅行者への通知に振り分ける |

- `amountForNewCount` を通すことで、DB トリガー（層3）が無くても B2C の金額が上書きされないようにする（防御の重ね）。

### 4.3 旅行者への通知（10.3・3.7）

- 前日のリマインドを、**集荷当日の預け入れの案内（1回）**に置き換える。文面は「本日 ○時までに、○個の荷物を ○○ホテルのフロントへお預けください」とし、**実際の集荷日と預け入れの期限**を基準にする。送る時刻は日本時間。
- **送る直前の確認（すべて満たす場合だけ送る）**: 両ホテルの受け入れ確認が `accepted` か `accepted_standing`／注文が `exception`・`cancelled` でない／運営の停止・集荷中止（`service_incidents`）に当たらない／集荷日が今日のまま。
- 3.7 の自動通知（「手元でお持ちください」）を送った注文には、預け入れの案内を送らない。両方が届く順番の競合は、送信待ちの列の無効化で防ぐ。
- 送る経路: WhatsApp の連携と同意がある場合は WhatsApp、それ以外はメール。WhatsApp が失敗したらメールに切り替える。
- 前日のメールを続けるかは、運用判断とする（5章 A08）。

### 4.4 紹介の帰属（新しい章）

- 紹介のリンク: `/r/<partner_slug>?placement=<許可リストの値>`。自由な転送先の URL は受け付けない。リンクは公開されるもので、認証には使わない。
- 帰属の規則: 正式申込（サーバーで作成した有効な `b2c_orders`）の時点から遡って30日以内の、**最後の有効な紹介**に帰属させる。通常の広告の UTM や直接の訪問では、紹介元を消さない。ページの再読み込みやボットでは期限を更新しない。正式申込の時点で、紹介元と規則の版を注文に固定する。
- 同意: 同意の前は30日の識別子を保存しない。拒否した人には「この紹介元を申込に適用する」の選択と、公開紹介コードの入力を用意する。
- 成果: `shipment_delivery_confirmations` の有効な確定 × 成果の対象の個数 × 単価の版。キャンセル・返金・配送未完了・保留中は確定しない。確定の取り消しや部分返金は、台帳に差額の訂正を追加する（元の行は消さない）。
- 一意性: 通常の成果は `(partner_id, shipment_id, commission_type)` で一意にする（個口ごとの識別が無いため、区間単位で個数を持つ）。

## 6. 実装の順序（案）

AJ 設計 16.4「基盤の予約・決済を先に縦に通し、その予約 ID に受付後の WhatsApp と AJ の紹介・成果の精算を接続する」に合わせる。B2C v1.2 17章の段階の後ろに、AJ の段階を足す。

| 段階 | 内容 | 前提 |
|---|---|---|
| 4-1〜4-6 | B2C v1.2 のとおり（基盤・共通ガード・個人ログイン・予約と決済・管理画面・通知）。4-2 に P15〜P17 と WhatsApp の自動応答の除外を追加 | A01・A02・A05 |
| 4-7 | 紹介の帰属（リンク・同意・紹介コード・注文への固定）と成果の台帳（保留・確定・訂正） | A01・A06 |
| 4-8 | 受付後の WhatsApp の連携（一時コード・同意）、当日の預け入れの案内、確定した遅延の通知 | A04・A08 |
| 4-9 | AJ の管理画面（役割・二段階認証・越境の防止・CSV）、月次の締めと支払いの明細 | B01〜B04 は設定値のまま進められる。本番の精算は合意の後 |
| 5・6 | テスト（AJ 設計 12章の受け入れ基準を含む）、B2B の回帰、支援技術での試用 | — |
| 7・8 | B2C v1.2 19章の承認事項＋ AJ との合意を確定 → 限定公開 → 8週間の実証 | 全承認・合意 |

- 所要日数は、v1.3 の承認後に見積もる。

## 7. 自己レビュー（この照合の弱点）

1. **WhatsApp・Meta の設定の現物は見ていない。** 確認したのはコードだけで、Meta のビジネス設定・登録番号・承認済みのテンプレートの一覧は未確認。
2. **本番の環境変数は確認していない。** 特に `TRACKING_SYNC_PAUSED` は、コードの既定と本番の値が違う可能性がある（2026-10-26 に再停止した記録がある）。
3. **Stripe の権限表（4.5）は、使う API の想定から作った。** 実装で実際に呼ぶ操作を洗い出すまでは確定ではない。
4. **AJ 設計の法務・プライバシーの論点（Cookie の同意・国外の個人情報の扱い）は、設計上の扱いを決めただけ。** 適法かどうかは判断していない。
5. **範囲が大きく広がる。** AJ の段階（4-7〜4-9）を加えると、B2C の公開までの作業量が大きく増える。B2C の基盤を先に公開し、AJ を後から足す分け方もありうる（A01 で判断する）。
