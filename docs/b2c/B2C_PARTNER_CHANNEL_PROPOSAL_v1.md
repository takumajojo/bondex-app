| — | （以下 N02〜N07 は「定価の2倍」の前提の論点。13,000円の決定で N02〜N05・N07 は不要。N06 は利益の確認として残す） | | |

| N04 | 定価の2倍は税込か税抜か | 公式料金表の金額は税込の表示と考えられる（要確認）。B2C の基準が税抜になったので、「定価（税込）×2 を税込価格とする」のか「×2 を税抜として、さらに消費税を足す」のかで約1割違う | 「公式表の金額 × 2 = 税込の販売価格」（お客様に見える金額がそのまま定価の2倍で説明しやすい） |

| N08 | **締切 17:00 と公開済みの「16:00」が違う** | 公開中のガイド・LP（`app/guide/lead-time/page.tsx`、`lib/landing-messages.ts` の3か所）は「個人旅行は集荷前日 16:00」。代理店向け（B2B）も 17:00 に揃えるか | B2B も 17:00 に揃えるかを決める。揃えるならページの文言を直す（今回は直さない） |
| N09 | 17:00 締切とホテルの受け入れ確認 | v1.3 では、未提携のホテルは予約ごとにホテルへ受け入れを確認する（3.5）。16:59 の予約は、ホテルへの確認と佐川への集荷依頼が営業時間の後になる | 前日 17:00 締切は「**集荷元・配送先とも包括受け入れ済みのホテル**」に限る。それ以外は確認の時間を見込んで締切を早める（例: 2営業日前 17:00）。佐川への集荷依頼を誰が何時までに出すかを決める |
| N10 | 4つの日付の確かめ方 | 集荷元のチェックイン・チェックアウト、配送先のチェックイン・チェックアウトの関係 | 下の 00.3 の規則で確かめる |

### 00.3 4つの日付の確認規則（B07 の決定を受けて）

B2B にはすでに同じ4つの列がある（`shipments.origin_check_in`・`origin_check_out`・`from_check_in`（配送先のチェックイン）・`to_check_out`。`lib/shipments-db.ts`）。B2C も同じ意味の列を持ち、名前の対応を揃える。

| 規則 | 内容 | 外れたとき |
|---|---|---|
| R1 | 集荷元: チェックイン ≤ チェックアウト。配送先: チェックイン ≤ チェックアウト | 入力エラー |
| R2 | 集荷日は、集荷元のチェックイン日〜チェックアウト日の間 | 選べない（理由: 「ご滞在の期間外です」） |
| R3 | 到着の見込み（最も遅い日）≤ 配送先のチェックアウト日の前日（チェックアウト当日の到着は受けない） | 選べない |
| R4 | 到着がチェックイン日より前のとき、配送先ホテルがチェックイン前の預かりに応じるか（`pre_checkin_hold_ok`） | 応じないホテルなら選べない |
| R5 | 配送先のチェックインは、集荷元のチェックアウト以降（通常の旅程） | 警告のみ（間に別の宿泊がある旅程を拒まない） |
| R6 | 日付はすべて日本時間の暦日 | — |

- 最短日の初期表示（ホテルURL案 02章）は、**集荷元のチェックアウト日を集荷日の上限**として計算する。チェックアウト当日の集荷が最も多い前提で、締切（前日 17:00）を過ぎていれば「次に選べる日」を示す。

## 02. 結論: 1つの B2C 予約基盤で両社に対応できる

- **阪急交通社（案件1）と ShipAll の案A（案件2）は、どちらも「旅行者が BondEx の画面で予約し、BondEx の Stripe で払う」形で、v1.3 の B2C 予約基盤とホテルURL案の「入口リンク」でそのまま表せる。** 両社専用のシステムは作らない。
- 違いは「入口リンクの設定」と「紹介元の精算の規則」だけにする。

| 入口 | 例 | 集荷元 | 紹介元 |
|---|---|---|---|
| 公式サイトから直接 | bondex.express の予約ページ | 旅行者が選ぶ | なし |
| 紹介リンク（固定しない） | 阪急交通社の案内メール・旅程表の QR、AJ の記事 | 旅行者が選ぶ（ツアーの事前設定があれば初期値） | 阪急交通社（＋海外代理店・ツアー） |
| ホテル固定リンク | ShipAll のタブレット、BondEx が直接提携したホテルのフロント QR | **固定**（サーバーがリンクから決める） | ShipAll（＋設置ホテル）／提携ホテル |

- **ShipAll の案C（ShipAll の画面で決済し、API で BondEx に発注）は B2C ではない。** 決済の主体が ShipAll になり、BondEx から見ると「代理店が注文して BondEx が代理店に請求する」B2B と同じ形になる。これは Partner API 計画（原則1: パートナー = 既存の `agencies`）にそのまま当てはまり、ShipAll は既に `agencies` に登録済み。**案C は B2C 基盤ではなく Partner API で実現する**（将来の段階）。
- 案B（ShipAll 専用フォーム）は、案A の入口リンクに「表示の設定」（ShipAll のロゴの併記など）を足すだけで実現でき、別のフォームは作らない。

## 03. パートナー別の設定（初期仮説の表を、データの形に落とす）

| テーブル | 役割 | 新規/拡張 |
|---|---|---|
| `partners` | 紹介元の会社。`partner_type`: `media`（AJ）／`travel_agency`（阪急交通社）／`platform`（ShipAll）／`hotel`（直接提携のホテル） | v1.3 を拡張 |

| `b2c_entry_presets`（新規） | ツアーの事前設定（ホテルと日付の初期値）。**個人情報を持たない** | 新規 |

## 04. 紹介元の識別

### 04.1 MVP で保存する項目（`b2c_orders` に申込の作成時に固定）

| 項目 | MVP | 理由 |
|---|---|---|
| 紹介パートナー（`referrer_partner_id`） | 必須 | 精算・集計の単位 |
| 下位の紹介元（`sub_referrer_id`: 海外代理店・ツアー・設置ホテル） | 必須（あれば） | ShipAll のホテル還元、阪急の代理店別の把握 |
| 入口リンク（`entry_link_id`・コードの控え） | 必須 | どの QR・URL から来たか |
| 集荷元ホテル（`origin_facility_id`）・固定されたか（`origin_locked`） | 必須 | ホテル固定の検証 |
| 相手側の参照値（`partner_session_ref`: ShipAll の `sid` など） | 任意 | 相手の記録との突き合わせ用。**意味を解釈せず、文字列として保存するだけ**（長さ・文字種を制限） |
| 予約番号・金額（税込・税抜）・決済状況・キャンセル・返金額・配送完了 | 既存の列・テーブルから取る（v1.3） | 重複して持たない |

- 個人情報（氏名・メール・電話）は URL に載せない。紹介リンクは「誰が配ったか」だけを表す。

### 04.2 紹介元を失わない仕組み

- 入口リンクを開いた時点で、サーバーが「予約の下書き」（`b2c_drafts`: 下書き ID、入口リンク、紹介元、固定の集荷元、有効期限 24時間）を作り、**下書き ID を必須 Cookie（`HttpOnly`・`Secure`・`SameSite=Lax`）に入れる**。画面の移動・再読み込み・Stripe からの戻りでは、この下書きから紹介元を引く。
- 申込（`b2c_orders`）を作る時点で、下書きの紹介元を**注文に固定**する。以後の画面の移動・時間の経過で変わらない。Stripe の Checkout には注文 ID だけを渡し、戻ってきたときも注文 ID から引く。
- 下書きの期限切れ（24時間）は「紹介元なし」に戻るのではなく、**同じ入口リンクから開き直せば同じ紹介元に戻る**（リンク自体が紹介元を表すため）。
- 30日の紹介の Cookie（v1.3 12.4・同意が必要）は AJ のような記事経由の紹介のためのもので、**ホテルのタブレット（共用の端末）では使わない**（04.4）。
- 帰属の競合（ホテルURL案 B05）: 最後に開いた有効な入口リンクを優先する。

### 04.3 不正な書き換えの防止

| 脅威 | 対策 |
|---|---|
| `?ref=shipall&hotel=H001` の `hotel` を書き換えて、別ホテルの還元にする／別ホテルを集荷元にする | **ShipAll 提案の形式（ホテル ID を URL に直接載せる）は採らない。** ShipAll には設置ホテルごとに BondEx が発行した乱数のコード（`/h/<code>`）を渡す。紹介元・設置ホテル・集荷元はサーバーがコードから決める |
| コードを手で作って別の紹介元を名乗る | コードは推測できない乱数。存在しない・停止中のコードは同じ応答（ホテル名を出さない）。レート制限 |
| ShipAll の `sid` を偽る | `sid` は突き合わせの参考値で、帰属の根拠にしない |
| 予約の途中で紹介元を差し替える | 申込 API はブラウザから送られた紹介元を使わない。下書き → 注文の順にサーバーで引く |
| 自分で予約して自分の紹介手数料を作る（自己紹介・水増し） | 手数料は配送完了で確定（v1.3 12.5）。取消率・同一カードの大量予約を検知して保留 |

- ShipAll 側がリンクを自動で作りたい（端末 ID・クリックの記録を付けたい）場合は、**BondEx のコードの後ろに ShipAll の参照値を付ける**（`/h/<code>?sid=<ShipAll の値>`）。`sid` だけが ShipAll の自由な値で、帰属に影響しない。

### 04.4 ホテルのタブレット（共用の端末）の注意

- 次の客が前の客の入力を見られないよう、**無操作 3分で下書きを破棄して最初の画面に戻す**。完了画面も一定時間で消す。
- カード情報の入力は Stripe の画面で行われ、BondEx・ShipAll には残らない。それでも共用の端末でのカード入力を嫌う客のために、**画面に QR を出して「ご自分のスマートフォンで続ける」を選べる**ようにする（同じ下書きを引き継ぐ一回限りのコード。紹介元・固定の集荷元も引き継ぐ）。
- 共用の端末では 30日の紹介の Cookie・「次回のために保存」を使わない（入口リンクに `shared_device=true` を設定）。

## 05. ShipAll 固有の連携

### 05.1 注文完了後に ShipAll へ戻す

ShipAll の希望: 完了後に `…/bondex/complete?order_id=XXX&ref=H001` へ戻し、注文番号を記録したい。

| 方式 | 内容 | 判断 |
|---|---|---|
| URL に注文番号を付けて戻すだけ | ShipAll が URL の値をそのまま信じる | **不採用**。手で URL を作れば存在しない注文を記録できる |
| **署名つきの戻り** | 戻り先 URL（ShipAll と事前に登録したもの。自由な URL は受けない）に、`order_ref`（ShipAll 用の照会番号。予約番号とは別）、`hotel_code`、`status=paid`、時刻、**HMAC 署名**を付ける。ShipAll は署名を確かめてから記録する | **MVP で採用** |
| サーバー間の照会 | ShipAll が `order_ref` で BondEx に問い合わせ、状態を確かめる | 将来（Partner API の認証を使う） |

- 戻すのは**決済が Stripe で確定した後**（BondEx のサーバーが Stripe の状態を確かめた後）に表示する完了画面からだけ。Stripe からの戻りの URL の値で決済の完了を決めない（v1.3 9.2 と同じ）。
- 戻りに客が乗らなかった（画面を閉じた）場合のために、**月次の CSV を正**とし、戻りは「ShipAll の画面の即時の表示」用と位置づける。
- ShipAll 用の照会番号（例: `SA-202611-0007`）は、予約番号・確認ページの鍵にはしない（v1.3 12.7 の AJ と同じ）。

### 05.2 月次明細（CSV）

| 列 | 内容 |
|---|---|
| ShipAll 用の照会番号 | `SA-YYYYMM-NNNN` |
| ホテルコード | ShipAll 側のコード（`partner_sub_referrers.external_code`）と BondEx のホテル名 |
| 申込日・集荷日（日単位）・配送完了日 | JST |
| 個数 | 申込の個数・配送完了の個数 |
| 注文金額 | 税込・税抜 |
| 決済状況 | 決済済み／一部返金／全額返金 |
| キャンセル | 有無と理由の区分（BondEx 都合／お客様都合） |
| 返金額 | 税込 |
| 手数料の対象額 | 規則の版で決めた基準（05.4） |
| 手数料の状態 | 見込み／保留／確定／支払い済み（v1.3 12.5） |
| ShipAll の参照値 | `sid`（あれば） |

- 個人情報（氏名・連絡先・追跡番号）は載せない。
- 集計は DB の中で行う（Supabase の API の 1,000行の上限で黙って欠ける事故を避ける）。CSV は数式の注入を防ぐ。
- **MVP は運営が CSV を出力して ShipAll に送る**。ShipAll 向けの管理画面は作らない（v1.3 12.7 の `/partners` の画面は、必要になった時点で ShipAll にも開く）。

### 05.3 Webhook・API

| 機能 | 既存 | MVP | 将来 |
|---|---|---|---|
| 注文確定の自動通知 | 無し | 署名つきの戻り（05.1）で代用 | Webhook（`order.confirmed`） |
| キャンセルの自動通知 | 無し | 月次 CSV で反映 | Webhook（`order.cancelled`・`order.refunded`） |
| 発注 API（案C） | 無し（Partner API 計画のみ） | 作らない | Partner API（ShipAll は既存の代理店として利用） |
| 追跡の連携 | 無し | 作らない | Webhook（`leg.picked_up`・`leg.delivered`） |

- Webhook の形式・署名・再送は **Partner API 計画の 4-7 をそのまま使う**（B2C 用に別の仕組みを作らない）。送信待ちの箱は Partner API の `partner_events` と v1.3 の `b2c_outbox` のどちらかに寄せる（N 項目 P05）。

### 05.4 手数料・精算（ShipAll）

| 論点 | 推奨 |
|---|---|
| 計上の基準 | **配送完了で確定**（v1.3 12.5 と同じ）。注文時は「見込み」 |
| キャンセル | 配送前のキャンセル → 見込みを取消（理由つき） |
| 全額・一部返金 | 確定前: 返金した個数を対象から除く。確定・支払い後: 元の行を変えず、差額の調整の行を足す |
| 追加料金 | 手数料の対象に含めるかは契約で決める（初期値: 含めない） |
| 月末締め | 翌月第1営業日に下書き → 担当者の承認 → 明細の送付 → 手動の振込 |
| 集計 | パートナー別・設置ホテル別 |
| 支払済み・未払い | `settlement_batches`・`payouts`（v1.3） |

- ShipAll からホテルへの還元は ShipAll が計算する。BondEx は「ホテル別の手数料の対象額」までを出す（BondEx がホテルへ直接払うのではない）。
- 料率は固定しない（`partner_terms_versions` に契約後に登録）。登録まで `B2C_COMMISSION_APPROVAL_ENABLED=false`（v1.3）で確定・精算を止め、記録だけ続ける。

| 要望 | 設計 |

## 07. ホテル固定URL の共通化

- ShipAll のタブレットは「設置ホテルを集荷元に固定した入口リンク」で、ホテルURL案の `hotel_fixed_origin` と同じもの。**紹介元が ShipAll、下位の紹介元が設置ホテル**という違いだけ。
- BondEx がホテルと直接提携する場合は「紹介元 = そのホテル」で、同じ仕組みを使う。ShipAll 専用の機能は作らない。
- ShipAll のホテルコード（`H001`）と BondEx のホテルマスタ（`b2c_facilities`）の対応は、`partner_sub_referrers` に1件ずつ登録する。**対応が未登録のホテルにはリンクを発行しない**（誤配送の防止）。
- 固定の条件・入力の制限・誤予約の防止は、ホテルURL案 04.3 のとおり（URL にホテル ID を載せない・申込 API で集荷元を再検証・ホテルが対象外になったらリンクを自動で停止）。
- 設置ホテルが「ShipAll のタブレットがあるが、BondEx の受け入れ確認は未了」の場合は、ホテルの審査（v1.3 3.3）を通るまでリンクを有効にしない。

| 既存データの移行 | 不要（`channel` の既定値 `'b2b'` で既存行はそのまま） |

## 10. 同時並行の開発は可能か

### 10.1 結論

**同じ開発プロジェクトとして並行で進められる。** ただし「共通の基盤」が先、2社の設定は後で、2社の固有の作業は基盤の途中から並行できる。両社のために2つの予約システムを作るより、作業量は小さい。

### 10.2 共通の部分（両社とも使う）

ログイン不要の予約・最短日の判定エンジン・料金計算（沖縄を含む）・Stripe の決済・予約確認・佐川への手配・追跡・メール/WhatsApp・キャンセルと返金・入口リンクと紹介元の記録・下書き・紹介元別の集計の土台・運営の処理画面。

### 10.3 固有の部分

| 阪急交通社 | ShipAll |
|---|---|
| ツアーの事前設定（`b2c_entry_presets`）とツアーコードの一括取り込み | 設置ホテルの対応表（ShipAll のコード ↔ BondEx のホテルマスタ）の登録 |
| 海外代理店・ツアー単位のリンクと QR の一括発行 | 署名つきの戻り（05.1）と ShipAll との署名の鍵の共有 |
| 団体の集中への対応（ホテルの1日の上限・集荷の手配） | 共用の端末の対応（無操作で消す・自分のスマートフォンへの引き継ぎ） |
| 参考の集計（精算なし） | 精算用の月次 CSV と手数料の規則の版 |

### 10.4 依存関係と順序

| 段階 | 作業 | 依存 | 2社の並行 |
|---|---|---|---|
| S0 | 事業判断（00.2 の N 項目・P 項目）、佐川への確認、法的な整理（v1.3 U06） | — | — |
| S1 | DB の土台（v1.3 13章 + 今回の `partner_sub_referrers`・`b2c_entry_presets`・`b2c_drafts`）、判定エンジン、料金の表 | S0 の価格・締切 | 共通 |
| S2 | 予約画面・申込 API・Stripe・確認メール | S1 | 共通 |
| S3a | 紹介リンク・ツアーの事前設定・一括発行 | S1 の DB | 阪急（S2 と並行可） |
| S3b | ホテル固定リンク・対応表・戻り・共用端末 | S1 の DB | ShipAll（S2 と並行可） |
| S4 | 運営の処理画面・キャンセル/返金・追跡・WhatsApp | S2 | 共通 |
| S5 | 集計・CSV（ShipAll 精算・阪急の参考） | S2・S3 | 2社で並行 |
| S6 | 本番前の試験（テストの Stripe・テスト用のホテル・テストの佐川） | 全部 | — |

- **固有の作業（S3a・S3b）は、共通の DB の土台（S1）さえあれば、予約画面（S2）の完成を待たずに作れる。** 入口リンクの解決（コード → 紹介元・固定の集荷元）を API として先に作り、予約画面はそれを呼ぶだけにするため。
- 現在の並行作業との衝突: 未コミットの集荷リマインド（`sql/054`・`lib/pickup-reminder.ts`）、未反映の追跡の切替（`sql/055`・7c234a4）、UI 刷新（`feat/bondex-ui-unit1`）。**B2C の SQL の番号は main に入った番号の次から**（B12）。UI 刷新の共通部品が先に入るなら、B2C の画面はそれを使う。

## 13. 自己レビュー（この案の弱点）

- （2026-10-30 解消）沖縄の価格は 13,000円に決定。公式の定価をすべて上回るので赤字の可能性は低いが、契約運賃（S11）は確認しておく。税抜か税込か（N02a）と、本島内・離島の扱い（N02b）が残る。
- （2026-10-30 解消）ShipAll は「ホテルに設置する代理店」で、ShipAll 自身からの注文は基本なし（B13）。既存の `agencies` の行は使わない。
- **ツアーの事前設定は、阪急から旅程のデータが来なければ使えない。** 来ない場合、阪急の旅行者はホテル・4つの日付を自分で入れることになり、入力の負担は通常の予約と同じ。
- **前日 17:00 の締切は、運営の手作業（佐川への集荷依頼・ホテルへの確認）の時間を圧迫する。** 包括受け入れのホテルに限る条件（N09）を外すと、締切に間に合わない予約が出る。
- **共用のタブレットでの決済は、客が嫌う可能性がある。** 自分のスマートフォンへの引き継ぎ（04.4）を用意するが、利用率は試してみないと分からない。
