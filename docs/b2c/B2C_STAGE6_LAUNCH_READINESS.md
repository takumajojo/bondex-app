### 0.3 改善事項（公開は妨げない）

- My Booking の秘密のリンクが送信待ちの文面の控え（`b2c_outbox.rendered`）に平文で残る（DB を見られる人には読める）。送る時にリンクを作り直す形にする。
- 共有パスワード（v1）の運営者も B2C の予約の詳細（名前・ホテル・根拠）を見られる（メール・WhatsApp は出さない）。v2 だけにするか判断。
- 運営者のメールアドレスを許可から外しても、登録済みのパスキーは使える（辞めた人の扱いは passkey の行を消す手順にする）。
- 定期の処理の秘密の比較が定数時間ではない・入口の token の最小 16文字（発行は 22文字以上にする）・旅行者の名前がそのまま通知に入る（HTML ではないので害は小さい）。
- 回収不能も未収として数えるので、回収不能が 2件たまると新しい予約が止まったままになる（`B2C_UNPAID_MAX_COUNT` で上限を変えて再開。運用で判断）。
- 配達完了の後に予約を `completed` にしていない（表示は配送の状態で出している）。
- 佐川の正式な個数との照合は、追跡の同期が佐川のお荷物問い合わせ API の時だけ（今の本番は Ship&co。佐川の API への切替は `feat/sagawa-tracking-api`）。それまでは運営が根拠を確かめる。
- Biz-Logi の集荷依頼の状態（依頼済み・要確認）を請求の再確認の条件に入れていない（統合ブランチで足すのがよい）。
- 運営の画面は最小（検索・並べ替え・通知の照合の一括操作なし）。

### 0.4 この Stage で直したこと

1. 追跡番号の数を個数として扱っていた（佐川は複数個口でも番号 1つ）→ お荷物問い合わせ API の正式な個数（`tracking_detail[].pieceCount`）で照合。
2. 未収による停止を計画どおり「2件または合計 3万円」に（5件は誤り）。止めるのは新しい予約だけ・運営に知らせる。
3. 秘密のリンクのページで計測（GA・Vercel・HubSpot）を読み込まない（URL の token を外部に渡さない）。
4. B2B の運営の API（区間の編集・訂正・個数の是正・ホテルの変更）で B2C の区間を変えられない（409）＋ DB のトリガー。
5. B2C のチャージバックを記録し、運営に知らせる（証拠の期限）。
6. 運営のパスキーの登録のメールのコードの総当たり対策（B2・`sql/077`）。
7. メールだけの Beta: WhatsApp が無効の間は WhatsApp の通知を送らずに片付ける（全予約で失敗の知らせが出ないように）。
8. 統合の試験の DB 名を自分専用にした（他のセッションの試験と衝突させない）。
