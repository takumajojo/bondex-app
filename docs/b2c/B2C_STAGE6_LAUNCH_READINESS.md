## 1. 実機での操作の確認の計画（iPhone・Android）

**前提**: 本番相当の試験環境（3章）の URL で行う。Stripe はテストモード、通知は試験用の宛先（社内のメールアドレス・社内の WhatsApp）だけ。

| 端末 | ブラウザ | 言語 |
|---|---|---|
| iPhone（iOS 最新・1つ前） | Safari、LINE の内部ブラウザ（阪急のご案内から開く想定） | 日本語・英語 |
| Android（最新） | Chrome、LINE の内部ブラウザ | 日本語・英語 |

| No. | 操作 | 確かめること |
|---|---|---|
| 01 | 阪急の予約 URL を開く → ホテル検索 → 日付 → 個数 → 料金 | 文字の切れ・はみ出しなし、キーボードで入力欄が隠れない、料金（税込）の表示 |
| 02 | 利用規約・特商法・キャンセル規定のリンク | 開ける・戻れる・言語が合う |
| 03 | カード登録（Visa）→ 確定 | 「いまは請求されません」の表示、確定のメール |
| 04 | カード登録（3D セキュア 4000002500003155）→ 銀行のアプリに切り替わって戻る | 戻った後に結果が出る（Stage 3 の弱点の確認）、二重に登録しない |
| 05 | 未確認のホテル → 確認待ちの表示 → 運営が確認 → 確定のメール | 「まだ確定していません」の表示 |
| 06 | My Booking（メールのリンクから）→ フロント向けの案内 → 取消 | 前日 18:30 の前は取消できる、後は案内だけ |
| 07 | 運営が集荷を確認 → 30分後に請求 → 受領のメール | 額・言語 |
| 08 | 請求の失敗（本人認証が必要なカード）→ 支払のメールのリンク → 本人認証 → 支払完了 | スマホの 3D セキュアの画面、支払のページの表示 |
| 09 | 画面の回転・文字の拡大（OS の設定で 200%）・ダークモード | 崩れない |
| 10 | 通信の切断（機内モード）中にカード登録・支払 | 「二重には請求されません」の案内、復帰後の結果 |

記録: 端末・OS・ブラウザ・結果・画面の写真。不具合は Blocker／改善に分ける。

## 2. Meta の WhatsApp のテンプレート

| テンプレート | 状態 |
|---|---|
| 予約確定・確認待ち・取消・前日・当日（5種×日本語・英語） | **申請の状況はこちらから確認できない**（WhatsApp Manager の権限がこのセッションに無い）。たくまさんに WhatsApp Manager で確認をお願いする |
| 支払が必要・支払完了・返金完了（3種×日本語・英語） | 申請の文面は `docs/b2c/B2C_NOTIFICATION_TEMPLATES.md`。未申請 |

## 3. 本番相当の Supabase の試験環境での検証の計画

| 項目 | 内容 |
|---|---|
| 環境 | 本番とは別の Supabase のプロジェクト（または Pro のブランチ）。本番のデータは入れない（ダミーだけ） |
| 移行 | 本番の移行の手順と同じ順番・同じ方法（1ファイル 1トランザクション・`sql/ops/migration_lock_prefix.sql` を前置き）: 067 → 069 → 068 → 061 → 062 → 073 → 071 → 074 → 072 → 070 → 075。適用の後に `b2c_confirm_order` が 071 の版であること・権限（anon から B2C の関数を呼べない）を確かめる |
| アプリ | Vercel のプレビュー（このブランチ）を試験の Supabase と Stripe のテストモードにつなぐ。**本番の DB につながるプレビューを作らない** |
| Stripe の Webhook（本物） | テストモードの Stripe に、プレビューの `/api/b2c/stripe/webhook` を受け口として登録（B2C 専用の署名の鍵）。カード登録・請求・失敗・返金を実際に起こし、Stripe から届いた通知で DB が正しく動くこと、重複の通知（Stripe の再送）で壊れないことを確かめる |
| 定期の処理 | GitHub Actions（または手動の curl）で `/api/b2c/cron/tick` を数分おきに呼ぶ |
| 通知 | `B2C_NOTIFY_LIVE=true` にする時は、宛先を社内のアドレスだけに限る（予約の時に社内のアドレスを使う） |
| 確かめること | 本物の Webhook・本物のメール（社内宛）・実機（1章）・運営の画面（パスキーの登録とログイン）・負荷（集荷日 1日の上限の件数を同時に予約） |

**ローカルでの代わり**: 本物の Stripe の Webhook は、Stripe の CLI（`stripe listen --forward-to`）があればローカルでも受けられる。この Mac には Stripe の CLI が入っていない（入れるにはたくまさんの承認が要る）。ローカルの試験では、Stripe から取り直した本物の PaymentIntent・Charge を署名付きの通知として送って確かめた（`scripts/test-b2c/charge_e2e.ts` の C07・C08）。

## 4. 利用規約・特定商取引法の表示・キャンセル規定（公開の準備）

**現状**: `/legal/terms` は代理店向け（"you (the partner agency)"・英語だけ）。`/legal/commercial-transactions` の料金は B2B の標準価格、支払は月次の請求書の記載があり、キャンセルは「集荷完了前は無償」。B2C の予約画面の同意の文は「利用規約に同意します」だが、規約へのリンクが無い。

**旅行者向けに必要なもの**（文案は法務の確認の後に公開。下は実装が前提にしている事実）:

| 項目 | 実装の事実（根拠） |
|---|---|
| 料金 | 1個 4,980円（税抜）、沖縄と本土の間 13,000円（税抜）、消費税 10%（切り捨て）。`lib/b2c/pricing.ts` |
| 請求の時期 | 予約の時はカードを登録するだけ。佐川が集荷した後（集荷の確認から 30分後）に、実際に集荷した個数で請求。`sql/074_b2c_stage5_payments.sql` |
| 個数の違い | 予約より多い個数を預けた時は同じ 1個あたりの料金で請求（予約の時の同意の文）。少ない時は差額を返金（運営が確認）。 |
| 支払ができなかった時 | 支払のリンクで本人認証・別のカードで支払。案内は失敗の時と 1・3・7日後 |
| 取消 | 集荷の前日 18:30（日本時間）まで My Booking から無料。佐川への集荷依頼の後は取消の申請（佐川の確認の後に確定）。集荷の後は取消できない。ホテルが受けられない・確認の期限切れは BondEx が無料で取消 |
| 返金 | カードへの返金。明細の反映まで数日〜数週間 |
| 補償・責任 | 貴重品・壊れ物・現金・パスポートは対象外（予約画面・通知の案内）。補償の上限は運送会社の約款に従う（B2B の規約と同じ考え方。旅行者向けの文で確認が必要） |
| 連絡先 | support@bondex.express（`lib/contact-links.ts`）。電話は請求があれば開示（特商法のページと同じ） |
| 言語 | 日本語・英語（予約画面と同じ） |
| 個人情報 | 名前・メール・WhatsApp・ホテル・カード（Stripe が保持。当社はカード番号を持たない）。阪急交通社の紹介元のコード（HNK001）を記録 |

**作業**: (1) 旅行者向けの利用規約・キャンセル規定・特商法の表示（日本語・英語）の文案 → 法務の確認 → 公開、(2) 予約画面の同意の文に規約・キャンセル規定・特商法・プライバシーポリシーへのリンクを付ける、(3) B2B のページは変えない（別のページ `/legal/traveler/*` にする案）。

## 5. 本番の公開の手順と切り戻しの手順（案・未承認）

**前提**: 本番の DB のバックアップ、18:00〜19:30 を避ける、機能のスイッチはすべて OFF で始める。

| 手順 | 内容 | 確かめること |
|---|---|---|
| 1 | Biz-Logi の統合の移行の手順（`docs/bizlogi-b2c-integration-report-20261104.md` 6章）の手順 1〜2 に、B2C の 074 を加える（071 の後） | `b2c_confirm_order` が 071 の版、anon から B2C の関数を呼べない |
| 2 | 本番の環境変数（Vercel）: `B2C_ACCESS_TOKEN_SECRET`（32文字以上）、`B2C_SITE_URL`、`STRIPE_B2C_WEBHOOK_SECRET`、`CRON_SECRET`、メールは Resend 推奨。スイッチはすべて OFF | 値を表示しない・Git に入れない |
| 3 | アプリをデプロイ（main へのマージは別の承認） | B2B の動き（代理店の予約・運営の画面・課金）が変わらない |
| 4 | 統合の移行の手順 4〜7（072・070） | ロックが有効 |
| 5 | Stripe の本番に B2C の Webhook の受け口を登録（B2B とは別の署名の鍵） | テストの通知が届く |
| 6 | 定期の処理（`/api/b2c/cron/tick`）を数分おきに呼ぶ仕組みを作り、`B2C_SCHEDULER_ENABLED=true` | 空で回る |
| 7 | 阪急の入口の token を作り（`b2c_entry_links`）、URL を社内で確認 | 社内の予約 1件で全工程（実際の集荷は社内の荷物で） |
| 8 | `B2C_MY_BOOKING_ENABLED`・`B2C_BOOKING_ENABLED`・`B2C_NOTIFY_LIVE`・`B2C_CHARGE_LIVE` を ON | 社内の予約で確定・通知・請求 |
| 9 | 阪急に URL を渡す | 受付の上限（日ごと）を小さく始める |

**切り戻し**:
| 何を止めるか | 方法 | 影響 |
|---|---|---|
| 新しい予約だけ | `B2C_BOOKING_ENABLED=false` | 既存の予約の確認・取消・請求・回収は続く |
| 請求だけ | `B2C_CHARGE_LIVE=false` | 請求は予定のまま残り、ON に戻した時に照合して 1回ずつ処理 |
| 通知だけ | `B2C_NOTIFY_LIVE=false` | 送信待ちに残り、ON に戻した時に期限内のものだけ送る |
| B2C 全体 | 上のスイッチをすべて OFF ＋ Stripe の B2C の Webhook の受け口を無効 | B2B は影響なし |
| アプリ | Vercel の Instant Rollback（Biz-Logi の切り戻しの手順に従う） | — |
| DB | B2C の表（061・062・073・074）は消さない（スイッチで閉じる）。Biz-Logi の部分は統合の切り戻しの SQL | — |
