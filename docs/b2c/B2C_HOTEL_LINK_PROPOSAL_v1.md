## 01. 佐川急便の全国配送所要日数の調査結果

2026-10-29 に公式ページを実際に取得して確認した。「確実性」は、公式で確認／公式だが条件付き／確認できず、の3段階。**確認できない条件は推測で埋めず、01.3 の佐川への確認事項にした。**

### 01.1 結論

- **全国の所要日数を区間ごとにまとめた公式の表・API・CSV は、公開されていない。** 公開されているのは郵便番号で1件ずつ調べる検索だけ。
- したがって、所要日数は**運営が公式の検索で区間ごとに確かめて登録する**か、**佐川から法人向けにデータをもらう**かのどちらかになる（01.3 の No.01）。検索への自動のアクセスは、規約で禁止も許可もされていない（No.02）。
- **重要: 配達の時間帯指定（午前中など）は「受け取り人は個人のみ」**と公式に書かれている。ホテル（法人）宛ての時間帯指定は使えない可能性が高い（No.04）。初期は時間帯指定を出さない v1.3 の方針と合う。
- 2026-10-29 時点、佐川は**不正アクセスの影響で Web サービス（Web 集荷など）を停止中**。電話での集荷は通常どおり。BondEx の集荷依頼は運営の手作業のため直接の影響は無いが、日数検索や追跡 API への影響は別途確かめる（No.10）。

## 02. 最短お届け予定日を自動計算する判定ロジック（配送可否判定エンジン）

### 02.1 原則

| 原則 | 内容 |
|---|---|
| 1つの関数 | 通常予約・ホテル専用URL予約・見積・申込の作成・Checkout の作成・リクエストの承認で、**同じ関数 `evaluateSchedule()` を使う**（`lib/b2c/schedule.ts`）。画面は結果を表示するだけで、判定しない |
| 推測しない | 所要日数は**運営が佐川の公式の検索で確かめて登録した値だけ**を使う。未登録の区間は「予約できない（お問い合わせ）」にする。推定値で埋めない |
| 目安で判定 | お届け予定日は「目安」。予約の可否は**目安の最も遅い日**で判定する（v1.3 6.1 を維持） |
| 失敗は安全側 | 設定の欠落・祝日表の期限切れ・DB の障害のときは「予約できない」を返す（誤って受け付けない） |
| 時刻は JST | 判定はすべて日本時間。サーバー（Vercel は UTC）の時刻をそのまま日付にしない（`todayYmdJst()` と同じ考え方） |

### 02.2 入力

| 入力 | 出どころ | 備考 |
|---|---|---|
| 現在時刻 | サーバー | ブラウザの時刻は使わない |
| 集荷元ホテル | `b2c_facilities.id` | 専用URLでは**リンクから決まる**。郵便番号・都道府県・特殊地域の区分を施設の行から引く |
| 配送先ホテル | `b2c_facilities.id` | 同上 |
| 旅行者の滞在日（任意→必須） | 画面 | 集荷元のチェックアウト日、配送先のチェックイン日・チェックアウト日。STEP 3 では未入力でもよい（02.5） |
| 個数 | 画面 | 上限は U22（推奨 5個） |

### 02.3 設定データ（値はすべて運営が登録。初期値を推測で入れない）

| データ | 内容 | 新規/既存 |
|---|---|---|
| `b2c_transit_times` | 発地域 × 着地域（初期は都道府県単位）の `transit_days_min`・`transit_days_max`、前提の集荷時間帯（午前／午後）、**根拠（佐川の検索結果の日付・担当者・メモ）**、`verified_at`、有効期間 | v1.3 の `b2c_routes` を置き換え・拡張 |
| `b2c_transit_overrides` | 郵便番号の前方一致（例: 離島・遠隔地）で、日数の加算・予約不可・時間帯指定不可を上書き | 新規 |
| `b2c_calendar` | 日付の例外（`no_pickup`・`no_delivery`・`no_booking`・`peak` と加算日数、地域） | v1.3 のまま |
| `b2c_business_calendar` | BondEx の営業日・営業時間（集荷依頼の手配・ホテル確認を行える時間） | v1.3 のまま（U02） |
| `b2c_booking_rules` | 受付締切の規則（例: 集荷前日 16:00）、最短の準備日数、最大の先日付（例: 60日） | 新規（v1.3 の route の締切列を分離） |
| `b2c_facility_rules` | **ホテル別の運用条件**: フロントへの預け入れ期限（例: 10:00）、集荷できる時間帯、ホテル独自の受付締切、1日の上限個数、集荷できない曜日・日付、包括受け入れ（`standing_acceptance`）、チェックイン前の保管可否 | 新規（v1.3 の `b2c_facilities` の列を分離・拡張） |
| 祝日 | `lib/business-days.ts`（2028年まで） | 既存。**期限切れの年は予約不可にする**（02.1） |

### 02.4 判定の手順（集荷日の候補 D ごとに）

```
evaluateSchedule(now, origin, dest, stay?, items) → {
  days: [{ pickupDate, status: 'available'|'unavailable', reason?, pickupSlot, arrivalMin, arrivalMax }],
  earliest: { pickupDate, pickupSlot, arrivalMin, arrivalMax } | null,
  nextAvailableAfter(date) // 選べない日を押したときの「次に選べる日」
}
```

候補 D = 明日（JST）から `max_days_ahead` 日後まで。**当日の集荷はしない**（既存の公開ページ「当日着のサービスではありません」、Biz-Logi の集荷依頼指定日は「今日の翌日より過去」がエラー E1-0090・Page.65）。

| 順 | 判定 | 不可のときの理由コード（画面の文言に対応） |
|---|---|---|
| 1 | 発着の区間の所要日数が登録済み・有効期間内 | `route_not_supported`（この区間は Web で予約できません。お問い合わせください） |
| 2 | 両ホテルが B2C の対象（`verified`）。未確認なら「リクエスト」として扱う（v1.3 5.3） | `facility_ineligible`／`facility_unverified` |
| 3 | D が集荷できる日（佐川の集荷・BondEx の手配・**ホテル別の集荷できない日**・`no_pickup`・`no_booking`・年末年始） | `no_pickup_day` |
| 4 | 受付締切より前: `now < min(BondEx の締切(D), ホテル別の締切(D), ホテル確認に必要な時間から逆算した締切(D))` | `past_cutoff`（締切は○月○日○時でした） |
| 5 | 到着の目安: `arrivalMin = 配達できる日へ繰り下げ(D + min + 繁忙期の加算 + 特殊地域の加算)`、`arrivalMax` も同様 | — |
| 6 | 滞在日（入力済みのとき）: 集荷元のチェックイン日 ≤ D ≤ 集荷元のチェックアウト日 | `after_origin_checkout` |
| 7 | 滞在日（入力済みのとき）: `arrivalMax` ≤ 配送先のチェックアウト日の前日。`arrivalMin` < 配送先のチェックイン日なら、配送先がチェックイン前の保管を受けるときだけ可 | `arrives_after_dest_checkout`／`arrives_before_checkin` |
| 8 | 両ホテルの受け入れ確認の期限（v1.3 3.5: 集荷前営業日 15:00）に、営業時間内で間に合う（包括受け入れのホテルは確認を待たない） | `not_enough_time_for_hotel_check` |
| 9 | ホテル別の1日の上限個数を超えない | `facility_capacity` |

- **最短お届け予定日** = 可能な D のうち `arrivalMax` が最も早いもの（同じなら `arrivalMin` が早いもの → D が遅いもの＝手元に長く置ける方）。
- **推奨集荷** = その D と、ホテル別の集荷時間帯（既定は午前 9:00〜12:00。佐川の集荷依頼の時間帯コード `09` = 9:00〜12:00、Biz-Logi Page.61）。旅行者に見せるのは「集荷の時間帯」ではなく **「○月○日 ○時までにフロントへお預けください」**（v1.3 5.1 の方針）。
- 表示: `arrivalMin = arrivalMax` なら「最短お届け予定日: 11月3日（目安）」、違えば「11月3日〜4日（目安）」。
- 配達の時間帯指定は**初期は提供しない**（v1.3 5.1 を維持）。佐川は時間帯指定ができない地域がある（Biz-Logi W2-0001・Page.67）ため、提供する場合も区間ごとの判定が要る。

### 02.5 滞在日を入れる前の「最短」の意味

ご指示のフロー（STEP 1 でホテルだけ選ぶ → STEP 3 で最短を表示）では、滞在日が未入力のため、最短は「明日以降で最も早く届く日」になります。実際には、旅行者は**集荷元を出発する日**に預けることが多いため、次のどちらかを判断してください（08章 B07）。

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A（推奨） | STEP 1 に「このホテルを出発する日」（任意・未入力なら最短）を1つだけ置く | 最短がそのまま使える日になる。後の STEP でのやり直しが減る | 入力が1つ増える |
| B | ご指示どおり STEP 3 は滞在日なしで最短を出し、STEP 5 の滞在日の入力で再判定 | STEP 1 が最も軽い | 出発日より前の最短が出て、STEP 5 で日程を選び直す人が出る |

### 02.6 再計算とサーバーの最終検証

- ホテル・日程・個数の変更のたびに `POST /api/b2c/availability` を呼び、候補を引き直す（入力の確定から 300ms 待って呼ぶ・レート制限あり）。
- 決済の直前（Checkout の作成時）に、同じ関数で**もう一度判定する**。結果が変わっていたら Checkout を作らず、新しい候補を示す（v1.3 5.1 の 5a）。
- 見積（`b2c_quotes`）に、判定に使った規則の版・所要日数の行 ID・結果を保存する（後から説明できるように）。

## 03. 通常予約とホテル専用URL予約の画面遷移案

### 03.1 共通の STEP（ご指示のフローを v1.3 5.1 に統合）

| STEP | 通常予約（公式サイト） | ホテル専用URL予約 | サーバーの処理 |
|---|---|---|---|
| 0 | トップ／エリア別ページ（東京・京都・大阪を優先して導線を置く） | QR・URL `/h/<リンクコード>` → リンクを照合 | 専用URL: コードからリンク・ホテルを引く。無効なら 03.3 |
| 1 | 集荷元ホテル・配送先ホテルを検索して選ぶ（＋02.5 の案 A なら出発日） | **集荷元は固定表示**（ホテル名・住所・「このホテル専用の予約ページです」）。**変更の操作は出さない**。配送先ホテルだけを選ぶ | 施設の判定（対象外は候補に出さない・選べない） |
| 2 | 区間と受付条件の判定（画面では待ち表示のみ） | 同左 | `evaluateSchedule()` |
| 3 | 最短お届け予定日と推奨集荷を表示（初期値） | 同左（ホテル別の預け入れ期限を反映） | 同上 |
| 4 | 集荷日・お届け予定日の変更（カレンダーは選べる日だけ有効。選べない日は理由と「次に選べる日」） | 同左 | 同上（変更のたびに再計算） |
| 5 | 個数・旅行者情報・滞在日・宿泊予約名 | 同左 | 形式の検証・滞在日での再判定 |
| 6 | 料金確認（「スーツケース1個 4,980円（税込）」）→ Stripe Checkout | 同左 | **最終検証**（料金・日程・施設・専用URLの有効性・集荷元の一致）→ Checkout |
| 7 | 完了 → 確認メール・確認ページ | 同左 | 手配処理（v1.3 9.4） |

- 選べない日のカレンダー表示は、色だけでなく文字と読み上げで理由を伝える（WCAG 2.2 AA。v1.3 5.1）。
- 「対象外のホテル」は検索結果に出さない。出す場合は選べない状態で理由を示す（v1.3 3.4）。

### 03.2 ホテル専用URLの画面の違い

| 項目 | 通常予約 | ホテル専用URL |
|---|---|---|
| 集荷元 | 検索して選ぶ | 固定・変更不可・ホテル名と住所を明示 |
| 配送先 | 検索して選ぶ | 検索して選ぶ（**集荷元と同じホテルは選べない**） |
| 見出し | BondEx の標準 | 「パレスホテル東京からの手荷物配送」など（ホテル名は施設マスタの正式名。ロゴの使用は提携の合意しだい・08章 B10） |
| 別のホテルから送りたいとき | — | 「別のホテルから送る場合はこちら」→ 通常予約へ（**集荷元の固定と紹介元の扱いは 08章 B05**） |
| 言語 | 英語・日本語の切り替え | 同左（リンクごとの既定の言語を設定可） |

### 03.3 リンクが無効・停止中・存在しないとき

- 存在しない・失効・停止中は、**どれも同じ文面**（「このリンクは現在ご利用いただけません」）と、通常予約への導線だけを出す。ホテル名は出さない（無効なリンクから提携先が推測されないように）。
- 予約の途中でリンクが停止されたら、申込の作成・Checkout の作成で拒否し、同じ文面を出す（03.1 の STEP 6）。

## 04. ホテルマスタ・専用URL・予約流入元のデータ設計案

### 04.1 考え方: 「集荷元」と「紹介元」と「入口」を分ける

| 概念 | 意味 | 例 |
|---|---|---|
| 集荷元ホテル（`origin_facility_id`） | 荷物を預けるホテル。配送の事実 | パレスホテル東京 |
| 紹介元（`referrer_partner_id`） | 予約を連れてきた相手。将来の報酬の相手 | パレスホテル東京／別のホテル／旅行会社／AJ |
| 入口（`entry_link_id`） | どの URL・QR から入ったか | パレスホテル東京のフロントの QR |

- 「パレスホテル東京の QR から、パレスホテル東京を集荷元にした予約」が最初の形ですが、**旅行会社がホテルの専用URLを配る**（集荷元=ホテル、紹介元=旅行会社）・**ホテルが別のホテルを紹介する**（集荷元=別ホテル、紹介元=紹介したホテル）にも、同じ列で対応できます。
- v1.3 の AJ の紹介（12章 `partners`）を広げて、ホテル・旅行会社も `partners` の1種類にします（`partner_type`: `media` / `hotel` / `agency`）。**紹介の帰属・成果台帳の仕組みを2つ作らない**ためです。報酬の支払いは作らず、記録だけにします。

### 04.2 テーブル

**`b2c_facilities`（ホテルマスタ。v1.3 13.2 に列を追加）**

| 列 | 内容 |
|---|---|
| `id` | **正式なホテル ID**（uuid。URL には出さない） |
| `place_id` | Google の ID（UNIQUE） |
| `name_ja`・`name_en`・`address_ja`・`address_en`・`postal_code`・`prefecture` | 表示と判定に使う。郵便番号は 02 の判定に必須 |
| `remote_area_class` | 通常／遠隔地／離島（`b2c_transit_overrides` から導出、確認済みのものだけ） |
| `status` | v1.3 3.1（`verified` など） |
| `partner_id` | 提携ホテルなら `partners.id`（任意） |

**`b2c_facility_rules`（ホテル別の運用条件・新規）**: 02.3 のとおり。版と適用期間を持ち、予約には使った版を保存する。

**`partners`（v1.3 13.4 を拡張）**: `partner_type`（`media` / `hotel` / `agency`）、`facility_id`（ホテルの場合）、`agency_name`（旅行会社の場合。B2B の `agencies` とは**結び付けない**か、参照だけにする・08章 B06）。

**`b2c_entry_links`（専用URL・新規）**

| 列 | 内容 |
|---|---|
| `id` | uuid |
| `code` | URL に載る値。**推測できない乱数**（例: 12文字・英小文字と数字）。UNIQUE。連番・ホテル名を使わない |
| `link_type` | `hotel_fixed_origin`（集荷元を固定）／`referral_only`（固定しない紹介リンク。AJ と同じ） |
| `fixed_origin_facility_id` | 固定する集荷元（`hotel_fixed_origin` のとき必須）。施設が `verified` でなければ有効にできない（DB の制約とアプリの両方） |
| `partner_id` | 紹介元（集荷元のホテルと同じとは限らない） |
| `placement` | 置き場所の区分（例: `front_qr`・`room_card`・`website`）。許可リスト |
| `status` | `active` / `paused` / `revoked`。**運営だけが変更**（個人ログイン・監査ログ） |
| `valid_from`・`valid_to` | 有効期間（任意） |
| `default_language` | 既定の言語 |
| `created_by_staff_id`・`created_at`・`revoked_at`・`revoke_reason` | 監査 |

- QR を印刷した後にリンクを止めたい場合は `paused`。漏えい・誤配布は `revoked` にして新しいコードを発行する（コードは再利用しない）。

**`b2c_entry_visits`（到達の記録・新規）**: リンク、時刻、ボットの判定、**個人情報なし**（v1.3 `referral_touches` と同じ方針。統合してもよい）。ホテル別の「QR を読んだ数 → 予約数」の把握に使う。

**`b2c_orders` に追加する列（申込の作成時に固定し、以後変えない）**

| 列 | 内容 |
|---|---|
| `booking_source` | `direct`（公式サイト）／`hotel_link`（ホテル専用URL）／`referral_link`（AJ など固定しない紹介） |
| `entry_link_id`・`entry_link_code_snapshot` | 入口 |
| `origin_facility_id`・`origin_facility_name_snapshot` | 集荷元（ID と、申込時点の名称の控え） |
| `origin_locked` | 専用URLで固定されたか |
| `referrer_partner_id`・`referrer_type_snapshot` | 紹介元（v1.3 の `partner_id` を改名・統合） |
| `facility_rules_version_id` | 判定に使ったホテル別の条件の版 |
| 既存（v1.3） | 予約番号、作成日時、個数、金額の控え（税込・税抜）、`refunded_amount_yen`、状態 |

- 配送状況は `shipments`（`b2c_order_id` で結び付く）と `b2c_orders.status` から取る。

### 04.3 セキュリティ（URL の書き換え対策）

| 脅威 | 対策 |
|---|---|
| URL のホテル ID を書き換えて別のホテルを集荷元にする | **URL にホテル ID を載せない。** 載せるのは乱数のコードだけ。集荷元はサーバーがコード → リンク → 施設の順に引く |
| 画面を改造して集荷元を差し替えた申込を送る | 申込 API はブラウザから送られた集荷元を**使わない**。`entry_link_code` を受け取ってサーバーで集荷元を決め、送られた値と違えば 422。Checkout の作成・リクエストの承認でも再検証 |
| コードの総当たり | 推測できない長さ、`/h/` と照会 API のレート制限、無効なコードと停止中のコードで同じ応答 |
| 停止したリンクで予約を続ける | 申込・Checkout の作成のたびに `status='active'` と有効期間を確かめる |
| 未確認・対象外のホテルを固定にしたリンク | 有効化の条件に `verified` を課す。施設が `rejected` になったらリンクを自動で `paused`（運営へ通知） |
| リンクの変更履歴が残らない | 作成・停止・失効を `b2c_audit_log` に残す |
| 紹介元の付け替え | 紹介元は申込の作成時にサーバーが決めて固定（v1.3 12.3 と同じ）。後から変えるのは運営の訂正だけ（理由必須・監査） |

## 05. ホテル別の予約件数・売上の集計

### 05.1 集計の軸

**集荷元ホテル別**（配送の実績）と**紹介元別**（予約を連れてきた実績）を、別々に出します。同じホテルでも数字が違いうるためです。

| 指標 | 定義 |
|---|---|
| 予約件数 | `b2c_orders` のうち `status` が `confirmed` 以降（`expired`・`rejected` を除く） |
| 配送個数 | 配送完了を確定した個数（v1.3 7.3 の `shipment_delivery_confirmations.delivered_item_count`） |
| 予約個数 | 申込時の個数 |
| 売上（税込） | 決済額 − 返金額 |
| 売上（税抜） | 上の税抜換算（会計・B2B との比較はこちら。v1.3 18章「税込と税抜を混ぜない」） |
| キャンセル件数 | `status='cancelled'`（理由コード別に BondEx 都合・旅行者都合を分ける） |
| 利用推移 | 上の指標の日・週・月別（JST の日付で区切る） |
| 到達 → 予約の率 | `b2c_entry_visits` の到達数に対する予約件数（専用URL のみ） |

### 05.2 作り方

- 初期は**運営用の DB ビュー（集計用の SQL）とCSV の出力**だけ。ホテル向けの画面は作らない（ご指示どおり）。
- 集計は DB の中で行う（`group by` のビュー・関数）。**アプリで全件を取得して足し算しない**（Supabase の API は既定で 1,000 行までしか返さず、黙って欠ける。既存のダッシュボードで実際に起きた事故）。
- 名称は申込時の控え（`origin_facility_name_snapshot`）で表示する。施設の名称を後で直しても、過去の集計の分類は ID で保たれる。
- テストの予約（`is_test`）は除外する。
- 将来の報酬（レベニューシェア）は、v1.3 の成果台帳（`commission_ledger`）に `partner_type='hotel'` の規則の版を足せば計算できる。**今回は台帳に書かない**（記録だけ）。

## 08. 未確定事項と、事業判断が必要な項目

| No. | 事項 | なぜ判断が要るか | 推奨 |
|---|---|---|---|
