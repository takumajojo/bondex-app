# Codex による設計監査（2026-11-03）

対象: `docs/b2c/B2C_PHASE1A_BETA_PLAN.md`、`docs/b2c/B2C_MVP_SCHEMA_v1.md`（v1.2）。たくまさんが会話に貼り付けたものの要旨。資料だけの監査で、コード・テストは未確認とのこと。

判定: 限定 Beta の開発は条件付きで進められる。本番公開は下の修正と検証の後。

## 実装前に直す 7点
1. 決済案 A と DB の状態が不一致（B 向けの pending_hold→held→captured が中心）。登録の状態と請求の状態を分け、請求待ち・処理中・本人認証待ち・成功・失敗・返金に統一。「枠」がカードか配送かを明確に。
2. 「試行ごとに連番」のキーでは二重請求を防げない（Stripe 成功・DB 記録失敗の後の再試行）。区間の基本料金の請求レコードを一意にし、既存の PaymentIntent を照合してから再試行。追加料金は別の ID。Stripe の重複防止キーは 24時間で消えうるので DB で永続的に防ぐ。
3. 確認済みのホテルでも、受付の締切（前日 17:00）とホテル連絡の期限（2営業日前）が矛盾。未確認のホテルの期限もスキーマ（前日 17:00）と計画（2営業日前 17:00）で不一致。出発・到着の両方を判定。
4. 予約の確定条件と、配送の手配の開始の時点が不足。取消後のカード登録成功の通知で復活させない。Webhook の署名・重複・順序の逆転に対応。
5. B2B との分離が課金の 4か所だけでは不足。shipments を共有するので、B2B の一覧・CSV・追跡・更新 API から B2C の行が見えない・変えられないことを検証。運営の個人ログインを後回しにするなら、現行の認証と権限を明記（手入力の名前は本人の証明にならない）。
6. 取消・変更・返金を配送と請求に反映する仕様が不足（再同意・ホテルへの再連絡・集荷依頼の取消・返金額と返金 ID）。30分の取り消しの猶予は、請求の予定時刻と状態を保存して競合を防ぐ。
7. 停止スイッチが既存客の確認ページまで止める。新規受付・既存予約の閲覧と取消・請求の実行を分けて制御し、停止中の請求を再開後に重複なく処理。

## 追加で詰める点
阪急 URL（紹介元コードと秘密の入口トークンを分ける）／DB 制約（予約番号の一意・外部キー・1予約1区間・金額と個数）／料金と荷物の条件（沖縄の税区分・サイズ・重量・受付不可品）／WhatsApp の送信手段と失敗時／Beta の 1日の受付上限・未収の上限・担当者不在時。
