## 1. 営業ダッシュボード（10 指標）

### 置き場所
**HubSpot ではなく BondEx の Next.js に作ります。** 無料プランではカスタム項目での絞り込みも
複数オブジェクト横断レポートも作れないため、HubSpot 側では 10 指標が実現できません。

```
URL: /sales           （既存の middleware.ts の認証で保護。新しい認証は作らない）
データ: Supabase の sales_* テーブル（サーバーコンポーネントから service_role で読む）
各行から HubSpot の該当会社ページへワンクリックで飛べるようにする
```

### 画面構成

**上段: 数字が並ぶ帯（一目で分かる 6 つ）**

| # | 指標 | 定義 | 出典 |
| --- | --- | --- | --- |
| 1 | 返信率 | 初回メール送信済み社数のうち、返信ありに到達した割合 | `stage >= replied` / `stage >= first_email_sent` |
| 6 | 契約社数 | ステージが 契約 以上 | `stage in (contract, shipping_started, repeat, upsell)` |
| 7 | 送客開始社数 | ステージが 送客開始 以上 | `stage in (shipping_started, repeat, upsell)` |
| — | Hotリード数 | 温度が hot / champion | `temperature in (hot, champion)` |
| — | 今週MTG件数 | 今週(JST 月〜日)の商談予定・実施 | `sales_event` の calendar / fathom |
| — | 承認待ち | 人の判断を待っている AI 提案の件数 | `sales_change_set.status='planned'` |

**中段: 今日やるべき会社 TOP10（この画面の主役）**

優先度スコアで並べ替えます。**AI ではなく計算式**で出します（毎日ブレないため）。
```
score =  温度係数 (champion 5 / hot 4 / warm 2 / cold 1 / lost 0)
       × ステージ係数 (poc系 3 / mtg系 2.5 / 返信あり 2 / 送信済 1)
       × 鮮度係数 (最終接触から 0-2日 1.5 / 3-7日 1.2 / 8-14日 1.0 / 15日〜 0.6)
       × 停滞ペナルティ (ステージが14日以上動いていない → 1.4 で加点。放置の警告)
       + 期限係数 (今日/明日が期限の Task がある → +10)
```
各行に「なぜ今日やるべきか」を1行で表示します（例: `返信から3日経過。日程候補を返していない`）。

**下段: 5 つのリスト（タブ切替）**

| # | タブ | 中身 |
| --- | --- | --- |
| 2 | 返信待ち | 送信済みで未返信。**経過日数の長い順**。7日超は赤 |
| 3 | Hotリード | 温度 hot / champion の全社。次回アクションと期限つき |
| 4 | 今週MTG | 曜日別。Fathom 録画へのリンク付き（実施済みのもの） |
| 5 | PoC一覧 | PoC調整 / PoC開始 / PoC成功 の全社。対象旅程・開始日・結果 |
| 8 | 失注理由 | 失注社の理由を分類集計（価格 / タイミング / 競合 / 反応なし / その他） |

**個社ページ: `/sales/[companyId]`（9 会社ごとの営業履歴）**

時系列で全イベントを1本のタイムラインに並べます。
```
2026-08-27 16:42  📨 受信  「8/31の週で調整可能」          → ステージ: 返信あり → MTG調整中
2026-08-27 09:15  📤 送信  BondEx ご提案                    (返信まで 7時間27分)
2026-08-26 14:00  🎥 商談  Fathom 要約あり ▶               → ステージ: MTG確定 → MTG実施
2026-08-22 10:03  📤 送信  初回営業メール                   → ステージ: 開始前 → 初回メール送信
```
Gmail / Fathom / HubSpot の該当箇所へ全行からリンクします。

## 2. 毎朝 9 時の営業レポート

### 配信
- 生成: 08:55 JST（9 時ちょうどに届くよう逆算）
- 配信先: `taniguchi@jojo-tokyo.com` へメール（既存の `[JOJO-CRAWL] daily` と同じ作法）
- 件名: `[BONDEX-SALES] 2026-08-28 朝の営業レポート`
- 同じ内容を `/sales` の上部にも表示（メールを開かなくても見られる）

> 配信先は谷口さんご本人のみです。社外・他の宛先には送りません。

### 本文フォーマット（ご指示の例に沿う）

```
おはようございます。

■ いまの状況
  Hot        7社
  今週MTG    4件
  返信待ち  12社（うち7日超が3社）
  承認待ち   2件 ← あなたの判断が必要です

■ 今日やるべきこと
  1. HIS（安藤様）
     返信あり・日程調整中。候補日を出してから2日経過、まだ確定していません。
     → 今日中に候補を再送するか、電話で確定させる

  2. TriX
     PoC対象の旅程を待っています（期限 10/1、あと35日）。
     前回催促から8日。そろそろ状況確認のタイミングです。

  3. Rising Destinations（ドゥシヤント様）
     契約準備。先方から返信あり後、こちらのアクションが止まっています。

■ 昨日 AI が更新した内容（5件）
  ・A Touch of Japan  返信あり → MTG調整中   (根拠: 8/27 のメール「8月31日の週で調整可能」)
  ・…

■ あなたの判断が必要です（2件）
  ・Toptour Europe を「失注」にする提案
    根拠: 8/12 の返信「今回は見送らせていただきます」／以後3週間音信なし
    [承認] [却下]  ← /sales から1クリック

■ 気づき
  返信率は先週 34% → 今週 41%。DMC 向けの方が Travel Agency より 2 倍返信が良いです。
```

### 「気づき」の作り方
A4 エージェントには**数字を計算させません**。集計済みの数値を渡し、
「この数値から営業担当が気づくべきことを 1〜3 個」だけ書かせます。
AI に算数をさせないのが、レポートを信頼できるものにするコツです。

## 3. 成果物9「実装コード」の方針

Phase 4 で書きますが、方針をここで確定します。

### 言語・基盤
既存 BondEx と同じ **TypeScript / Next.js / Supabase**。新しい言語もフレームワークも入れません。

### 実行基盤の選択（要ご判断）

| 案 | 内容 | 費用 | 判定 |
| --- | --- | --- | --- |
| A. Mac の launchd | 既存 `jojo-daily-report` と同じ | 0円 | ❌ **Mac が寝ていると営業メールを取りこぼす** |
| B. GitHub Actions | 既存 `jojo-aio-pipeline` と同じ | 0円（下記の計算に注意） | ✅ **推奨** |
| C. Supabase Edge Functions + pg_cron | Supabase 内で完結 | 0円 | ○ Bが使えない場合 |

> **B の無料枠の実測**: プライベートリポジトリの GitHub Actions は月 2,000 分まで無料。
> 20 分間隔・営業時間（08:00–24:00 JST）で 1 日 48 回、1 回あたり約 40 秒 → **月 約 960 分**。
> 無料枠の半分で収まります。**15 分間隔にすると月 1,280 分**でこれも収まりますが、
> 余裕を見て **20 分間隔を推奨**します（メール返信の検知が最大 20 分遅れるだけで実害はありません）。

### CLI の作法（既存 crm-sync と完全に揃える）
```bash
npx tsx scripts/sales-os/cli.ts collect            # 取り込みのみ。HubSpotに触らない
npx tsx scripts/sales-os/cli.ts think              # AI判断 → change_set作成。HubSpotに触らない
npx tsx scripts/sales-os/cli.ts apply              # ★DRY RUN（既定）。差分レポートを出して終わり
npx tsx scripts/sales-os/cli.ts apply --apply      # 実際に書き込む
npx tsx scripts/sales-os/cli.ts apply --batch <id> # 特定バッチだけ反映
npx tsx scripts/sales-os/cli.ts report             # 朝レポート生成（--send で送信）
npx tsx scripts/sales-os/cli.ts replay --from <日付> # 過去イベントでAIの精度を再検証（書き込まない）
```
**`--apply` を付けない限り、HubSpot へは 1 バイトも送信されません。** 既存 crm-sync と同じ思想です。

## 6. この設計の弱点（自己レビュー）

正直に書きます。

1. **無料プランの制約が設計を歪めている。**
   カスタム項目 10 個という制限のため、本来なら HubSpot 上で絞り込めるはずの「課題」「競合」
   「決裁者」がテキストの中に埋もれます。HubSpot 画面で「競合ありの会社だけ見る」ができません。
   ダッシュボードで代替しますが、**HubSpot 単体では機能が落ちる**のは事実です。
   → 将来 Starter($20/月程度) にすると項目 1,000 個・Workflow 利用可になり、この歪みは消えます。

2. **Gmail の絞り込み精度が未知数。** 設計では 4 段構えで守っていますが、
   実測はこれからです（Phase 3-4）。的中率が低ければ、`pending` 判定を増やして
   「AI が迷ったら人に聞く」方向に倒すことになり、**「人は何もしない」の理想からは後退します。**

3. **Fathom の自動取得ができない可能性がある。** これが確定すると、会議後だけは
   人の操作が1回入ります。要件「人間が CRM を更新しない」に対する最大の穴です。

4. **AI の判断品質を評価する仕組みが弱い。** `--replay` で再検証できる設計にはしましたが、
   「正解データ」が無いため、精度は谷口さんの目視に依存します。運用開始後 1 ヶ月で
   誤判定を集め、評価セットを作る作業が別途必要です。

5. **担当者が谷口さん1人である前提の設計。** 営業が複数人になると、
   「誰の Gmail を見るか」「Task を誰に割り当てるか」で作り直しが要ります。
   Owner の扱いだけは複数人を想定した作りにしておきます。
