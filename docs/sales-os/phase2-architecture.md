## 0. Phase 1 の回答を受けた「設計の前提が変わった点」

谷口さんの回答「**HubSpot は無料プラン**」により、当初想定の一部が成立しなくなりました。
ここを曖昧にしたまま作ると後で全部やり直しになるため、最初に明記します。

| 当初の想定 | 無料プランの現実 | 本設計の対応 |
| --- | --- | --- |
| HubSpot Workflow で自動化する | **Workflow は有料プラン専用。無料では使えない** | Workflow を使わない。自前の AI エージェントが唯一の書き手になる（成果物4を再定義） |
| 必要なだけカスタム項目を作る | **カスタム項目はアカウント全体で 10 個まで**。しかも**すでに 10 / 10 使用済み** | 未使用の 9 個を整理して枠を空け、8 個だけ新設。残りは Note と Supabase に持たせる（成果物3） |
| HubSpot のダッシュボードで10種の指標を見る | 無料は**既製レポートのみ**。カスタム項目での絞り込み・複数オブジェクト横断レポートは不可 | ダッシュボードは BondEx の Next.js 側に自前で作る |
| 取引パイプラインでステージ管理 | 無料は 1 パイプラインのみ | もともと谷口さんの指示どおり **Company がステージを持つ**ので影響なし |

> 出典: HubSpot Product and Services Catalog / Technical Limits（Free tools: "10 custom properties in total"、
> 有料: "1,000 custom properties per object"）。
> **お願い**: 設定 → プロパティ の画面に「10個中10個使用」の表示が出るはずです。Phase 3 の前に目視確認をお願いします。

### これは悪いニュースではありません
無料プランで Workflow が使えないことは、むしろ**設計をきれいにします**。
HubSpot の Workflow と自前 AI の両方が CRM を書き換えると「どっちが書いたか分からない」状態になり、
デバッグ不能になります。**書き手を AI エージェント 1 つに固定できる**のは、保守性の面で純粋な利点です。

## 1. 全体像

```
   [ 営業担当者がやること = メール / Google Meet / 電話 のみ ]
                    │
   ┌────────────────┼────────────────┬──────────────────┐
   │                │                │                  │
 Gmail          Google Calendar    Fathom           WhatsApp (将来)
   │                │                │                  │
   └────────────────┴────────────────┴──────────────────┘
                    │  ① 取り込み層 (Collectors)
                    │     生イベントを正規化して1つの形に
                    ▼
         ┌──────────────────────────┐
         │  Supabase: sales_event   │  ← 全イベントの台帳(不変・追記のみ)
         └──────────────────────────┘
                    │  ② 判断層 (Claude Agents)
                    │     Triage → Extract → Decide
                    ▼
         ┌──────────────────────────┐
         │  Supabase: change_set    │  ← 「HubSpotをこう変える」提案
         │  (status: planned/       │     DRY RUN はここで止まる
         │   applied/rejected)      │
         └──────────────────────────┘
                    │  ③ 反映層 (Applier) ※--apply 明示時のみ
                    ▼
         ┌──────────────────────────┐        ┌─────────────────────┐
         │  HubSpot (人が見る場所)   │        │ 自前ダッシュボード    │
         │  Company/Contact/        │◀──────▶│ /sales (Next.js)     │
         │  Note/Task/Meeting       │        │ 10指標 + 朝レポート   │
         └──────────────────────────┘        └─────────────────────┘
```

### 3つの層の役割分担（ここが設計の背骨）

| 層 | 責任 | 壊れたときの影響 |
| --- | --- | --- |
| **取り込み層** | 外部サービスの生データを `sales_event` に入れるだけ。**判断しない** | 取りこぼしのみ。CRM は汚れない |
| **判断層** | イベントを読んで `change_set` を作るだけ。**HubSpot に触らない** | 誤判断が提案として残るだけ。CRM は汚れない |
| **反映層** | `change_set` を HubSpot に書くだけ。**判断しない** | ここだけが CRM を汚しうる。だから最も薄く、最も厳しく作る |

**AI が直接 HubSpot API を叩くことは絶対にありません。** AI の出力は必ず `change_set` という
検証可能なデータ構造を経由します。これが「本番反映前に必ず DRY RUN」「変更前後の差分レポート」という
絶対条件を、運用ルールではなく**アーキテクチャとして**満たす仕組みです。

## 2. なぜ Supabase を挟むのか（HubSpot 直書きにしない理由）

BondEx はすでに Supabase を使っており（`sql/001〜023`）、追加コストはゼロです。挟む理由は4つ。

1. **無料プランのカスタム項目 10 個制限を回避する。** 課題・価格感・競合・導入時期・決裁者・リスク・
   返信速度…をすべて HubSpot の項目にすることは物理的に不可能。構造化データは Supabase が持ち、
   HubSpot には「人が読む形」で書きます。
2. **冪等性（同じイベントを二度処理しない）。** 現行 crm-sync はローカルの JSON 台帳で重複防止して
   いますが、Mac を変えると効かなくなります。Supabase なら台帳が永続します。
3. **ダッシュボードが速い。** 10 指標を毎回 HubSpot API から集計すると、無料プランの
   レート制限（100 req/10秒）にすぐ当たります。
4. **AI の判断履歴が残る。** 「なぜ Hot と判定したか」を後から検証できます。誤判定の修正は
   プロンプト修正に直結します。

## 3. 営業ステージの定義（Company が持つ）

谷口さんのフローをそのまま 15 段階にします。**内部値は変えず、表示名だけ日本語**にします。

| # | 内部値 | 表示 | この状態の意味 | 温度感の既定 |
| --- | --- | --- | --- | --- |
| 00 | `not_started` | 開始前 | 対象として登録済み。まだ接触していない | Cold |
| 01 | `first_email_sent` | 初回メール送信 | こちらから送った。返信待ち | Cold |
| 02 | `replied` | 返信あり | 相手から返信が来た（内容は問わない） | Warm |
| 03 | `meeting_scheduling` | MTG調整中 | 「話したい」の意思あり。日程未確定 | Warm |
| 04 | `meeting_booked` | MTG確定 | 日時が決まった | Hot |
| 05 | `meeting_done` | MTG実施 | 商談が終わった | Hot |
| 06 | `poc_arranging` | PoC調整 | トライアル合意。対象案件を待っている | Hot |
| 07 | `poc_running` | PoC開始 | 実際に荷物を運んでいる | Hot |
| 08 | `poc_success` | PoC成功 | トライアルが成功した | Champion |
| 09 | `contract` | 契約 | 契約締結 | Contract |
| 10 | `shipping_started` | 送客開始 | 本番の送客が始まった | Contract |
| 11 | `repeat` | 継続利用 | 2回目以降の利用がある | Contract |
| 12 | `upsell` | アップセル | 追加提案中 / 拡大中 | Contract |
| 90 | `dormant` | 休眠 | 一定期間まったく動きがない | Cold |
| 99 | `lost` | 失注 | 断られた / 立ち消え確定 | Lost |

### ステージ遷移の安全ルール（誤爆を防ぐ核心）

| ルール | 内容 | 理由 |
| --- | --- | --- |
| **R1 前進のみ自動** | 番号が上がる遷移だけ AI が自動適用する | 「ありがとうございます」の一言で MTG確定 → 返信あり に戻る事故を防ぐ |
| **R2 後退は提案止まり** | 番号が下がる遷移は `change_set` に積むだけ。朝レポートで承認を求める | 後退は必ず人の判断が要る |
| **R3 失注は自動化しない** | 明確な断り文言を検知しても、提案止まり | 失注の確定は経営判断。AI がやることではない |
| **R4 休眠だけは例外的に自動** | 最終接触から N 日（既定 45 日）動きなし → 自動で休眠。動いたら自動で復帰 | 時間ルールなので誤判定しない。かつ可逆 |
| **R5 確信度 0.80 未満は適用しない** | AI が自信のない判断は提案止まり | 曖昧なメールで動かない |
| **R6 一度に 2 段階以上飛ばさない** | 例外: MTG確定 → MTG実施 は Fathom の録画という物証があるので飛ばしを許可 | 物証のない飛躍を防ぐ |

## 4. 成果物4「Workflow 設計」の再定義

**HubSpot Workflow は無料プランに存在しないため、HubSpot 上には 1 本も作りません。**
代わりに、同じ役割を果たす**自前のジョブ定義**を設計します。実体は cron で回る TypeScript です。

| ジョブ名 | 実行間隔 | やること | 書き込み |
| --- | --- | --- | --- |
| `collect:gmail` | 15 分ごと (08:00–22:00 JST) | Gmail の新着/新送信を `sales_event` へ | Supabase のみ |
| `collect:calendar` | 30 分ごと | Google Calendar の BondEx 商談予定を `sales_event` へ | Supabase のみ |
| `collect:fathom` | 30 分ごと | 新しい録画の要約・アクションアイテムを `sales_event` へ | Supabase のみ |
| `think` | 15 分ごと（collect の直後） | 未処理イベントを AI が判断し `change_set` を作る | Supabase のみ |
| `apply` | 15 分ごと | 自動適用可の `change_set` を HubSpot へ反映 | **HubSpot（唯一の書き手）** |
| `stage:dormant` | 毎日 08:30 JST | 休眠判定（R4） | Supabase → change_set |
| `report:morning` | 毎日 09:00 JST | 朝の営業レポート生成・自分宛メール送信 | 送信のみ |
| `reconcile` | 毎日 03:00 JST | HubSpot と Supabase の突き合わせ。ズレを検出 | 検出のみ（自動修正しない） |

実行基盤は 2 案あります（Phase 3 で決定）:

| 案 | 長所 | 短所 | 推奨 |
| --- | --- | --- | --- |
| A. Mac の launchd | 既存 `jojo-daily-report` と同じ。追加費用ゼロ | **Mac が寝ていると動かない**。営業メールは日中来るので実害あり | △ |
| B. GitHub Actions | 既存 `jojo-aio-pipeline` と同じ。24 時間動く。無料枠内 | シークレット管理が増える | **◎ こちらを推奨** |

> 谷口さんの「長時間ジョブは 08:00 JST 前に完了」ルールに合わせ、
> 夜間の重い処理（`reconcile`）は 03:00 JST 開始・想定 5 分で完了します。

## 5. 成果物6「Gmail 同期」— 最重要パート

### 解くべき問題
受信トレイは 97,568 通・未読 50,395 通。BondEx の営業スレッドは `BondEx` ラベルで 6 スレッドのみ。
**「Gmail を監視して返信が来たらステージを進める」を素直に作ると、メルマガや他事業のメールで誤爆します。**

### 4 段構えの絞り込み

```
 全メール (約 800通/日)
   ↓ 【第0段】機械的除外  ← AI を使わない。コストゼロ
 候補 (約 20通/日)
   ↓ 【第1段】対象判定    ← Haiku。安い
 営業スレッド (約 5通/日)
   ↓ 【第2段】抽出・判断  ← Sonnet。ここだけ賢いモデル
 change_set
```

**第0段: 機械的除外（AI 不使用）**

| 除外条件 | 具体例 |
| --- | --- |
| 送信者が `noreply@` / `no-reply@` / `notifications@` | GitHub, Square, Booking.com |
| ヘッダに `List-Unsubscribe` または `Precedence: bulk` | メルマガ全般 |
| 除外ドメインリストに一致 | udemy.com, curama.jp, aeris.net, squareup.com … |
| 他事業の識別子を含む | jojotokyo.com フォーム通知, `[JOJO-CRAWL]`, nami, JOJO Nail |
| 自動返信 (`Auto-Submitted` ヘッダ) | 不在通知 |
| すでに処理済み (`gmail_message_id` が台帳にある) | 再処理防止 |

**第0段: 積極的採用（この2つのどちらかを満たすものだけ通す）**

1. **相手ドメインが営業対象リストにある** — `sales_target_domain` テーブル（HubSpot の
   営業対象会社から自動同期）
2. **自分が送った BondEx 営業メールのスレッド** — `SENT` かつ本文に BondEx 営業文の
   特徴（`BondEx` / `手荷物配送` / `luggage delivery` / 営業署名）を含む

> **2 が肝です。** 新規開拓では相手ドメインは未知です。「谷口さんが BondEx の営業メールを送った」
> 瞬間にそのドメインが営業対象リストに自動追加され、以後その相手からの返信が拾えるようになります。
> **対象リストが自分で育つ**ので、手でメンテする必要がありません。
> これが「人間が CRM を更新しない」を成立させる仕掛けです。

**第1段: Triage（Haiku 4.5）**
「これは BondEx の法人営業のやり取りか？ yes/no + 確信度」だけを聞きます。1 通あたり数円未満。

**第2段: Extract & Decide（Sonnet 5）**
スレッド全体（最大直近 10 通）を読ませ、後述の構造化 JSON を返させます。

### 抽出する項目（ご指示の 9 項目 + 3）

| 項目 | 型 | 保存先 |
| --- | --- | --- |
| 現在の課題 | text | Supabase + HubSpot AI要約欄 |
| 価格感 | text | Supabase + HubSpot AI要約欄 |
| 競合 | text[] | Supabase + HubSpot AI要約欄 |
| 導入時期 | text | Supabase + HubSpot AI要約欄 |
| 決裁者 | text | Supabase + HubSpot AI要約欄 |
| 次回アクション | text + 期限 + 担当 | **HubSpot Task** |
| 温度感 | enum(6) | **HubSpot 専用項目** |
| リスク | text | Supabase + HubSpot AI要約欄 |
| AI要約 | text | **HubSpot Note** |
| 提案ステージ | enum(15) | **HubSpot 専用項目** |
| 確信度 | 0.0–1.0 | Supabase（適用可否の判定に使う） |
| 判断根拠 | text（引用付き） | Supabase（誤判定の検証用） |

### 返信速度の計測（AI 不使用・完全に機械的）
`SENT` の送信時刻と、同スレッドの相手からの次の受信時刻の差を秒で記録します。
会社ごとに中央値を取り、`fast(<6h) / normal(<24h) / slow(<72h) / cold(>72h)` に分類。
これは計算なので AI に判断させません。ブレません。

### スレッドと会社の紐付け
1. 相手のメールドメイン → `sales_target_domain` → Company ID（**最優先。社名一致より確実**）
2. 見つからなければ HubSpot Contact のメールアドレス完全一致 → 関連 Company
3. それでも見つからなければ **新規作成せず**「未紐付けイベント」として朝レポートに出す

> Phase 1 で `name` が空で `domain` だけの会社（`his-world.com` 等）が実在したため、
> **社名ではなくドメインを主キーにします**。

## 6. 成果物7「Fathom 同期」

### 2 系統に分ける（重要）
Phase 1 で判明したとおり、この環境の Fathom は**対話ログイン型の MCP** です。
cron の無人実行では使えない可能性が高いため、二層に分けます。

| 用途 | 使うもの | 備考 |
| --- | --- | --- |
| **自動処理（cron）** | **Fathom REST API または Webhook** | ★ API キーの取得が必要。**Phase 3 のブロッカー候補** |
| 谷口さんが対話で調べるとき | Fathom MCP | 既に動作確認済み |

Fathom が Webhook に対応していれば「会議終了 → 即座に処理」が可能です。
非対応なら 30 分ポーリングにします（体感差はほぼありません）。

### 処理フロー
```
録画完了
  ↓ recording_id / 参加者メール / 要約 / アクションアイテム / 文字起こし を取得
  ↓ 参加者のメールドメイン → 会社を特定（メールと同じロジック）
  ↓ Sonnet 5 に要約+文字起こしを渡し、以下9項目を生成
  ↓
  ├→ HubSpot Meeting を作成（実施日時・タイトル・Fathom URL・参加者を関連付け）
  ├→ HubSpot Note を作成（下記フォーマット）
  ├→ HubSpot Task を作成（Fathom のアクションアイテム + AI の推奨フォロー）
  └→ ステージを更新（MTG確定 → MTG実施 は物証があるので自動。R6 の例外）
```

### Note のフォーマット（会議後・ご指示の9項目）
```
【BondEx AI 議事録】2026-08-26 商談 / 安田様(DMC)
Fathom: https://fathom.video/calls/798899252

■ Meeting Summary
■ Current Challenges
■ Business Opportunity
■ Decision Maker
■ Budget
■ Timeline
■ Risk
■ Next Action
■ Recommended Follow-up

--- 以下は機械が読む行。編集しないでください ---
bondex-event-id: <uuid>
```
最終行の識別子により、**同じ会議で二度 Note を作りません**（HubSpot のカスタム項目を消費せずに
重複防止を実現します。無料プラン 10 個制限への対策）。

> Phase 1 で取得した実データを見る限り、Fathom の要約はすでに
> 「現状の課題 / 料金体系 / トライアル / DMC背景」まで構造化されており、品質は十分です。
> AI の役割は「翻訳」ではなく「BondEx の営業フォーマットへの再配置」になります。

## 7. 成果物5「Claude Agent 構成」

4 つのエージェントに分割します。1 つの巨大プロンプトにしないのは、**誤判定したときに
どこを直せばよいか分かる**ようにするためです（成果物10: 保守しやすい構成）。

| エージェント | モデル | 入力 | 出力 | 使用頻度 |
| --- | --- | --- | --- | --- |
| **A1 Triage** | Haiku 4.5 | メール1通の件名+冒頭500字 | `{is_sales: bool, confidence}` | 約50回/日 |
| **A2 Thread Analyst** | Sonnet 5 | スレッド全文（最大10通）+ 会社の現在状態 | 抽出12項目 + 提案ステージ + 根拠 | 約10回/日 |
| **A3 Meeting Analyst** | Sonnet 5 | Fathom要約 + 文字起こし + 会社の現在状態 | 議事録9項目 + 抽出12項目 + Task案 | 約5回/週 |
| **A4 Morning Briefer** | Sonnet 5 | 全社の現在状態サマリ（Supabaseから集計済み） | 朝レポート本文 + 今日やるべきTOP10 | 1回/日 |

### 全エージェント共通の鉄則（プロンプトに明記する）
1. **書かれていないことを埋めない。** メール/文字起こしに無い情報は `null`。推測禁止。
   （谷口さんの既存ルール「メール・電話・URL・住所を未確認のまま書き込まない」をそのまま継承）
2. **必ず根拠を引用する。** 各抽出項目に、判断の元になった原文の該当箇所を添える。
3. **確信度を正直に出す。** 迷ったら低く出す。低いものは自動適用されないので、
   低く出しても損はしないと明示する。
4. **個人携帯番号を出力しない。**（既存ルール）
5. **金額は数値のみ。** 「500万くらい」は数値にせず原文のまま `note` に残す。

### 出力の検証
各エージェントの出力は Zod スキーマ（既存の `scripts/crm-sync/schema.ts` を拡張）で検証します。
スキーマ違反は `change_set` に入れず、エラーとして朝レポートに出します。**壊れた JSON が
HubSpot に届く経路は存在しません。**

## 8. 成果物10「保守しやすい構成」


### WhatsApp を後から足せるようにする仕掛け
すべての取り込み層は `ChannelEvent` という同じ型を返します。
```ts
type ChannelEvent = {
  channel: "gmail" | "calendar" | "fathom" | "whatsapp" | "phone"
  direction: "inbound" | "outbound"
  occurredAt: string        // ISO8601
  externalId: string        // 冪等化キー
  participants: { email?: string; phone?: string; name?: string }[]
  subject?: string
  body: string
  raw: unknown
}
```
WhatsApp 追加時に触るのは `collectors/whatsapp.ts` **1ファイルだけ**です。
判断層・反映層・ダッシュボードは一切変更不要にします。

### 運用上の「壊れにくさ」
| リスク | 対策 |
| --- | --- |
| AI が誤ってステージを進める | R1〜R6 + 確信度 0.80 閾値 + 朝レポートでの事後確認 |
| 同じイベントを二度処理 | `sales_event.external_id` の一意制約（DB レベルで防ぐ） |
| HubSpot API 障害 | `change_set` は残るので、復旧後に再実行すれば追いつく |
| プロンプト変更で挙動が変わる | プロンプトを `.md` に分離 + 過去イベントでの回帰テスト（`--replay`） |
| 誤って本番に書く | `--apply` 未指定なら物理的に書き込まない（既存 crm-sync と同じ作法） |
| AI 費用の暴走 | 1日あたりのトークン上限を設定。超えたら停止して朝レポートで通知 |

## 9. 「会社画面を開いた瞬間に30秒で理解できる」の実現方法

無料プランではカスタム項目が足りないため、HubSpot の Company 画面の**左サイドバー上部**に
